# DataForge 数据开发平台项目计划书

## 一、项目概述

### 1.1 项目背景

过去十余年，企业数据团队的作业模式并未发生本质变化：手动搭建数据管道、逐行编写 ETL 逻辑、人工排查任务异常、在多个系统之间反复切换。行业调研数据显示，一个 10 至 15 人的中型数据团队，约六到七成的工时被消耗在配置同步任务、编写标准 SQL、排查数据质量、维护元数据文档等重复性操作上，真正投入数据建模、业务分析与架构设计的精力不足三成。

2025 年以来，大语言模型从"代码生成器"进化为"意图理解与任务执行体"，数据研发的核心命题从"代码写不完"转向"AI 生成的代码是否正确"。但这个命题背后有一个更深层的前提常被忽略：**智能体要正确理解业务数据，靠的既不是更大的模型，也不是更巧的提示词，而是企业能否为它提供规范、无歧义、可检索的信息**——一张表是什么、一个指标怎么算、数据从哪来到哪去、由哪个任务在何时产出。缺少这些信息，智能体就只能"看似会写 SQL，实则猜口径"，产出越大、错得越快。

这一进化最先在通用编程领域被验证：以 opencode、WorkBuddy、Cursor、Claude Code 为代表的 AI 编程助手，已经把"人提需求、智能体编码、人做确认"变成日常。但这类工具有一个共同前提——**提需求的人就是写代码的人**：需求以技术语言表述（用什么语言、读哪些表、按什么粒度聚合），智能体的上下文是代码仓库与工程结构，使用者天然具备把业务诉求翻译成技术指令的能力。

数据开发恰恰不满足这个前提：**懂业务的人不会写 SQL，会写 SQL 的人不懂业务**。因此本项目的落点不是做一个"更会写代码的工具"，而是把 AI 编程助手已经验证有效的范式**往业务方那一侧前移一格**——让不懂代码的业务方也能直接驱动数据开发；为此必须把"让智能体正确理解业务数据"所需的**规范开发环境**与**四类基础信息**系统性地补齐。"谁站在需求的起点上"，是本平台与 AI 编程助手、与 DataWorks 等云数据平台的分界线，详见 1.3。

### 1.2 项目定位

DataForge 是面向数据开发的一体化平台，核心目标是**让智能体正确理解业务数据**。平台由四大核心组件构成：

| 组件 | 形态 | 提供的关键能力 | 在"智能体理解业务数据"中的角色 |
| --- | --- | --- | --- |
| dataforge | 桌面应用 | 规范开发环境：代码头参数声明、编译校验、命名与口径约束 | 从源头保证开发产生的信息规范且前后相互关联 |
| dataforge-server | 平台服务 | 库表描述信息、数据指标描述信息、统一身份与权限 | 回答"表/字段是什么、指标口径是什么" |
| Marquez | 开源系统（集成） | 数据血缘信息（OpenLineage） | 回答"数据从哪来、流向哪、影响谁" |
| DolphinScheduler | 开源系统（集成） | 任务依赖信息（工作流 / DAG / 调度） | 回答"数据由什么任务、在何时产出" |


四大核心组件共同回答同一个问题——**如何让智能体正确理解业务数据**：dataforge 构建规范开发环境，保证源头信息规范且前后关联；dataforge-server 提供库表与指标描述，回答"是什么"；Marquez 提供血缘，回答"从哪来、到哪去"；DolphinScheduler 提供任务依赖，回答"何时、依赖什么产出"。

> **强调一：谁使用本平台。** 本平台的第一使用者不只是数据工程师。**业务需求方是平台内的一级角色**——他不需要写代码，也不需要先把需求翻译成技术语言，只需要在开发助手里把"要算什么、多久要、多准才行"讲清楚，其余由智能体与平台完成。这一点决定了本平台的全部设计重心（见 1.3）。

> **强调二：本项目所有程序可在企业内部免费使用（代码不开源）；公司主要收益来源为数据开发与集群运维服务。**

### 1.3 差异定位：与 AI 编程助手、云数据平台的分界在"谁提需求"

本平台有三类参照物：AI 编程助手（opencode、WorkBuddy、Cursor、Claude Code 等，已经证明"人提需求、智能体编码"这条路走得通）、云厂商一体化数据开发治理平台（阿里云 DataWorks、华为云 DataArts Studio、腾讯云 WeData、瓴羊 Dataphin）、开源 Web 开发门户（Apache Hue，在 Cloudera 发行版中已改名 Cloudera Data Explorer），此外还有企业自建脚本与自研工具。**DataForge 与它们的分界不在"用不用 AI"，而在"谁站在需求的起点上"。**为控制表宽，本节各表的列名从简：**AI 编程助手** 指 opencode / WorkBuddy / Cursor / Claude Code 等，**云数据开发平台** 指 DataWorks / DataArts Studio / WeData / Dataphin 等（含各自 Copilot），**Hue** 指 Cloudera Data Explorer（开源 Hue 亦可独立部署），**其他云平台** 指上面未单列的 DataArts / WeData / Dataphin。

| 维度 | AI 编程助手 | 云数据开发平台 | DataForge |
| --- | --- | --- | --- |
| 谁提需求 | **开发者本人**——提需求的人就是写代码的人 | 业务方在平台**之外**提（会议 / 文档 / 工单），由开发者转述进平台 | **业务方在平台之内直接提**——业务需求方是平台一级角色 |
| 需求的表述方式 | 技术语言：用什么语言、读哪些表、按什么粒度聚合 | 需求文档或工单；进入平台后仍需开发者翻译成任务配置 | **业务语言**：要算什么指标、什么口径、多久要、多准才行、哪些是敏感数据 |
| 智能体读到的上下文 | 代码仓库、工程结构、依赖源码 | 云上元数据、表结构、任务配置 | **规范开发环境 + 库表与字段描述 + 指标口径 + 血缘 + 任务依赖**（五类信息，见 3.2） |
| 需求到代码由谁翻译 | 开发者自己（他同时是需求方与实现方） | 开发者，或由开发者驱动的 Copilot 辅助 | **智能体**：需求编写 → 数仓设计 → 数据开发 三段接力（见 3.3） |
| 交付终点 | 本地代码 | 云上任务，运维由客户自理或另购服务 | **程序 + 调度任务**，并可整体交由我方代开发与代运维（见 1.6） |
| 业务方是否需要懂技术 | 需要 | 不需要，但需求必须经人转述 | 不需要，且**无需转述** |

**一句话概括**：DataForge 做的是把 AI 编程助手已经跑通的能力**前移到业务方这一侧**——它不是让开发者写得更快，而是让不懂代码的业务方也能直接开工。因此 AI 编程助手不是本项目的竞品，而是本项目所继承的范式；云数据平台也不是本项目的对手，而是对照面：**它们让"会写代码的人"和"买了平台的人"更高效，DataForge 让"有业务问题的人"自己开工。**

**为什么"谁提需求"这个位置差异至关重要**，有三点：

1. **数据开发的损耗主要发生在"业务语义 → 技术语义"这一跳。**通用编程里这一跳在开发者脑中完成、成本近乎为零；数据开发里它要跨越专业壁垒，且每传递一轮都可能丢信息。把起点前移到业务方，等于把这一跳交给上下文可核查的智能体，而不是交给会议纪要。
2. **它决定了智能体的上下文从哪来。**开发者提需求时，上下文是代码仓库；业务方提需求时，智能体读不懂代码仓库，只能依赖库表描述、指标口径、血缘与任务依赖——这正是本项目把"让智能体正确理解业务数据"作为第一设计原则的原因（见 3.2）。**换句话说，四类基础信息不是附加功能，而是"业务方能提需求"这件事的前提条件。**
3. **它是数据代开发服务能够成立的技术基础。**既然业务方能在平台内用业务语言把需求讲清楚，智能体又能把它翻译成设计、代码与调度任务，那么"企业方人员提出数据开发需求、我方完成数据处理程序开发及上线维护"就不再依赖驻场与口传——服务可以被产品化、被计量、被交接。详见 1.6。

**再按产品能力逐项对照。**下表把开源门户与云平台拉到同一组能力维度上逐项比较，**一项能力一行**，顺序为数据集成 → 数据治理 → 开发环境 → 作业调度 → 数据血缘 → 权限管理 → 任务管理 → 指标管理 → 知识管理 → AI 能力落点。**对手能力按公开资料整理，具体版本与功能以厂商文档为准。**

| 能力维度 | DataForge | Hue | 阿里云 DataWorks | 其他云平台 |
| --- | --- | --- | --- | --- |
| 数据集成 | **不自研同步引擎**：同步任务作为 DolphinScheduler 任务类型（DATAX / SEATUNNEL / SQOOP 等）被编排，连接器由集群既有组件提供；本平台的主路径是在开发环境里**写程序做同步**（多执行策略：JDBC / Kyuubi / Spark / Flink / HBase / Doris），另有数据源配置与连接测试、分布式文件浏览（HDFS / JuiceFS / S3） | 以查询网关为主体（Hive / Impala / Spark SQL / Trino / Phoenix），不含同步与迁移 | 自建数据集成模块：50+ 异构数据源连接器、离线与实时（CDC）同步、整库与分库分表、Serverless 资源组弹性伸缩 | 各自的数据集成模块，并提供多云 / 跨云接入（WeData 另在实时链路做数据对账） |
| 数据治理 | 治理动作**前移**到生成期与提交期：代码规范、参数声明、编译与 SQL 校验在代码写出来时约束，质量规则类型被规范为 7 类、校验任务独立成文件挂在处理任务下游；库表与字段描述随 DDL 增量沉淀，未标注清单与同步失败告警可见；行数、存储量与冷热保留天数已随元数据采集，配套的数据价值评估列入规划 | 无治理模块（无质量规则、无脱敏、无资产目录） | 平台侧一体化：数据质量（规则模板库 → 监控规则 → 与任务绑定 → 强 / 弱规则）、数据保护伞（敏感数据识别与分级分类、脱敏）、数据地图与资产目录 | 数据标准、质量规则体系与资产目录；Dataphin 以 OneData 方法论与数据标准见长 |
| 开发环境 | 桌面端 IDE：**Java / Scala / Python / SQL / Shell 五类语言同一环境**内编辑与调试；Java / Scala 语言服务（悬停 / 跳转 / 补全 / 诊断）；本地 Maven 编译与 SQL 语法校验；代码头三段式参数声明（程序 / 资源 / 任务）；Git 同步、文件历史回滚与回收站保留策略 | 浏览器内 SQL 编辑器（Hive / Impala / Spark SQL / Trino）与 Spark / PySpark 交互式笔记本，左栏库表与对象存储浏览、查询历史 | 云上 IDE / Notebook，以 SQL / Python / Shell 为主；Java / Scala 需自行编译打包后以资源或 UDF 形式引用 | 以 SQL / Python / Shell 为主，无本地编译闭环 |
| 作业调度 | 集成 DolphinScheduler：工作流定义（含 DAG 画布）、调度配置、**一键提交调度**（含文件夹级批量），代码头声明的参数自动落地任务节点；提交带环境维度（prod / gray / test，默认 test） | 可在门户内调度查询与工作流，不涉及程序编译与提交 | 自带调度：周期实例、任务依赖与基线、补数据，与同步任务共用一套工作流 | 自带调度，支持把开发产物发布到调度系统 |
| 数据血缘 | 集成 Marquez（OpenLineage）：表级与字段级血缘图谱、影响分析与溯源；**仅生产环境提交时注入**，覆盖经平台提交的 Spark 作业，同步链路的血缘同样接上 | 无血缘图谱，提供查询历史与执行计划 | 内置血缘解析：表级 / 字段级血缘与影响分析 | 内置血缘解析，覆盖任务与数据服务链路 |
| 权限管理 | 角色—资源三级授权；**行 / 列级权限在 SQL 下发前改写**（行条件并入 WHERE、投影列裁剪为白名单），命中约束但无法安全改写时一律拒绝；列级脱敏（full / 身份证 / 手机 / 邮箱 / 部分）多角色按列取更严者，且**对智能体同样遮蔽**；可选装 spark / flink-listener，在引擎侧分析期拦截写入，可覆盖绕过平台提交的作业 | 以自身用户 / 组管理与底层引擎授权为主，无行 / 列级改写机制 | 云侧权限体系（RAM + 空间成员角色），配套敏感数据识别与脱敏；写入合规靠平台侧权限与审批 | 权限体系与数据分级分类（DataArts 在信创合规上见长） |
| 任务管理 | 任务实例与运行实例集中可查：工作流定义、任务配置、调度配置与运行状态在同一处呈现，失败可沿任务依赖与集群部署信息定位；**自动化问题排障列入规划** | 查询历史与工作流执行记录 | 运维中心：实例运维、失败重跑与补数据、智能诊断与告警 | 运维中心 / 实例运维，并对异常做归因 |
| 指标管理 | **指标体系是平台的一等资产**：指标编码、业务定义、计算表达式、责任人与刷新周期，字段级绑定到数据源 / 库 / 表 / 字段，构成可检索、可复用的指标口径目录；指标编码是需求—设计—开发三段产物的**唯一主线**，口径只在一处定义 | 无指标口径体系 | 数据地图、智能建模与数据服务 API，指标检索用于消除二义性、避免重复计算 | 数据标准与指标体系（Dataphin 的原子指标 / 派生指标体系） |
| 知识管理 | 企业知识文档的分类、检索与维护，作为智能体上下文来源之一，并配有面向智能体的知识文档工具组；**当前为标题 / 正文关键字匹配，向量检索列入规划** | 无 | 由数据地图与资产目录承载知识检索，Copilot 侧叠加资产语义 | 资产盘点与智能推荐（WeData 的语义层支持自然语言查询转换） |
| AI 能力落点 | **智能体在桌面端本地进程推理，模型与密钥由用户自配，服务端零模型调用**；业务能力以 6 个工具组注册（compile / indicator-query / knowledge-document / lineage / metadata-agent / sql-validate），经平台接口按权限取上下文；默认沙箱运行 | SQL AI Assistant：自然语言生成 / 编辑 / 解释 / 优化 / 修复 SQL，模型由客户自选（Cloudera AI、Azure OpenAI、Bedrock 等），RAG 用表结构 + 每表 3 行样本 | DataWorks Copilot：代码生成与纠错、智能建表、发布描述、异常诊断（对接 Qwen、DeepSeek-R1），并已发布端到端的数据开发 Agent | 借云侧大模型做标准推荐、质量规则推荐、异常归因与资产盘点 |

**本平台的优势**：

1. **业务方直接提需求、智能体负责编码**（对照见上文各表）。业务需求方是平台一级角色，用业务语言提需求，智能体按「需求编写 → 数仓设计 → 数据开发」三段分别产出需求文档、数仓设计与分层 DDL、程序与调度任务；三段用同一业务名称、以指标为唯一主线贯穿，同一会话内切换角色不清空上下文（见 3.3）。
2. **开发到上线是一条闭环，且不限 SQL。**在一个开发环境里用 Java / Scala / Python / SQL / Shell 写程序：Java / Scala 本地编译（Maven）产出主 Jar 包，Python / SQL / Shell 免编译，随后**一键提交调度**，代码头声明的参数自动落在调度任务节点上。同类平台以 SQL / Python / Shell 编辑器为主，Java / Scala 通常要自己编译打包、再以资源或 UDF 形式引用，开发与上线是两段。
3. **给智能体喂上下文，而不是只给人用界面。**开发环境、库表与指标描述、血缘、任务依赖在本平台里首先是**给智能体读的上下文**——经元数据代理等接口按权限、按结构提供；并让信息缺口可见（未标注表 / 字段清单、血缘覆盖率）。
4. **推理在本地，平台不做模型调用。**智能体在桌面端本地进程执行，模型与密钥由用户自配，服务端零模型调用，适合数据不宜出内网的场景；云平台的 AI 能力默认走云侧模型。
5. **写入在引擎侧还有一道闸门。**可选装 spark / flink-listener，在计算引擎侧对写入做合规拦截——这是同类平台没有的一层，它们依赖平台侧权限与审批。

**客观说明**：在托管运维与连接器丰富度上云平台明显领先（DataWorks 的 Serverless 资源组与数十种数据源连接器、WeData 与 Dataphin 的开箱即用）；Hue 在浏览器端即开即用与稳定性上有十余年积累；云平台在数据集成、数据治理（数据质量、资产目录）等模块的完整度也更成熟。需要说明的是，本项目在这两块上的取舍是不自研同步引擎与规则引擎——同步由集群既有的 DataX / SeaTunnel 等组件承接、平台负责编排、提交与血缘，质量规则以代码为载体、由独立校验任务执行，缺的是统一视图而不是能力本身。在这个前提下，本平台进一步放弃"托管"与"连接器广度"，把工程投入集中在"多语言开发闭环 + 让智能体读懂业务数据"这一件事上；集群部署与运维由配套服务承接（见 1.6）。另需说明一点：本平台在工程上的额外复杂度（上下文供给、口径治理、面向业务方的安全边界），正来自"提需求的人是业务方"这一前提——这是本项目主动承担的代价，不是待补的短板。

### 1.4 建设目标

总体目标：建成"规范开发环境 + 四类基础信息"的数据开发平台，使智能体能够正确理解业务数据，把"AI 生成的代码是否正确"从风险变成可验证的常态。具体目标分为七个方面：

1. **规范开发环境目标**：由 dataforge 桌面端把数据开发收敛到一个受约束的入口——代码头参数声明、编译与 SQL 校验、命名与口径约束，确保开发产生的信息规范且前后相互关联。
2. **信息底座目标**：由 dataforge-server 沉淀库表描述信息与数据指标描述信息，作为智能体理解"数据是什么"的权威口径来源。
3. **血缘与依赖目标**：集成 Marquez 获取数据血缘信息、集成 DolphinScheduler 获取任务依赖信息，让数据"从哪来、何时产出、影响谁"可追溯。
4. **智能体上下文闭环目标**：将上述规范环境与四类信息汇聚为智能体的上下文供给层，使其在生成代码前即可调用准确的业务上下文，而非凭空推断。
5. **业务方直提需求目标**：把业务需求方作为平台一级角色纳入开发闭环——他无需懂 SQL、也无需经开发者转述，用业务语言即可提出需求；由智能体完成从需求到数仓设计、程序代码与调度任务的翻译，人只做澄清、确认与验收（见 3.3）。这是本平台与 AI 编程助手、云数据平台的根本差异，也是数据代开发服务可规模化交付的前提（见 1.3、1.6）。
6. **自动化运维目标**：为 SQL / Scala / Java 三类程序提供**一键上线调度**（已具备）——把编译、参数声明、提交与依赖编排收敛为一次操作；并推进**自动化问题排障**（功能规划中），基于集群部署信息与任务依赖关系，在任务失败时自动定位到受影响的上游任务或资源瓶颈。
7. **数据价值评估目标（功能规划中）**：整理数据资产清单及其处理所消耗的计算资源，结合数据使用情况（访问频次、下游引用等），评估数据的使用价值，识别高价值资产与长期闲置的低效资产，为资源优化与治理决策提供依据。

### 1.5 建设范围与边界

**本期建设范围**：

- dataforge 桌面端全功能客户端（规范开发环境：AI 助手、代码编辑与语言服务、编译与 SQL 校验、程序参数声明、调度提交）。
- dataforge-server 平台服务（库表描述、字段描述、指标描述、统一身份与多级权限、知识库、数据源与存储、审计）。
- Marquez 与 DolphinScheduler 的集成（血缘信息采集与图谱展示、工作流定义与任务依赖管理、运行实例监控）。

**明确不包含在本期范围**：

- 不替代底层存储与计算引擎本身（Hive / Spark / Flink / Doris / ClickHouse 由既有集群提供）。
- 不自研元数据存储引擎与血缘采集引擎，而是集成 Marquez / OpenLineage 与既有元数据体系。
- 不承担数据模型设计与数仓分层建模的方法论落地，平台只提供承载与校验能力。

### 1.6 产品与商业模式

本项目所有程序（dataforge 桌面端、dataforge-server 及配套组件）**可在企业内部免费使用**，软件**代码不开源**，以闭源形式提供。

公司的收益来源不是软件授权收费，而是以**数据开发服务**与**集群运维服务**为核心的专业服务收费——软件作为获客与留客的载体，专业服务作为主要收益来源，形成"软件免费、服务收费"的模式。

**业务方能够在平台内直接提需求，是上述服务模式得以成立的技术基础**（见 1.3）：企业方人员用业务语言提出数据开发需求，智能体完成需求澄清、数仓设计、程序编码与提交调度，我方工程师负责口径确认、评审把关、上线发布与后续运维——**企业出需求，我方出开发与运维**。

#### 1. 数据代开发服务的交付路径

数据代开发服务的成本，传统上集中在两处：需求调研与口径确认（随指标数线性增长、高度依赖驻场沟通），以及开发与上线（逐指标手写与人工配置）。基于本平台的交付路径，把这两处的承担者换了：

| 环节 | 传统数据代开发 | 基于 DataForge |
| --- | --- | --- |
| 需求提出 | 业务方口述，实施方整理成需求文档，往返多轮 | 业务方在平台内按模板直接填写，智能体一次性列出全部待确认问题 |
| 口径定义 | 会议与文档对齐，易出现同一指标多种算法 | 指标编码在需求阶段确定，需求 / 设计 / 程序三段产物共用同一编码（见 3.3） |
| 设计与编码 | 工程师逐指标手写 | 智能体产出设计文档、分层 DDL 与程序，工程师评审确认 |
| 编译与上线 | 人工打包，在调度系统里手工配置参数 | 本地编译产出主 Jar 包，代码头参数自动落地任务节点，一键提交调度 |
| 运维与变更 | 依赖原开发人员的记忆，换人即断层 | 口径、血缘、任务依赖在平台内可查，换人可接手 |

**由此得到三个服务特征**：单指标交付的人工投入从"编写"转为"确认"——人不再是产能瓶颈；服务可以按指标数计量与定价（见下节）；交付物不依赖个人记忆，长期代运维可持续。**这也是"软件免费、服务收费"能够闭环的原因：软件把服务的人力成本压下来，服务把软件的价值变现。**

### 2.2 功能需求

#### 1. 规范开发环境（dataforge）

- **AI 开发助手**：支持多模型切换、工具调用（命令执行 / 文件编辑 / 网络检索 / 任务 / Skill 等）、沙箱执行、权限审批与交互式问答；支持会话切换与任务历史回溯；支持不同任务类型的角色化系统指令。
- **代码编辑与智能提示**：提供专业 IDE 级编辑体验，包含文本语法高亮、主题、快捷键；通过语言服务器协议桥接 Java 与 Scala 语言服务，提供悬停提示、定义跳转（含依赖源码）、补全、诊断。
- **编译与校验**：本地提供 Java / Scala 的 Maven 编译服务与 SQL 语法校验能力，供 AI 助手与编辑器调用；编译前自动生成 Maven 工程配置。
- **程序参数声明与提交调度**：程序文件头部以结构化字段声明程序参数、资源参数与任务参数；运行前必须确认参数；提交调度时把声明参数落地到调度任务节点，支持文件夹级批量提交与环境标识（默认 test）。
- **文件与版本管理**：工作区文件浏览与多选操作；Git 仓库自动同步；文件历史与回滚；删除走回收站机制，并按保留期与容量上限自动清理。

#### 2. 信息底座（dataforge-server）

- **库表与字段描述**：库表元数据浏览、字段明细、元数据同步，沉淀"表/字段是什么"的权威描述。
- **数据指标描述**：指标体系维护（指标定义与计算口径），支持跳转血缘查看关联字段。
- **统一认证与授权**：无状态令牌认证、登录登出、当前用户信息获取；基于角色与租户的权限控制，权限可到行级与列级；操作审计日志。
- **数据源与存储管理**：数据源配置的增删改查、连接测试（Kyuubi / Doris / ClickHouse / MySQL 等）；存储配置与分布式文件浏览（HDFS / JuiceFS / S3 / 本地）。
- **知识管理**：企业知识文档的分类、检索与维护，作为智能体上下文来源之一。

#### 3. 血缘与任务依赖（Marquez / DolphinScheduler）

- **数据血缘**：通过 OpenLineage 采集血缘信息，图谱化展示表级与字段级血缘，支持影响分析与溯源。
- **任务依赖**：管理工作流定义（含 DAG 画布）、任务配置、调度配置、任务实例与运行实例，呈现数据"何时、依赖什么产出"。

#### 4. 运维与治理类能力（规划中）

前 3 类需求构成"让智能体正确理解业务数据"的基础，本期优先交付；以下 3 项决定平台在业务侧能否长期被用起来，列入规划并各自给出就绪判据：

- **自动化问题排障**：任务失败时，依据集群部署信息与任务依赖关系自动定位到受影响的上游任务或资源瓶颈，输出根因候选与影响范围。就绪判据：对给定失败实例，能给出至少一条可验证的根因线索（上游任务未产出 / 资源不足 / 配置错误），且在平台内可追溯到对应任务节点。
- **知识检索增强**：把知识库检索从当前的关键字匹配（标题与正文的模糊匹配）升级为向量检索，提升智能体生成代码前检索业务知识的命中率。就绪判据：同一组业务问题上，向量检索的相关文档命中率高于关键字检索；检索接口与现有知识库接口兼容，智能体侧工具签名无需变更。
- **数据价值评估**：以数据资产清单、其处理所消耗的计算资源、以及使用情况（访问频次、下游引用）三个输入评估数据使用价值，识别高价值资产与长期闲置的低效资产。就绪判据：可输出资产级价值排序，且"资源消耗"与"使用情况"两项输入均有可核查来源。

> **说明**：以上 3 项为规划中能力，不纳入本期功能验收；其需求条目、对应模块与就绪判据的对应关系见 7.5。

## 三、总体架构

### 3.1 架构总览

平台由四大核心组件（dataforge、dataforge-server、Marquez、DolphinScheduler）构成，组件之间边界清晰：桌面端承载交互与本地计算，服务端承载信息底座，Marquez 与 DolphinScheduler 承载血缘与任务依赖。

| 组件 | 承载能力 | 对智能体理解业务数据的贡献 |
| --- | --- | --- |
| dataforge（桌面端） | 规范开发环境：编辑器、语言服务、编译校验、代码头参数声明、AI 助手运行时（沙箱） | 保证开发产生的信息规范且前后相互关联 |
| dataforge-server | 库表描述、字段描述、指标描述、统一身份与多级权限、数据源与存储、审计 | 提供"表/字段是什么、指标口径是什么" |
| Marquez | 数据血缘信息（OpenLineage 采集与图谱展示） | 提供"数据从哪来、流向哪、影响谁" |
| DolphinScheduler | 任务依赖信息（工作流 / DAG / 调度 / 实例） | 提供"数据由什么任务、在何时产出" |

### 3.2 核心设计：智能体理解业务数据的五类信息

本平台把"让智能体正确理解业务数据"作为第一设计原则。智能体在生成或修改数据代码前，需要五类输入才能做到不凭空推断：

| 信息 | 来源组件 | 回答的问题 |
| --- | --- | --- |
| 规范开发环境 | dataforge | 代码结构、参数声明、命名与口径是否规范、是否前后关联 |
| 库表描述信息 | dataforge-server | 表与字段是什么、业务含义与约束 |
| 数据指标描述信息 | dataforge-server | 指标的计算口径与数据来源 |
| 数据血缘信息 | Marquez | 数据从哪来、流向哪、影响谁 |
| 任务依赖信息 | DolphinScheduler | 数据由什么任务、在何时、依赖什么产出 |

这五类信息共同构成智能体的上下文供给层：规范开发环境决定信息**源头是否规范、前后是否关联**，库表与指标描述决定**语义是否权威**，血缘与任务依赖决定**来龙去脉是否可追溯**。平台的建设顺序与优先级，均以"这五类信息是否就绪"为依据。

### 3.3 需求驱动的开发闭环：业务方 → 需求 → 智能体编码

**设计思路**。AI 编程助手（opencode、WorkBuddy 等）已经验证了"人提需求、智能体编码、人做确认"这一范式，但它们默认**提需求的人就是写代码的人**：需求以技术语言给出，从业务诉求到技术指令的翻译由开发者自己在脑中完成。**DataForge 把提需求的人换成业务方**，于是必须额外解决三件事：① 业务语言到技术语言的翻译由谁做；② 口径如何保证只有一个版本；③ 不懂技术的业务方进入同一个开发平台后，安全边界如何划。前两件由"三段接力 + 指标唯一主线"解决，第三件由角色—资源三级授权与 SQL 下发前的行 / 列改写解决（见 4.2）。

数据开发最常见的失败不是"写不出 SQL"，而是需求在传递中走形——业务方口头讲一版、需求文档写一版、数仓设计再翻译一版、开发按各自理解落地一版，四版之间没有强制对齐，等发现口径不一致时已经投产。本平台的思路是：**把业务方、需求与编码放进同一个平台、同一份上下文，用"指标"作为唯一主线贯穿三段产物，让智能体承担从需求到代码的翻译，人只负责提出需求与确认。** 业务需求方因此不是"平台外的提需求的人"，而是平台内的一级角色。

**三个角色、三份产物**。平台的服务端角色体系与开发链路一一对应，开发助手内的任务类型即角色：

| 环节 | 角色（任务类型） | 产出物 | 对下游的作用 |
| --- | --- | --- | --- |
| 需求 | 业务需求方（需求编写） | `docs/{业务名称}_开发需求.md` | 用业务语言定义"要算什么"：指标口径、数据范围、时效要求、质量要求与敏感数据范围 |
| 设计 | 数据架构师（数仓设计） | `docs/{业务名称}_数仓设计.md`、`ddls/{分层}_ddl.sql` | 把需求翻译为数仓设计：分层与表结构、为指标分配编码并绑定字段、定义质量规则与脱敏建议 |
| 开发 | 数据开发工程师（数据开发） | `{语言}/{分层}/{程序文件}`、调度任务 | 按指标编码实现程序、声明代码头参数与依赖、编译校验、一键提交调度上线 |

**衔接关系：一套契约、四条同源线**。三段产物不是三份各说各话的文档，而是共享同一份契约：

- **同一业务名称贯穿三份产物**，不得各自另起名——这是"同一条链路能被检索到一起"的前提。
- **指标是唯一主线**：业务需求方定义"要算什么"，数据架构师分配指标编码并绑定字段，数据开发工程师按编码实现；口径要改只改一处，三段自动对齐。
- **四条信息线端到端同源**：① **数据时效**——需求写明的更新频率与最晚可用时间，必须落到设计的表名刷新周期后缀与更新策略，再到开发的程序名执行周期后缀与调度周期；出现降级（需求要小时级、落地成日级）必须显式说明原因并列入待确认问题。② **数据源名称**——三处同名。③ **数据质量**——需求用业务语言提要求，设计定义规则名、校验对象、阈值与处置方式，开发实现为独立的质量校验任务挂在处理任务下游。④ **敏感数据**——需求识别范围，设计分类分级并给出脱敏建议，开发实现脱敏，全链路不得明文落库。

**从需求提出到编码完成的流转**：

1. 业务方在开发助手中以「需求编写」角色提出诉求。智能体先做需求澄清：确认业务背景、目标、使用对象与决策场景；信息不足时一次性列出全部待确认问题，避免多轮追问。
2. 澄清完成后产出需求文档 `docs/{业务名称}_开发需求.md`，并标注本需求涉及的敏感数据范围。
3. 切换到「数仓设计」角色。智能体读取该需求文档，产出数仓设计文档与分层 DDL，为指标分配编码并绑定字段。
4. 切换到「数据开发」角色。智能体依据设计文档与指标编码实现程序（Java / Scala / Python / SQL / Shell 任选），在代码头声明程序参数、资源参数、任务参数与依赖，经编译与 SQL 校验后一键提交调度。
5. 全过程可以在同一会话内完成：**切换角色不新建会话**——任务类型的系统指令按轮下发，新角色从下一轮生效，之前的对话与工具调用结果全部保留，智能体始终知道"前面做了什么"。
6. 产出物落在同一工作区，受 Git 版本管理与文件权限约束，删除与回滚走安全评估闸门与回收站；指标定义与编码沉淀在服务端，成为可检索、可复用的资产。

**价值**：

- **需求不再靠口头传递**。需求是平台内可检索、可追溯的一等产物，与设计、代码同源命名，一条链路一眼可查。
- **口径只在一处定义**。指标编码是唯一主线，业务方用业务语言提、架构师编码绑定字段、开发按编码实现，避免"同一个指标四种算法"。
- **人力从翻译变成确认**。需求到代码的翻译由智能体承担，人只提出需求、澄清疑问与验收结果。
- **四类约束不会被漏掉**。时效、数据源、质量、敏感数据在需求阶段就写清并逐段传递，降级必须显式说明，不会在传递中静静消失。
- **业务方能安全地进入同一个平台**。业务需求方是平台一级角色，受角色—资源三级授权约束；行 / 列级权限在 SQL 下发前改写生效——共平台不等于共数据。

### 3.4 关键技术设计决策

**决策一：信息底座先行。**

智能体能力的上限不由模型决定，而由它能否读到规范、无歧义的业务信息决定。因此平台的投入优先级是先建规范开发环境与四类信息底座，再逐步扩展运维与治理类能力。

**决策二：从源头约束，而不是事后清洗。**

库表描述、指标口径这些信息若靠事后人工补录，必然残缺且滞后。平台在开发环境侧就通过代码头参数声明、编译校验、命名与口径约束，让"规范"发生在信息产生的时刻，而不是在信息流转之后的补救阶段。同步地，代码头参数声明把程序入参与调度任务的参数显式对齐，使开发阶段产生的信息与上下游环节可以直接衔接——规范解决的是同一件事有没有唯一说法，关联解决的是这件事与上下游能否对上。

**决策三：血缘与任务依赖直接集成成熟开源系统，不自研。**

数据血缘与任务调度是通用基础设施，Marquez（OpenLineage）与 DolphinScheduler 生态成熟。平台以集成代替自研，把工程投入集中在"如何把这些信息汇聚成智能体可用的上下文"这一差异化能力上。

**决策四：AI 助手以内置运行时 + 沙箱方式提供，而非云端调用。**

AI 助手需要执行命令、读写工作区文件、调用本地编译服务，这些能力要求它运行在用户本机且受控。因此助手以本地进程形式由客户端托管，固定监听本机端口，并在 macOS 与 Linux 上以系统级沙箱包装执行。

## 四、组件设计

### 4.1 DataForge 桌面端（规范开发环境）

**技术形态**：基于 Electron 44 的跨平台桌面应用，渲染层采用 React 19 + Vite 8 + TypeScript 7。当前工程规模为 336 个 TypeScript / TSX / CSS 文件、约 7.99 万行代码。

**主进程能力**：

| 模块 | 职责 |
| --- | --- |
| AI 助手运行时管理 | 启动、监督、终止本地助手进程，固定监听本机端口；macOS 以系统沙箱、Linux 以容器沙箱包装；退出时优雅清理进程与数据库锁文件 |
| 编译服务 | 本地编译 HTTP 服务，随机端口 + 令牌鉴权，端点通过环境变量注入 AI 助手进程 |
| 语言服务桥 | 把 Java / Scala 语言服务器的标准输入输出流转换为 WebSocket，供前端语言客户端使用 |
| 工程生成与编译 | Maven 工程生成与 Java / Scala 编译、本地运行 |
| 配置与凭据存储 | 应用配置与安全凭据的分层存储，敏感项不落前端可读位置 |
| 平台适配 | 三平台路径、二进制命名与沙箱策略的差异化处理 |

**规范开发环境的关键机制**：

- **代码头参数三段式**：程序文件头部以结构化字段声明程序参数（业务入参）、资源参数（资源诉求）、任务参数（提交与引擎侧参数），取值为真实值。它有统一消费面：运行程序时取参数名预填，提交调度时取真实值写入调度任务节点。
- **运行程序必须确认参数**：任何程序运行前弹出参数确认窗口，参数以键值对逐行编辑，语义为"所见即所发"。
- **编译与 SQL 校验前置**：Java / Scala 提交调度必经本地编译（主 Jar 包由编译结果回填，未通过则无法提交）；SQL 语法校验作为编辑器与 AI 助手的能力提供，当前覆盖 MySQL / Doris / ClickHouse，用于把语法与结构问题拦在开发阶段。
- **删除与回滚安全闸门**：所有删除与回滚操作先经过纯函数化的安全评估，快照根节点为空一律中止；删除走回收站目录并生成清单，且回收站目录对版本控制隐身。回收站另有保留策略——默认保留 30 天 / 50 个批次 / 2 GiB，最新 2 个批次永不清理，目录名解析不出批次时间的一律不清理；清理延迟合并执行（一次回滚连续移入上百个文件只统计一次），删除目标必须是回收站目录的直接子项，越界即拦截。回收站定位为误删缓冲而非备份，超期版本的保障由 Git 承担。
- **沙箱化执行**：AI 助手的命令执行默认运行在系统沙箱内。

渲染层功能模块包括：开发助手、编辑器、AI 面板、数据探索、指标管理、知识库、文件浏览器、调度管理、数据血缘、系统管理、设置。

### 4.2 dataforge-server（库表描述 + 指标描述）

**技术形态**：基于 SpringBoot 3.2.1 + Java 17 的单体服务，采用"通用层 + 业务模块层"分层结构，共 6 个业务模块、20 个控制器、28 张表。

| 层次 | 内容 |
| --- | --- |
| 技术底座 | Spring Security 6 + JWT（jjwt 0.12.3）、MyBatis-Plus 3.5.5、MySQL / PostgreSQL / MariaDB / H2、Knife4j 4.4.0（OpenAPI 3）、Hutool 5.8.24 |
| 元数据模块 | 库表与字段元数据、元数据同步、元数据代理（供智能体使用）、指标与指标字段、未标注表 / 字段清单、元数据同步失败告警 |
| 系统管理模块 | 认证登录与令牌、用户、角色、权限与菜单权限、租户、项目权限、操作审计日志 |
| 运维管理模块 | 数据源配置、存储配置、分布式文件浏览、执行引擎管理 |
| 数据开发模块 | 开发工程、程序参数、代码执行（多引擎策略，含执行结果 / 日志 / 取消 / 校验）、Jar 依赖管理 |
| 知识库模块 | 企业知识文档管理 |
| 数据质量模块 | 数据质量校验结果管理 |

**对智能体理解业务数据的贡献**：通过元数据同步沉淀库表与字段描述，通过指标体系沉淀指标口径，通过元数据代理接口（`/metadata/agent`）把这些信息以结构化方式提供给智能体，回答"表/字段是什么、指标怎么算"。

**权限模型**：支持到行级与列级（`sys_table_permission_row` / `sys_table_permission_column`），文件权限按路径 + 存储配置维度控制；行 / 列约束在 SQL 下发前改写生效（行条件并入 WHERE、投影列裁剪为白名单），覆盖 JDBC / Kyuubi 与 Spark / Flink / HBase 路径，命中约束但无法安全改写时一律拒绝执行。

### 4.3 Marquez（数据血缘）

Marquez 是开源的元数据与血缘服务，本平台通过 OpenLineage 标准采集作业级与数据集级血缘事件，并由桌面端的血缘视图图谱化展示。

| 能力 | 说明 |
| --- | --- |
| 血缘采集 | 通过 OpenLineage 传输端点采集作业运行时的输入 / 输出数据集事件 |
| 血缘展示 | 桌面端基于图可视化组件呈现表级与字段级血缘关系 |
| 影响分析与溯源 | 上游变更时识别受影响的下游表，指标异常时沿血缘上溯定位来源 |

**对智能体理解业务数据的贡献**：血缘信息回答"数据从哪来、流向哪、影响谁"，是智能体判断"改动这张表会影响什么""这个指标的数据源头在哪"的依据。

### 4.4 DolphinScheduler（任务依赖）

DolphinScheduler 是开源的工作流调度系统，本平台集成其项目管理、工作流定义、任务编排与实例监控能力，并把开发环境声明的参数落地为任务节点参数。

| 能力 | 说明 |
| --- | --- |
| 工作流定义 | 桌面端提供工作流定义编辑器与 DAG 画布，可视化编排任务依赖 |
| 任务配置 | 任务节点配置（程序参数、资源参数、任务参数、环境标识） |
| 调度与实例 | 调度配置、任务实例与运行实例监控 |

**对智能体理解业务数据的贡献**：任务依赖信息回答"数据由什么任务、在何时、依赖什么产出"，是智能体判断数据时效性与下游可用性的依据。

## 七、验收标准与质量保障

### 7.1 交付物清单

- 桌面端应用的三平台安装包与升级包。
- 平台服务端的容器镜像（多架构）与编排文件、初始化脚本、启停与清理脚本、端到端自检脚本。
- 用户手册、部署手册、验收测试报告。

### 7.2 功能验收

- 桌面端在 macOS / Windows / Linux 三平台可安装启动，核心链路（登录、开发、编译、参数声明、提交调度、数据探索、血缘查看）可用。
- 平台服务端全部已声明接口通过联调与自检脚本验证，权限控制按角色生效，库表描述与指标口径可检索。
- 血缘与任务依赖在平台内可查询：表的字段血缘与任务依赖关系完整展示。
- 规划中能力（自动化问题排障、知识检索增强、数据价值评估）不纳入本期功能验收，按 2.2 第 4 条的就绪判据逐项判定，对应关系见 7.5。

### 7.3 质量保障

| 维度 | 标准 |
| --- | --- |
| 单元测试 | 桌面端依赖自动化测试框架覆盖核心逻辑；纯函数必须有分支覆盖，测试全量通过作为回归基线 |
| 类型检查 | 前端与主进程代码通过静态类型检查，无类型错误 |
| 兼容性 | 交付前在目标平台与依赖版本矩阵上逐版本执行最小用例 |
| 专项验证 | 涉及安全闸门、参数语义、权限判定的改动必须配套自动化测试 |
| 性能 | 建立性能基线并保留对比数据；关键路径有可量化的优化前后对比 |

### 7.4 交付验收方式

由项目负责人组织，交付方提供测试报告、兼容性验证记录与部署手册；验收方按功能清单逐项验证。

## 八、预期效益

**智能体正确理解业务数据**。这是本平台的首要效益：把散落在代码、文档、口头经验中的业务信息，收敛为规范无歧义的库表描述、指标描述、血缘与任务依赖，让智能体在生成代码前就能读到权威上下文，从根上降低"AI 生成代码是否正确"的不确定性。

**开发效率效益**。规范开发环境把数据开发收敛到一个受约束的入口，消除跨工具切换与手工配置的重复劳动；一键上线调度进一步把编译、参数声明、提交与依赖编排收敛为一次操作。作为方向参照，行业同类实践给出的量化结果是指标开发类工作由 6 至 8 小时压缩到 5 至 10 分钟、代码规范合规率提升至 98%——**该组数字为外部参照，不构成本项目的承诺值**，本项目的效益一律按 8.1 的本项目口径度量。

**服务可规模化效益**。"业务方在平台内直接提需求、智能体承担需求到代码的翻译"这一机制（见 1.3），使数据代开发服务的边际人力投入不再随指标数线性增长：人的角色从"编写"转为"确认与把关"，服务得以按指标计量、按周期续费。同时，需求文档、数仓设计、程序与调度任务四份产物同名同源且都在平台内可检索，交付与交接不依赖个人记忆——**这决定了代开发与代运维能否长期维持，而不只是一次性项目**。详见 1.6。

**数据质量效益**。规范开发环境把参数声明与口径约束前置，编译与 SQL 校验在开发阶段拦截语法与结构问题，减少因口径误读或结构错误引发的数据污染，把修复成本从下游回洗前移到编码当下。

**资产沉淀效益**。库表描述、指标口径、血缘与任务依赖沉淀在平台侧，成为可复用的组织资产，同时构成智能体的上下文供给层，形成"信息越规范、智能体越准确、开发越快"的正向循环。

### 8.1 效益指标与度量基线

为避免效益停留在定性描述，本节把各项效益落到本平台**当前可核查的基线**上。表中"当前值"取自第九章附录与已落地能力，可直接复核；"目标口径"尽量取机制性约束——机制成立的即为必然结果，不做估算性承诺。

| 效益维度 | 本项目基线（当前值） | 目标口径 / 判断方式 | 度量方式 |
| --- | --- | --- | --- |
| 智能体上下文可用性 | 5 类信息均有承载组件；元数据代理接口已落地，业务能力以 6 个工具组注册给智能体，通过平台接口取上下文 | 智能体取业务上下文一律走平台接口，不再依赖会话内临时粘贴 | 智能体工具调用中"平台接口类"调用的占比（桌面端 AI 助手会话日志 + 服务端接口日志） |
| 指标开发效率 | 一键上线调度已具备：编译、参数声明、提交与依赖编排收敛为一次操作；运行程序前强制弹出参数确认窗口 | 单指标从需求到上线的人工介入环节收敛为「确认参数 → 提交调度」两步 | 调度系统任务实例时间戳（首次提交 → 上线成功的耗时） |
| 服务可承接性 | 需求文档 / 数仓设计 / 分层 DDL / 程序 / 调度任务五类产物同名同源，且均在平台内可检索；指标口径、血缘与任务依赖可查（见 3.3） | 任一指标可在不询问原开发者的前提下，仅凭平台内信息还原其口径与产出链路——代开发与代运维的交接不依赖个人记忆 | 抽样已交付指标，由非原开发者仅凭平台信息还原口径与上游链路的成功率 |
| 代码规范合规 | 代码头以 @程序参数 / @资源参数 / @任务参数 三个字段声明业务入参、资源诉求与引擎侧参数，提交调度时取值落地到任务节点；编译与 SQL 校验位于提交链路上 | 经平台提交调度的程序均以编译产物或校验通过的 SQL 为输入；指标口径描述不含"相关""大概"等模糊表述 | 校验拦截次数与放行数；指标口径描述的模糊词检查结果 |
| 数据质量修复成本 | 语法与结构类问题在编译 / SQL 校验阶段被拦截，修复发生在编码当下而非下游回洗 | 该类问题不流入下游生产（下游回洗次数趋近于 0，属机制约束而非估算） | 开发阶段拦截数 与 生产环境故障登记数 的对比 |
| 回归质量基线 | 59 个测试文件、1001 个测试用例；关键安全闸门（删除与回滚的安全评估、回收站保留策略、凭据信封）有纯函数单测覆盖；前端与主进程通过静态类型检查 | 每次交付保持全量通过（并发执行时的偶发超时须单独复跑确认后方可放行）；新增纯函数分支覆盖 100% | 回归测试报告（通过数 / 用例数）与静态类型检查结果 |
| 平台承载规模 | 桌面端 336 个 TS / TSX / CSS 文件、约 7.99 万行代码；服务端 6 个业务模块、20 个控制器、28 张表、13 种数据源类型 | 本期不以规模增长为目标，以"已落地能力全部可验收"为目标 | 第九章附录基线与验收报告逐项比对 |
| 资产沉淀 | Marquez 血缘与 DolphinScheduler 任务依赖已集成，表级与字段级血缘可在平台内查询 | 血缘覆盖率（有血缘声明的表 / 关键表总数）与任务依赖完整率可统计 | Marquez 血缘节点数；调度系统工作流与任务数 |

> **口径说明**：本表不使用估算值。正文提到的"指标开发 6—8 小时压缩至 5—10 分钟""规范合规率 98%"来自行业同类实践的公开结果，属**外部参照**，只用于说明该方向的行业上限；本项目的实际收益以本表口径度量。
