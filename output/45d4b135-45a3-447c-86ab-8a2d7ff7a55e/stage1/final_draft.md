# DataForge 数据开发平台项目计划书

## 一、项目概述

### 1.1 项目背景

过去十余年，企业数据团队的作业模式并未发生本质变化：手动搭建数据管道、逐行编写 ETL 逻辑、人工排查任务异常、在多个系统之间反复切换。行业调研数据显示，一个 10 至 15 人的中型数据团队，约六到七成的工时被消耗在配置同步任务、编写标准 SQL、排查数据质量、维护元数据文档等重复性操作上，真正投入数据建模、业务分析与架构设计的精力不足三成。

2025 年以来，大语言模型从"代码生成器"进化为"意图理解与任务执行体"，数据研发的核心命题从"代码写不完"转向"AI 生成的代码是否正确"。但这个命题背后有一个更深层的前提常被忽略：**智能体要正确理解业务数据，靠的既不是更大的模型，也不是更巧的提示词，而是企业能否为它提供规范、无歧义、可检索的信息**——一张表是什么、一个指标怎么算、数据从哪来到哪去、由哪个任务在何时产出。缺少这些信息，智能体就只能"看似会写 SQL，实则猜口径"，产出越大、错得越快。

本项目组的落点正在于此：不做一个"更会写代码的工具"，而是把"让智能体正确理解业务数据"所需的**规范开发环境**与**四类基础信息**系统性地补齐，让 AI 的能力建立在有据可依的底座之上。

### 1.2 项目定位

DataForge 是面向数据开发的一体化平台，核心目标是**让智能体正确理解业务数据**。平台由四大核心组件构成：

| 组件 | 形态 | 提供的关键能力 | 在"智能体理解业务数据"中的角色 |
| --- | --- | --- | --- |
| dataforge | 桌面应用 | 规范开发环境：代码头参数声明、编译校验、命名与口径约束 | 从源头保证开发产生的信息规范且前后相互关联 |
| dataforge-server | 平台服务 | 库表描述信息、数据指标描述信息、统一身份与权限 | 回答"表/字段是什么、指标口径是什么" |
| Marquez | 开源系统（集成） | 数据血缘信息（OpenLineage） | 回答"数据从哪来、流向哪、影响谁" |
| DolphinScheduler | 开源系统（集成） | 任务依赖信息（工作流 / DAG / 调度） | 回答"数据由什么任务、在何时产出" |


四大核心组件共同回答同一个问题——**如何让智能体正确理解业务数据**：dataforge 构建规范开发环境，保证源头信息规范且前后关联；dataforge-server 提供库表与指标描述，回答"是什么"；Marquez 提供血缘，回答"从哪来、到哪去"；DolphinScheduler 提供任务依赖，回答"何时、依赖什么产出"。

> **强调**：本项目所有程序可在企业内部免费使用（代码不开源）；公司主要收益来源为数据开发与集群运维服务。

### 1.3 建设目标

总体目标：建成"规范开发环境 + 四类基础信息"的数据开发平台，使智能体能够正确理解业务数据，把"AI 生成的代码是否正确"从风险变成可验证的常态。具体目标分为六个方面：

1. **规范开发环境目标**：由 dataforge 桌面端把数据开发收敛到一个受约束的入口——代码头参数声明、编译与 SQL 校验、命名与口径约束，确保开发产生的信息规范且前后相互关联。
2. **信息底座目标**：由 dataforge-server 沉淀库表描述信息与数据指标描述信息，作为智能体理解"数据是什么"的权威口径来源。
3. **血缘与依赖目标**：集成 Marquez 获取数据血缘信息、集成 DolphinScheduler 获取任务依赖信息，让数据"从哪来、何时产出、影响谁"可追溯。
4. **智能体上下文闭环目标**：将上述规范环境与四类信息汇聚为智能体的上下文供给层，使其在生成代码前即可调用准确的业务上下文，而非凭空推断。
5. **自动化运维目标**：为 SQL / Scala / Java 三类程序提供**一键上线调度**（已具备）——把编译、参数声明、提交与依赖编排收敛为一次操作；并推进**自动化问题排障**（功能规划中），基于集群部署信息与任务依赖关系，在任务失败时自动定位到受影响的上游任务或资源瓶颈。
6. **数据价值评估目标（功能规划中）**：整理数据资产清单及其处理所消耗的计算资源，结合数据使用情况（访问频次、下游引用等），评估数据的使用价值，识别高价值资产与长期闲置的低效资产，为资源优化与治理决策提供依据。

### 1.4 建设范围与边界

**本期建设范围**：

- dataforge 桌面端全功能客户端（规范开发环境：AI 助手、代码编辑与语言服务、编译与 SQL 校验、程序参数声明、调度提交）。
- dataforge-server 平台服务（库表描述、字段描述、指标描述、统一身份与多级权限、知识库、数据源与存储、审计）。
- Marquez 与 DolphinScheduler 的集成（血缘信息采集与图谱展示、工作流定义与任务依赖管理、运行实例监控）。

**明确不包含在本期范围**：

- 不替代底层存储与计算引擎本身（Hive / Spark / Flink / Doris / ClickHouse 由既有集群提供）。
- 不自研元数据存储引擎与血缘采集引擎，而是集成 Marquez / OpenLineage 与既有元数据体系。
- 不承担数据模型设计与数仓分层建模的方法论落地，平台只提供承载与校验能力。

### 1.5 产品与商业模式

本项目所有程序（dataforge 桌面端、dataforge-server 及配套组件）**可在企业内部免费使用**，软件**代码不开源**，以闭源形式提供。

## 二、需求分析

### 2.1 用户角色与典型场景

平台按角色收敛权限（服务端初始化脚本预置 1 个超级管理员角色，其余角色按需创建）。典型使用场景如下：

| 角色 | 典型场景 | 核心诉求 |
| --- | --- | --- |
| 数据开发工程师 | 在规范环境中编写程序，借助 AI 助手生成与纠错代码，编排工作流并提交调度 | 环境规范、上下文完整、提交一步到位 |
| 数据分析人员 | 浏览库表与指标口径，编写即席查询并可视化，查看字段血缘与任务依赖 | 找数快、口径准、来龙去脉可追溯 |
| 运维 / 平台管理员 | 管理用户角色租户、配置数据源与外部系统连接、查看审计日志 | 权限边界清晰、配置集中、操作留痕 |
| 数据平台负责人 | 掌握任务运行状态、数据资产分布、平台使用情况 | 全局可视、问题可定位 |

### 2.2 功能需求

#### 1. 规范开发环境（dataforge）

- **AI 开发助手**：支持多模型切换、工具调用（命令执行 / 文件编辑 / 网络检索 / 任务 / Skill 等）、沙箱执行、权限审批与交互式问答；支持会话切换与任务历史回溯；支持不同任务类型的角色化系统指令。
- **代码编辑与智能提示**：提供专业 IDE 级编辑体验，包含文本语法高亮、主题、快捷键；通过语言服务器协议桥接 Java 与 Scala 语言服务，提供悬停提示、定义跳转（含依赖源码）、补全、诊断。
- **编译与校验**：本地提供 Java / Scala 的 Maven 编译服务与 SQL 语法校验能力，供 AI 助手与编辑器调用；编译前自动生成 Maven 工程配置。
- **程序参数声明与提交调度**：程序文件头部以结构化字段声明程序参数、资源参数与任务参数；运行前必须确认参数；提交调度时把声明参数落地到调度任务节点，支持文件夹级批量提交与环境标识（默认 test）。
- **文件与版本管理**：工作区文件浏览与多选操作；Git 仓库自动同步；文件历史与回滚；删除走回收站机制，并按保留期与容量上限自动清理。

#### 2. 信息底座（dataforge-server）

- **库表与字段描述**：库表元数据浏览、字段明细、元数据同步，沉淀"表/字段是什么"的权威描述。
- **数据指标描述**：指标体系维护（指标定义与计算口径），支持跳转血缘查看关联字段。
- **统一认证与授权**：无状态令牌认证、登录登出、当前用户信息获取；基于角色与租户的权限控制，权限可到行级与列级；操作审计日志。
- **数据源与存储管理**：数据源配置的增删改查、连接测试（Kyuubi / Doris / ClickHouse / MySQL 等）；存储配置与分布式文件浏览（HDFS / JuiceFS / S3 / 本地）。
- **知识管理**：企业知识文档的分类、检索与维护，作为智能体上下文来源之一。

#### 3. 血缘与任务依赖（Marquez / DolphinScheduler）

- **数据血缘**：通过 OpenLineage 采集血缘信息，图谱化展示表级与字段级血缘，支持影响分析与溯源。
- **任务依赖**：管理工作流定义（含 DAG 画布）、任务配置、调度配置、任务实例与运行实例，呈现数据"何时、依赖什么产出"。

#### 4. 运维与治理类能力（规划中）

前 3 类需求构成"让智能体正确理解业务数据"的基础，本期优先交付；以下 3 项决定平台在业务侧能否长期被用起来，列入规划并各自给出就绪判据：

- **自动化问题排障**：任务失败时，依据集群部署信息与任务依赖关系自动定位到受影响的上游任务或资源瓶颈，输出根因候选与影响范围。就绪判据：对给定失败实例，能给出至少一条可验证的根因线索（上游任务未产出 / 资源不足 / 配置错误），且在平台内可追溯到对应任务节点。
- **知识检索增强**：把知识库检索从当前的关键字匹配（标题与正文的模糊匹配）升级为向量检索，提升智能体生成代码前检索业务知识的命中率。就绪判据：同一组业务问题上，向量检索的相关文档命中率高于关键字检索；检索接口与现有知识库接口兼容，智能体侧工具签名无需变更。
- **数据价值评估**：以数据资产清单、其处理所消耗的计算资源、以及使用情况（访问频次、下游引用）三个输入评估数据使用价值，识别高价值资产与长期闲置的低效资产。就绪判据：可输出资产级价值排序，且"资源消耗"与"使用情况"两项输入均有可核查来源。

> **说明**：以上 3 项为规划中能力，不纳入本期功能验收；其需求条目、对应模块与就绪判据的对应关系见 8.5。

## 三、总体架构

### 3.1 架构总览

平台由四大核心组件（dataforge、dataforge-server、Marquez、DolphinScheduler）构成，组件之间边界清晰：桌面端承载交互与本地计算，服务端承载信息底座，Marquez 与 DolphinScheduler 承载血缘与任务依赖。

| 组件 | 承载能力 | 对智能体理解业务数据的贡献 |
| --- | --- | --- |
| dataforge（桌面端） | 规范开发环境：编辑器、语言服务、编译校验、代码头参数声明、AI 助手运行时（沙箱） | 保证开发产生的信息规范且前后相互关联 |
| dataforge-server | 库表描述、字段描述、指标描述、统一身份与多级权限、数据源与存储、审计 | 提供"表/字段是什么、指标口径是什么" |
| Marquez | 数据血缘信息（OpenLineage 采集与图谱展示） | 提供"数据从哪来、流向哪、影响谁" |
| DolphinScheduler | 任务依赖信息（工作流 / DAG / 调度 / 实例） | 提供"数据由什么任务、在何时产出" |

### 3.2 核心设计：智能体理解业务数据的五类信息

本平台把"让智能体正确理解业务数据"作为第一设计原则。智能体在生成或修改数据代码前，需要五类输入才能做到不凭空推断：

| 信息 | 来源组件 | 回答的问题 |
| --- | --- | --- |
| 规范开发环境 | dataforge | 代码结构、参数声明、命名与口径是否规范、是否前后关联 |
| 库表描述信息 | dataforge-server | 表与字段是什么、业务含义与约束 |
| 数据指标描述信息 | dataforge-server | 指标的计算口径与数据来源 |
| 数据血缘信息 | Marquez | 数据从哪来、流向哪、影响谁 |
| 任务依赖信息 | DolphinScheduler | 数据由什么任务、在何时、依赖什么产出 |

这五类信息共同构成智能体的上下文供给层：规范开发环境决定信息**源头是否规范、前后是否关联**，库表与指标描述决定**语义是否权威**，血缘与任务依赖决定**来龙去脉是否可追溯**。平台的建设顺序与优先级，均以"这五类信息是否就绪"为依据。

### 3.3 关键技术设计决策

**决策一：信息底座先行。**

智能体能力的上限不由模型决定，而由它能否读到规范、无歧义的业务信息决定。因此平台的投入优先级是先建规范开发环境与四类信息底座，再逐步扩展运维与治理类能力。

**决策二：从源头约束，而不是事后清洗。**

库表描述、指标口径这些信息若靠事后人工补录，必然残缺且滞后。平台在开发环境侧就通过代码头参数声明、编译校验、命名与口径约束，让"规范"发生在信息产生的时刻，而不是在信息流转之后的补救阶段。同步地，代码头参数声明把程序入参与调度任务的参数显式对齐，使开发阶段产生的信息与上下游环节可以直接衔接——规范解决的是同一件事有没有唯一说法，关联解决的是这件事与上下游能否对上。

**决策三：血缘与任务依赖直接集成成熟开源系统，不自研。**

数据血缘与任务调度是通用基础设施，Marquez（OpenLineage）与 DolphinScheduler 生态成熟。平台以集成代替自研，把工程投入集中在"如何把这些信息汇聚成智能体可用的上下文"这一差异化能力上。

**决策四：AI 助手以内置运行时 + 沙箱方式提供，而非云端调用。**

AI 助手需要执行命令、读写工作区文件、调用本地编译服务，这些能力要求它运行在用户本机且受控。因此助手以本地进程形式由客户端托管，固定监听本机端口，并在 macOS 与 Linux 上以系统级沙箱包装执行。

## 四、组件设计

### 4.1 DataForge 桌面端（规范开发环境）

**技术形态**：基于 Electron 44 的跨平台桌面应用，渲染层采用 React 19 + Vite 8 + TypeScript 7。当前工程规模为 336 个 TypeScript / TSX / CSS 文件、约 7.99 万行代码。

**主进程能力**：

| 模块 | 职责 |
| --- | --- |
| AI 助手运行时管理 | 启动、监督、终止本地助手进程，固定监听本机端口；macOS 以系统沙箱、Linux 以容器沙箱包装；退出时优雅清理进程与数据库锁文件 |
| 编译服务 | 本地编译 HTTP 服务，随机端口 + 令牌鉴权，端点通过环境变量注入 AI 助手进程 |
| 语言服务桥 | 把 Java / Scala 语言服务器的标准输入输出流转换为 WebSocket，供前端语言客户端使用 |
| 工程生成与编译 | Maven 工程生成与 Java / Scala 编译、本地运行 |
| 配置与凭据存储 | 应用配置与安全凭据的分层存储，敏感项不落前端可读位置 |
| 平台适配 | 三平台路径、二进制命名与沙箱策略的差异化处理 |

**规范开发环境的关键机制**：

- **代码头参数三段式**：程序文件头部以结构化字段声明程序参数（业务入参）、资源参数（资源诉求）、任务参数（提交与引擎侧参数），取值为真实值。它有统一消费面：运行程序时取参数名预填，提交调度时取真实值写入调度任务节点。
- **运行程序必须确认参数**：任何程序运行前弹出参数确认窗口，参数以键值对逐行编辑，语义为"所见即所发"。
- **编译与 SQL 校验前置**：提交前必经本地编译与 SQL 校验，把语法与结构问题拦截在开发阶段。
- **删除与回滚安全闸门**：所有删除与回滚操作先经过纯函数化的安全评估，快照根节点为空一律中止；删除走回收站目录并生成清单，且回收站目录对版本控制隐身。
- **沙箱化执行**：AI 助手的命令执行默认运行在系统沙箱内。

渲染层功能模块包括：开发助手、编辑器、AI 面板、数据探索、指标管理、知识库、文件浏览器、调度管理、数据血缘、系统管理、设置。

### 4.2 dataforge-server（库表描述 + 指标描述）

**技术形态**：基于 SpringBoot 3.2.1 + Java 17 的单体服务，采用"通用层 + 业务模块层"分层结构，共 6 个业务模块、20 个控制器、28 张表。

| 层次 | 内容 |
| --- | --- |
| 技术底座 | Spring Security 6 + JWT（jjwt 0.12.3）、MyBatis-Plus 3.5.5、MySQL / PostgreSQL / MariaDB / H2、Knife4j 4.4.0（OpenAPI 3）、Hutool 5.8.24 |
| 元数据模块 | 库表与字段元数据、元数据同步、元数据代理（供智能体使用）、指标与指标字段 |
| 系统管理模块 | 认证登录与令牌、用户、角色、权限与菜单权限、租户、项目权限、操作审计日志 |
| 运维管理模块 | 数据源配置、存储配置、分布式文件浏览、执行引擎管理 |
| 数据开发模块 | 开发工程、程序参数、代码执行（多引擎策略，含执行结果 / 日志 / 取消 / 校验）、Jar 依赖管理 |
| 知识库模块 | 企业知识文档管理 |
| 数据质量模块 | 数据质量校验结果管理 |

**对智能体理解业务数据的贡献**：通过元数据同步沉淀库表与字段描述，通过指标体系沉淀指标口径，通过元数据代理接口（`/metadata/agent`）把这些信息以结构化方式提供给智能体，回答"表/字段是什么、指标怎么算"。

**权限模型**：支持到行级与列级（`sys_table_permission_row` / `sys_table_permission_column`），文件权限按路径 + 存储配置维度控制。

### 4.3 Marquez（数据血缘）

Marquez 是开源的元数据与血缘服务，本平台通过 OpenLineage 标准采集作业级与数据集级血缘事件，并由桌面端的血缘视图图谱化展示。

| 能力 | 说明 |
| --- | --- |
| 血缘采集 | 通过 OpenLineage 传输端点采集作业运行时的输入 / 输出数据集事件 |
| 血缘展示 | 桌面端基于图可视化组件呈现表级与字段级血缘关系 |
| 影响分析与溯源 | 上游变更时识别受影响的下游表，指标异常时沿血缘上溯定位来源 |

**对智能体理解业务数据的贡献**：血缘信息回答"数据从哪来、流向哪、影响谁"，是智能体判断"改动这张表会影响什么""这个指标的数据源头在哪"的依据。

### 4.4 DolphinScheduler（任务依赖）

DolphinScheduler 是开源的工作流调度系统，本平台集成其项目管理、工作流定义、任务编排与实例监控能力，并把开发环境声明的参数落地为任务节点参数。

| 能力 | 说明 |
| --- | --- |
| 工作流定义 | 桌面端提供工作流定义编辑器与 DAG 画布，可视化编排任务依赖 |
| 任务配置 | 任务节点配置（程序参数、资源参数、任务参数、环境标识） |
| 调度与实例 | 调度配置、任务实例与运行实例监控 |

**对智能体理解业务数据的贡献**：任务依赖信息回答"数据由什么任务、在何时、依赖什么产出"，是智能体判断数据时效性与下游可用性的依据。

## 七、风险识别与应对

本章风险按四类归集：信息类（R1 描述不完整、R2 关联信息不全）、权限与安全类（R4 权限边界、R6 凭据）、操作类（R3 AI 产出、R5 删除回滚）、依赖类（R7 上游变更）。每条都写明**触发场景**——什么情况下会发生、当前实现里对应什么具体行为，以及影响与手段，避免只给结论。"应对措施"一列区分已落地与待补，待补项即尚未闭合的缺口。

| 编号 | 风险场景与触发条件 | 影响 | 应对措施（已落地｜待补） |
| --- | --- | --- | --- |
| R1 | 库表与指标描述不完整、不新鲜。典型触发：建表未写表 / 字段注释；同一指标的口径在多处文档中写法不一致；DDL 变更后元数据同步失败——服务端在 DDL 执行后触发同步，失败只记警告日志、不阻断执行，于是表结构已经变了、平台上的描述还是旧的 | 智能体按旧描述生成代码，口径错误被放大；字段说明缺失时只能靠列名猜语义 | 已落地：开发环境强制代码头参数声明与口径约束；DDL 执行后自动触发元数据同步；库表与指标描述可检索、按权限浏览。待补：同步失败升级为可观测告警（当前仅落日志）；提供"未标注表 / 字段"清单，让缺失可见 |
| R2 | 血缘与任务依赖覆盖不全。三种具体缺口：① 血缘事件要求"已配置 OpenLineage 传输地址（桌面端设置项，或程序里声明的 lineage.transportUrl）且作业经平台提交到 Spark 执行"，未配置、或在集群上手工执行、或走 Kyuubi / Hive 直连的作业都不产生血缘；② 血缘视图由桌面端直连 Marquez 读取，Marquez 地址不可达时视图不可用；③ 任务依赖信息来自 DolphinScheduler，只覆盖经平台提交的工作流，其他调度方式与人工产出没有依赖信息 | 影响分析与溯源在缺口处断链：智能体无法判断"改这张表会影响谁""这个指标的数据源头在哪" | 已落地：提交 Spark 任务时由平台注入 OpenLineage 传输参数（服务端构建提交命令时会剔除业务侧自带的 openlineage / lineage 配置，避免被覆盖）；血缘按 OpenLineage 标准采集。待补：对"无血缘声明的表"做显式降级标注（当前表现为静默缺行）；补一张血缘与依赖覆盖率视图 |
| R3 | AI 生成的代码存在口径错误或危险操作。典型触发：误读指标口径导致算错口径；生成无分区条件的全表扫描或大范围 DELETE / TRUNCATE；把 test 环境的参数带到生产提交 | 错误写入被批量放大；误提交上线后影响生产数据 | 已落地：提交前强制编译与 SQL 校验；代码头参数声明 + 运行前参数确认窗口（所见即所发）；AI 助手默认沙箱运行、工具调用需审批。待补：对 DELETE / TRUNCATE / 无分区全表扫描类语句增加显式二次确认 |
| R4 | 权限边界不构成强隔离。四个已核实的情形：① **租户不是数据隔离边界**——租户与用户是 1:1 绑定（租户用户关联表对 tenant_id 与 user_id 都加了唯一约束），数据源、存储配置、开发项目、库表与文件权限表都没有租户字段，租户只影响角色绑定与审计日志，跨租户的资源可见性完全依赖授权时的人为约束；② **校验的失败路径是"放行"**——DML（INSERT / UPDATE / DELETE）权限检查在 SQL 解析失败时只打 debug 日志并放行执行；行 / 列权限的合并规则是"任一命中权限未对该表做限制即整体放宽"，多角色并集时宽权限会静默覆盖窄权限；③ **行 / 列级权限只覆盖部分执行路径，且是结果集返回后的后过滤**——仅 Kyuubi 与 JDBC（MySQL / PgSQL / Doris）路径生效，Spark / Flink / HBase 三条路径不做行过滤与脱敏，且聚合类查询（count / sum）的数值不受行级过滤影响；④ 超级管理员角色短路所有检查 | 越权读取与写入未被拦截；聚合口径泄露；跨租户资源越界 | 已落地：角色—资源三级授权（文件路径含递归、库表 CRUD 加行 / 列限制、项目读 / 编辑 / 删除）；检查集中在服务端接口层；数据源与租户口令 AES 加密存储；操作审计日志记录租户维度。待补：解析失败改为默认拒绝（fail-close）并告警；合并规则由"取并集放宽"改为"取交集收紧"；行 / 列权限补齐到 Spark / Flink / HBase 路径，或改为下发 SQL 前注入过滤条件；明确租户是否作为资源隔离维度并在产品说明中写清，避免把它误当隔离边界 |
| R5 | 删除与回滚造成不可恢复的丢失。典型触发：回滚时取到的版本快照为空，若按空快照反推"待删除集合"，会把全部现存文件纳入删除范围；回收站被人工清理或超期自动清理后无法恢复 | 工作区代码或文件丢失，需从 Git 或其他备份重建 | 已落地：所有删除与回滚先经安全评估纯函数（空快照一律中止）；删除走回收站（带清单文件）而非直接删除；回收站对 Git 隐身，避免被自动同步覆盖；评估与保留策略均有单元测试覆盖；**回收站保留期与容量上限**——默认保留 30 天 / 50 个批次 / 2 GiB，最新 2 个批次永不清理，名字解析不出批次时间的目录一律不碰；清理在写入后延迟合并执行（一次回滚连续移入上百个文件只统计一次），删除目标必须是回收站目录的直接子项，越界即拦截；单个批次删不掉只记日志，不影响删除主流程。回收站定位是误删缓冲而非备份，超期清理后的版本保障由 Git 承担 |
| R6 | 敏感凭据泄露。磁盘这条路径已闭合：凭据经系统钥匙串加密后落盘，文件被拷贝、随云盘同步、被备份带走的都只是密文。残留触发面：① 密钥在设置页需明文回填以供编辑，截图、录屏、投屏可带走；② 系统钥匙串不可用的环境（如未装 libsecret 的 Linux 容器）会降级为明文落盘，只告警不阻断；③ 换机器或钥匙串被重置后，原加密凭据解不开，会静默变成"未配置" | 大模型密钥、调度令牌、数据源口令泄露 | 已落地：不在渲染层持久化令牌密钥；凭据统一落主进程受控目录；数据源与租户口令在服务端 AES 加密存储；非本机后端地址强制加密传输；**凭据落盘加密**——df-stores 的敏感字段（apiKey / token / password / secret / credential）在主进程读写咽喉处经系统钥匙串（macOS Keychain、Windows DPAPI、Linux libsecret / kwallet）加密，落盘为自描述信封而非明文，旧明文文件读时原样兼容、下次写入自动升级；钥匙串可用但加密失败时置空（fail-close），绝不明文回写；**导出剥离**——"导出诊断配置"在主进程侧把凭据字段替换为 `***` 后返回，明文凭据不经过渲染层。待补：截图与录屏等人工旁路无自动化兜底（密钥需在设置页明文回填以供编辑） |
| R7 | 上游依赖变更导致功能不可用。涉及 Marquez（OpenLineage API）、DolphinScheduler（工作流与实例接口）、Kyuubi / JDBC 驱动与各集群版本、语言服务（JDT.LS / Metals）版本。**血缘与调度是桌面端直连上游、不经服务端中转**，上游地址、版本或鉴权方式变化会直接表现为客户端功能异常 | 血缘视图、提交调度、语言服务能力不可用 | 已落地：上游地址与令牌集中在客户端设置项并支持连接测试；跨版本适配按目标版本矩阵逐版本验证。待补：把上游接口变更纳入发布前兼容性清单；明确上游不可达时的降级提示文案 |

## 八、验收标准与质量保障

### 8.1 交付物清单

- 桌面端应用的三平台安装包与升级包。
- 平台服务端的容器镜像（多架构）与编排文件、初始化脚本、启停与清理脚本、端到端自检脚本。
- 用户手册、部署手册、验收测试报告。

### 8.2 功能验收

- 桌面端在 macOS / Windows / Linux 三平台可安装启动，核心链路（登录、开发、编译、参数声明、提交调度、数据探索、血缘查看）可用。
- 平台服务端全部已声明接口通过联调与自检脚本验证，权限控制按角色生效，库表描述与指标口径可检索。
- 血缘与任务依赖在平台内可查询：表的字段血缘与任务依赖关系完整展示。
- 规划中能力（自动化问题排障、知识检索增强、数据价值评估）不纳入本期功能验收，按 2.2 第 4 条的就绪判据逐项判定，对应关系见 8.5。

### 8.3 质量保障

| 维度 | 标准 |
| --- | --- |
| 单元测试 | 桌面端依赖自动化测试框架覆盖核心逻辑；纯函数必须有分支覆盖，测试全量通过作为回归基线 |
| 类型检查 | 前端与主进程代码通过静态类型检查，无类型错误 |
| 兼容性 | 交付前在目标平台与依赖版本矩阵上逐版本执行最小用例 |
| 专项验证 | 涉及安全闸门、参数语义、权限判定的改动必须配套自动化测试 |
| 性能 | 建立性能基线并保留对比数据；关键路径有可量化的优化前后对比 |

由项目负责人组织，交付方提供测试报告、兼容性验证记录与部署手册；验收方按功能清单逐项验证。

## 九、预期效益

**智能体正确理解业务数据**。这是本平台的首要效益：把散落在代码、文档、口头经验中的业务信息，收敛为规范无歧义的库表描述、指标描述、血缘与任务依赖，让智能体在生成代码前就能读到权威上下文，从根上降低"AI 生成代码是否正确"的不确定性。

**开发效率效益**。规范开发环境把数据开发收敛到一个受约束的入口，消除跨工具切换与手工配置的重复劳动；一键上线调度进一步把编译、参数声明、提交与依赖编排收敛为一次操作。作为方向参照，行业同类实践给出的量化结果是指标开发类工作由 6 至 8 小时压缩到 5 至 10 分钟、代码规范合规率提升至 98%——**该组数字为外部参照，不构成本项目的承诺值**，本项目的效益一律按 9.1 的本项目口径度量。

**数据质量效益**。规范开发环境把参数声明与口径约束前置，编译与 SQL 校验在开发阶段拦截语法与结构问题，减少因口径误读或结构错误引发的数据污染，把修复成本从下游回洗前移到编码当下。

**资产沉淀效益**。库表描述、指标口径、血缘与任务依赖沉淀在平台侧，成为可复用的组织资产，同时构成智能体的上下文供给层，形成"信息越规范、智能体越准确、开发越快"的正向循环。

### 9.1 效益指标与度量基线

为避免效益停留在定性描述，本节把各项效益落到本平台**当前可核查的基线**上。表中"当前值"取自第十章附录与已落地能力，可直接复核；"目标口径"尽量取机制性约束——机制成立的即为必然结果，不做估算性承诺。
