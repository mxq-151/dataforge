结论先行

这两个模块都不是从零新增的能力，而是补齐平台既有契约的两端——这一判断直接改变了工作量结构与实现优先级。

数据质量：规则的「契约」已经完整写在智能体提示词里（opencodeInstructions.ts 定义 7 类规则类型、S1/S2/S3 三阶段分工、DQC 质量层、dqc_ 前缀、以及「校验输出须可定位：规则名/校验对象/阈值/实际值/是否通过」）；结果的「落点」也已经存在（data_quality_check_result 表 + 写入接口）。缺的是中间的规则定义、执行计划与消费界面。所以它是「把文档约定升级为平台能力」，不是「新建一个治理平台」。

资产目录：分类体系天然存在于命名规范（{分层}_{业务域}_{实体描述}_{刷新周期}），资产属性也已有大量存量（生命周期、存储量、血缘、行/列权限、关联指标）。所以它不需要新建一套人工维护的分类元数据，而是「规范驱动的资产目录」——这正是 DataForge 区别于 DataWorks 的地方。

定位表述建议：数据质量是第 6 类智能体上下文（数据该满足什么约束）；资产目录不产生新的上下文类别，它是「库表描述 + 指标描述 + 血缘 + 任务依赖」四类的聚合消费面，是「人」侧的元数据调研入口，与智能体侧的元数据代理接口 /metadata/agent 对位。

工作量概览：桌面端 12 处改动（其中 2 个 key 必须同批改，否则入口不可见）；服务端新增 15 张表、改造 3 张表、约 46 个接口，分三批次交付；集成侧 3 项调度工作、1 项血缘复用。

一、评估前提与现状基线

1.1 核对方法与结论口径

本次评估不采信计划书的「已落地」标注作为唯一依据，而是对两端代码逐项核对：桌面端核对 ActivityBar 入口表、ActiveTab 与菜单码映射、App.tsx 视图挂载、各面板目录；服务端核对 modules/ 包结构、20 个控制器、sql/init 四方言建表脚本与 sql/testdata 种子数据。凡本方案给出的接口路径、表名、字段名，均为代码中实际存在的对象或明确标注为「新增」。

「差距」的判定口径为三项：DataWorks 有而本项目完全没有（新建）；DataWorks 有而本项目只完成一半（补齐，工作量显著更小）；DataWorks 有而本项目形态不同、不应照搬（改造或明确不做）。第三类是本方案的主要决策点。

1.2 三个改变方案性质的发现

发现一：质量规则的契约已经存在，而且写在提示词里

src/hooks/opencode/opencodeInstructions.ts 是三角色系统指令的唯一契约来源，其中与质量相关的约定已经相当完整：

契约现存内容平台侧状态
规则类型固定 7 类且三阶段同名词：主键唯一性、非空、值域、行数波动、行数环比、上下游对账、口径一致性；明令「禁止自造同义词」无枚举、无存储
S1 需求第 7 条：用业务语言说明需覆盖的规则类型与可接受偏差只落 markdown
S2 设计第 6 条：稽核规则清单，含规则名、所属表/字段、规则类型、阈值、处置方式只落 markdown
S3 开发校验任务与处理任务分离、单独成文件挂下游；输出须可定位；不通过时阻断下游或告警只落代码文件
分层归属DQC 质量层＝质量规则定义与稽核结果存储；表名前缀 dqc_；DDL 文件 dqc_ddl.sql无 DDL 模板

结论：契约完备、落点缺失。当前的断点是——智能体在设计阶段产出的「稽核规则清单」没有地方落库，在开发阶段写完的校验任务也没有地方回传结果与统一判定。数据质量模块的第一职责就是消除这个契约断裂，因此规则类型必须与提示词的 7 类一一对齐，不得自造（详见 2.2）。

发现二：质量结果的落点已经存在，是「半条链路」

服务端 modules/quality 模块共 7 个文件、671 行，提供实体 DataQualityCheckResult、CRUD 与失败统计；表 data_quality_check_result 字段为数据源/库/表/检查项/检查时间/检查记录数/未通过记录数/未通过明细。这张表的形态是「接收结果」而非「管理规则」——说明其设计初衷就是接收 S3 产出的校验任务上报的结果。已有通路：

  • POST /quality/check-result（写入）、GET /quality/check-result/list（分页，支持表与检查项过滤）、GET /quality/check-result/statistics/fail（按表+日期+检查项聚合失败数）。

同时「检查项」是自由文本 varchar(200)，没有与 7 类规则类型枚举绑定。因此精确的缺口是：有结果写入、无规则定义；有原始记录、无可执行计划；有接口、无界面。桌面端全仓库检索「数据质量」，只有提示词文件命中，没有任何质量相关的 UI。

发现三：资产目录的分类与属性，大半已经存在

「分层规范」与「表名命名规范」已经规定了 {分层}_{业务域}_{实体描述}_{刷新周期} 的强制格式与 ODS/DWD/DWS/ADS/DIM/DQC/TMP 七层枚举。这意味着资产目录的一级分类（分层）与二级分类（业务域）可以从表名解析得到，不需要像 DataWorks 那样由人工维护业务分类树。

资产属性侧的存量比预期更多。table_metadata 已有 row_count、size_bytes、hot_days/cold_days/keep_days（生命周期）、partition_columns、storage_format、location、last_modify_time、sync_time 与表/字段双结构指纹；column_metadata 已有 column_comment、is_partition、is_primary_key、nullable；指标表 indicators 已有 topic（主题域）、business_owner/tech_owner、visibility、code（指标编码唯一）、刷新周期字段，且 indicators_fields 建立了指标 → 数据源/库/表/字段的关联，可直接反查出「这张表产出哪些指标」。

由此得出一条设计原则：table_metadata 的资产属性改造应对齐 indicators 的既有字段命名与语义（business_owner / tech_owner / topic / visibility），而不是另发明一套。同平台内两套 owner 语义会在权限与责任判定上打架。

二、数据质量模块设计

2.1 实体模型与对标映射

DataWorks 数据质量由五个核心实体构成：规则模板（定义「如何检查」）→ 监控规则（模板的具体应用，含阈值与强弱）→ 质量监控（把一组规则与一个调度任务关联的执行计划）→ 运行实例 → 规则级校验结果，另加告警订阅与大盘。本方案的实体模型与之同构，但每个实体的落点按本项目形态改造。

DataWorks本项目落点差异
规则模板新增 dq_rule_template；内置模板＝提示词 7 类规则类型，自定义模板＝校验 SQL内置模板与提示词契约同源，不自造类型
监控规则新增 dq_rule，含表/字段、分区表达式、比较方式、期望值、橙红阈值、处置方式「强弱」沿用提示词术语「处置方式」，取值为阻断/告警
质量监控新增 dq_task + dq_task_rule_rel；触发方式＝调度触发/手动触发「关联调度节点」改为「关联工作流与节点」
运行实例新增 dq_run_instance，记录批次、触发来源、统计与调度实例号与 DolphinScheduler 工作流实例号对齐
规则结果新增 dq_rule_result；老表 data_quality_check_result 保留兼容把自由文本「检查项」收敛为规则类型枚举 + 规则名
告警订阅新增 dq_alert_log；渠道先做站内记录，后接 Webhook/邮件本项目无钉钉/飞书，第一期不铺渠道
校验执行复用 CodeExecutionController 的多引擎策略与数据源连接不新建计算引擎
大盘扩展已有 /quality/check-result/statistics/fail，新增覆盖率与趋势复用已有聚合逻辑

2.2 硬约束：规则类型必须与提示词契约同源

7 类规则类型已在提示词中定义为「全链路统一术语」，禁止自造同义词。因此规则模板库的内置部分必须就是这 7 类，且三处（提示词、前端枚举、服务端枚举）必须一致。为防漂移，建议把枚举抽为单一常量并在提示词中引用，配套一个单测断言三处枚举集合相等——这与项目既有的「契约唯一来源」原则一致。

规则类型校验对象结果形态
主键唯一性主键/唯一键字段组重复行数，阈值 0
非空关键字段空值或空串行数，阈值 0
值域枚举字段、数值字段越界行数或越界比例
行数波动表级相对历史基线的涨跌幅，橙/红双阈值
行数环比表级当期与上期的涨跌幅
上下游对账上下游两张表记录数或金额差额，容忍度可配
口径一致性同一指标的两处计算结果差值与偏差率

实现要点：行数波动与行数环比需要「历史基线」。基线应取自平台自身的规则结果历史（dq_rule_result 中该规则近 N 次的 actual_value），而不是每次都重新查引擎算基线——这既省算力，也让基线的定义可解释、可回看。这是与 DataWorks 一致的做法。

2.3 页面结构

一级入口「数据质量」，面板内六个页签，与 DataWorks 的模块划分对齐但做了收敛（第一期不做报告订阅）：

  • 质量大盘：规则覆盖率（已配置规则的表 / 有产出任务的核心表）、校验通过率趋势、TOP 质量问题表、问题责任人、强规则阻断次数。
  • 规则配置（按表）：左侧复用数据源/库/表树（与资产目录共用组件），右侧为该表的规则清单与新建入口。这是主入口，对齐 DataWorks 的「配置规则：按表」。
  • 规则模板：内置 7 类模板（只读，与提示词同源）+ 自定义 SQL 模板（可维护）。
  • 质检任务：规则集、触发方式、关联工作流与节点、处置方式、告警订阅。
  • 运行记录：运行实例列表 → 规则级结果详情（规则名、校验对象、阈值、实际值、状态、执行 SQL、异常明细）。这与提示词「校验输出须可定位」逐项对应。
  • 告警订阅：订阅项与发送记录。

跨模块联动沿用既有范式：规则配置页点表名 → 跳数据血缘；运行记录详情可跳调度实例；资产详情的「数据质量」页签反跳本模块规则列表（第 4.1 节的 onNavigate 模式已在指标管理中跑通）。

2.4 关键设计决策

编号决策理由
D1校验 SQL 复用 CodeExecutionController 多引擎策略下发，不新建计算引擎项目已支持 Kyuubi/Doris/ClickHouse 等引擎连接与执行，重复建设无收益
D2阻断下游采用「质检作为 DAG 节点」，不做「平台反向置调度节点失败」提示词的 S3 规范已要求「校验任务独立挂在处理任务下游」，节点非零退出即天然阻塞，实现更简单可靠
D3校验 SQL 下发前必须过 SqlPermissionRewriter 行/列权限改写否则质检成为绕过行/列权限通道——这是安全闸门，不是优化项
D4平台表为规则的唯一事实源；dqc 层结果表 DDL 由平台下发模板提示词已声明 DQC 层职责但无 DDL 模板，S2 各自造表会导致全仓不一致；类比「编译前自动生成 Maven 工程配置」的既有做法
D5结果表扩维度，「检查项」收敛为规则类型枚举 + 规则名，老表保留兼容自由文本无法与 7 类规则对齐，也无法做覆盖率达统计
D6新增第 7 个智能体工具组，把规则清单作为上下文供 AI 读取质量规则是第 6 类上下文；AI 生成代码前知道目标表的非空/唯一/枚举约束，可直接避免违反既定口径
D7S2 产出的「稽核规则清单」支持一键落库为规则草稿把设计文档与平台规则打通，避免人工二次录入；这是本项目相对 DataWorks 的差异化能力

三、数据资产目录模块设计

3.1 与既有模块的边界

这是本模块最容易做重的部分——平台已有数据探索（含库表浏览与表详情）、指标管理、数据血缘、系统管理（库表权限）。若不划清边界，会出现「四处各有一个表列表」的局面。

模块回答的问题入口形态
资产目录这表是什么、谁负责、能不能用、质量如何、影响谁找数认数（治理视角，含属性）
数据探索我要查数、我要写 SQL取数即席查询（写操作视角）
指标管理这个指标怎么算、口径是什么口径维护（不变）
数据血缘数据从哪来、流向哪图谱分析（不变）
系统管理谁能看哪些表、行/列约束怎么配权限配置（不变，资产详情只读展示）

三条落地规则：① 资产目录不重复做查询编辑器，需要查询时跳数据探索；② 不重复做血缘图，详情页的血缘页签复用现有 Marquez 客户端渲染，或直接跳数据血缘并带定位参数（已有 lineageJumpTarget 机制）；③ 库表树抽为共享组件，数据探索保留引擎视角，资产目录在此基础上叠加治理属性与规范视角。

定位表述（写文档时建议采用）：智能体通过元数据代理接口 /metadata/agent 完成「现状调研」；资产目录是同一份调研能力的人的入口。S1 与 S2 的系统指令都把「后端元数据服务」列为调研必经环节——业务需求方要能自己找数认数，才谈得上用业务语言提出准确需求。这使资产目录不是可选的治理装饰，而是「业务方提需求」这条主张的基础设施。

3.3 规范驱动的分类体系

命名规范已强制表名格式为 {分层}_{业务域}_{实体描述}_{刷新周期}，且「表名、库名一律使用小写字母与下划线」，分层前缀限定为 ods_/dwd_/dws_/ads_/dim_/dqc_（另有 tmp_ 与视图 v_），刷新周期后缀限定为统一枚举（d/h/w/m/y/r/f）。据此可以建立一条确定性解析链：

  1. 取首段匹配分层枚举 → 得到资产分层；
  2. 取末段匹配刷新周期枚举 → 得到刷新周期（不匹配则视为实体描述的一部分）；
  3. 剩余段的第二段 → 得到业务域；其余为实体描述；
  4. 解析失败的表（历史遗留、外部导入、视图）归入「未分类」，并自动成为一个治理项。

这样做的收益有三：分类树零维护成本；分类与代码里实际遵循的规范始终一致；命名不合规的表会被自动暴露出来，成为可治理的清单。同时保留人工覆盖能力——table_metadata 增加 category_code 后，人工设置的分类优先于解析结果。

3.4 页面结构

一级入口「资产目录」，采用左右分栏：

  • 左栏：顶部搜索框，下方视角切换（引擎视角 / 规范视角），再下方为目录树。
  • 右栏：选中节点即展示对应内容——选中数据源或分层展示概况，选中库或业务域展示表清单，选中表直接进入资产详情。
  • 资产详情：页头为表名、分层与业务域标签、负责人、收藏按钮与操作组（加入专辑、跳数据探索查询、刷新元数据）；左侧基础信息面板（生命周期、存储量、行数、最近更新、健康度、表说明）；右侧页签为概览、字段、分区、血缘、指标、产出任务、数据质量、使用记录、权限、使用说明。
  • 我的收藏与资产盘点作为左栏底部的次级入口。

4.2 耦合与升级兼容

约束一：第 2 项与第 1、4 项必须同批提交。菜单可见性按 MENU_CODE_MAP[tab.id] 取码后再与用户 menuTags 比对；若 ActiveTab 与 FIRST_LEVEL_TAB_IDS 里已有新 id 但映射表没有对应码，取值 undefined，新入口会被静默过滤掉，表现为「代码写了但入口不出现」。

约束二：新增一级菜单码会改变「拥有全部菜单」的兜底判定。FIRST_LEVEL_MENU_CODES 由 MENU_CODE_MAP 的值派生，因此码从 9 个变为 11 个后，凡是靠「menuTags 覆盖全部一级码」这条捷径获得全部菜单可见性的非超管角色，都会因缺少新码而失去该捷径，回落为按码过滤。超管不受影响（其 menuTags 直接取 FIRST_LEVEL_MENU_CODES）。

处理动作：升级前排查是否存在此类角色（sys_role_menu_permission 中授权数等于旧一级码总数的角色），若有则在迁移脚本中一并补授两个新菜单码；sys_menu_permission 需新增两条菜单记录。

约束三：菜单种子数据只在测试数据脚本里，生产初始化脚本没有。四方言的 sql/init 脚本只初始化 admin 用户与 SUPER_ADMIN 角色，菜单与角色授权只存在于 sql/testdata。因此新增菜单码的迁移必须自带菜单与授权种子，不能假设生产库里已有 sys_menu_permission 数据（详见 5.4）。

第三批告警订阅多渠道、按模板批量配置、试跑、报告订阅；数据专辑、资产盘点与治理健康项、向量检索评估依赖第一、二批稳定

建议的起步顺序：服务端第一批可与桌面端改动并行，桌面端先用占位面板打通入口（对应改动 1–7），待接口就绪再接真实数据。这样能最早暴露菜单权限与挂载链路的问题，而这类问题与业务逻辑无关，越晚发现越麻烦。

七、验收判据与不做的事

7.1 验收判据

每项均可核查，不设无法验证的指标。

对象判据
数据质量对一张已配置规则的表，手动触发后运行记录中可看到规则级结果，且「规则名、校验对象、阈值、实际值、是否通过」五项齐全
数据质量行数波动规则的基线与历史结果一致，可回溯到具体哪几次历史值参与了基线计算
数据质量处置方式为「阻断」的规则校验失败时，下游任务确实未执行；且该次失败可在质量与调度两侧互相定位
数据质量大盘能给出规则覆盖率与失败趋势，且覆盖率分母口径可解释（有产出任务的核心表）
数据质量内置规则模板的类型集合与提示词中的 7 类完全一致，无多无少
资产目录输入关键词一次请求返回表/字段/指标三类结果并分组展示
资产目录按规范视角浏览时，分层与业务域与表名解析结果一致；解析失败的表出现在「未分类」并计入治理项
资产目录表详情页聚合展示字段、分区、生命周期、存储量、负责人、质量规则数、产出任务、关联指标
资产目录无权限用户在目录树与检索结果中看不到越权表名与字段名（含字段级校验）
资产目录收藏后出现在我的收藏；热度上报后 T+1 可在详情页看到趋势
升级从旧版本升级后，存量角色的可见菜单不减少（只增不减）

7.2 明确不做的事

  • 不新建计算引擎与调度器：校验执行复用既有引擎策略，触发与阻断复用 DolphinScheduler。
  • 不做「平台反向置调度节点失败」：改用质检作为 DAG 节点的天然阻塞，第一期不引入反向写调度状态的能力。
  • 不重复做查询编辑器与血缘图：需要时跳数据探索与数据血缘。
  • 不做人工维护的业务分类树：分类由命名规范解析，人工仅做覆盖。
  • 不引入向量检索：与已规划的「知识检索增强」合并评估，避免两套嵌入设施。
  • 不做 AI 自动生成质量规则：第一期规则来自人工配置与架构师设计建议，AI 生成留待规则模型稳定后再评估。
  • 不做加权治理健康分：只做可核查的治理项计数，避免产生不可解释的分数。
  • 不做告警渠道的全量铺开：第一期先做站内订阅与发送记录，渠道对接看客户实际环境（本项目无钉钉/飞书依赖）。
