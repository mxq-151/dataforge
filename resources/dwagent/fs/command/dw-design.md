按「数仓开发」套件完成设计阶段。业务名称：`$ARGUMENTS`。

如果 `$ARGUMENTS` 为空，先在工作区 `docs/` 下查找唯一的 `*_开发需求.md`；找到多个就停下来问用户选哪个，不要猜。

## 执行顺序

1. **解析需求**：调用 `dw-extract-req {businessName}`。
   - 失败（W01/W02/W03）→ 停止，原样报告错误码与位置，不修补需求文档。
   - 成功 → 记录指标数量、场景、输出方式、数据时效。

2. **登记证据**：对需求第 4 章的源系统/业务对象、以及候选上游表，调用外部只读 `metadata_search`；必要时 `metadata_detail` 查字段。把真实命中整理成记录，调用 `dw-submit-meta`（每批 ≤20）。
   - 不命中就不登记；不命中对象一律不得进入设计。
   - 数据源名称以 metadata 返回为准，不自行起名。

3. **设计分层与表**：按主题域分组，每组 ≤8 张，派 `dw-modeler`（任务=table）。必须覆盖：
   - ODS 贴源、DWD 明细、DWS 汇总、ADS 应用、DIM 维度；
   - 每张表的粒度、主键、分区、存储、生命周期、更新方式（全量/增量/拉链）、可重跑；
   - 维度建模：事实表、维度表、退化维度、缓慢变化维（scd2 三字段）；
   - 宽表与汇总表边界：宽表放 DWD/DWS，ADS 只放面向场景的结果。
   - 设计依据不足时写入待确认，不虚构表。

4. **指标落地**：按主题域分组，每组 ≤10 条，派 `dw-modeler`（任务=metric）。
   - 指标名称逐字继承需求第 3 章；
   - 编码 `{项目编码}_NNNN`，全局唯一；
   - 字段来源必须绑定到真实 `库.表:字段`；
   - 数据源与证据一致；
   - 下钻维度写成 `维度名(库.表:字段→字段)`，需要归属/分摊的写进含义或表达式。

5. **稽核规则**：按表分组，每组 ≤20 条，派 `dw-modeler`（任务=quality）。
   - 规则类型只取 7 类；阈值写成 `比较符+数值`；
   - 每张表至少 1 条；有上下游关系的表至少 1 条上下游对账。

6. **全局校验**：调用 `dw-validate-design {}`。
   - 有 error → 按 `byUnit` 回退对应单元，修完重跑，直到 `blocking=0`。
   - 不要用「我认为已经修好」替代工具复跑。

7. **语义审查**：派 `dw-design-reviewer`，范围五类（自洽/指标唯一/聚合层级/维度可落地/可追溯），结论通过 `dw-submit-review {phase:"design"}` 提交。blocker 必须回退修正，且复核时沿用同一 finding id。

8. **定稿**：先 `dw-finalize-design {businessName, dryRun:true}`，再正式调用。
   - 合并冲突不得覆盖已有章节，交用户确认；
   - 成功后调用 `dw-trace-metric` 抽查 3–5 个需求指标，任一 W26 即视为未完成。

## 硬约束

- 主 agent 不整篇读需求文档；只读工具摘要。
- 子代理只见自己单元；不要把所有证据/所有表一次性塞给它。
- 不写 SQL 落地代码（本命令只到设计 + DDL）。
- 不虚构库/表/字段/引擎/质量规则类型。
- 不通读渲染后的设计文档来「检查」；形状与规则由工具校验。

## 交付

```
产物：docs/{业务}_数仓设计.md；ddls/{分层}_ddl.sql；.dw/trace.json
规模：N 张表 / M 个指标 / K 条规则
校验：A/B 0 error；C 类 open blocker 0；合并冲突 0
未关闭：finding-id（severity）… 或 无
待确认：需求第 9 章 + metadata 缺口（逐条）
```
