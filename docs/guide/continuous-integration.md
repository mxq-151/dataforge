# 持续集成

> [文档首页](../README.md) › 使用教程

持续集成把「代码写完」到「生产上线」收敛成一条可校验、可回溯的流水线：本地校验 → 提交测试环境 → 灰度验证 → 生产上线。整条链路的闸门由**代码头契约**与**环境后缀**两点控制，不依赖人工记忆流程。

## 一、链路总览

#### 1. 编码与自检

由智能体按「需求编写 → 数仓设计 → 数据开发」链路产出脚本与程序，文件开头必须书写合规代码头（见「代码管理」）。

#### 2. 提交前校验

SQL 走 `sql-validate` 语法校验，Java / Scala 走 Maven 编译；同时校验代码头合规性、`@依赖` 存在性与作业名一致性。任一不通过都无法提交。

#### 3. 提交测试环境

在「提交调度」中选择环境，默认即**测试**。提交后生成的工作流名称自动带 `_test` 后缀，与生产、灰度互不覆盖。

#### 4. 灰度验证

同一份代码改选**灰度**再次提交，得到独立的 `_gray` 工作流，用于小范围验证口径与性能。

#### 5. 生产上线

验证通过后提交**生产**（`_prod`），上线工作流并配置定时调度。生产是唯一允许注入数据血缘参数的环境。

## 二、提交前的校验项

| 校验项 | 校验内容 | 不通过时 |
| --- | --- | --- |
| **代码头合规** | 必须用块注释（`/* ... */`）写在文件最开头且连续；`@备注`/`@引擎`/`@依赖`/`@数据源` 必填，`@程序参数`/`@资源参数`/`@任务参数` 无值时写「无」 | 判定不符合规范并拦截提交 |
| **SQL 语法校验** | 调用 `sql-validate` 校验语法 | 返回语法错误，需修复后重新校验 |
| **Java / Scala 编译** | 自动生成 Maven 工程并执行 `mvn clean package -DskipTests`，产出 JAR | 编译失败则不产出 JAR，主 Jar 无法回填，提交按钮不可用 |
| **依赖存在性** | `@依赖` 按 `{调度项目}.{前置任务名称}` 解析，并跨工作流解析前置任务 | 不存在的前置依赖被识别并告警 |
| **作业名一致性** | 从程序中提取的作业名与文件名比对 | 报错并阻止提交 |

## 三、环境闸门：生产 / 灰度 / 测试

环境取值固定为 `prod`（生产）、`gray`（灰度）、`test`（测试），默认 **测试**，且每次打开提交弹窗都回到默认值（不做记忆，避免误提生产）。环境直接拼在工作流名称末尾：

**工作流名称 = 基础名 + 环境后缀**

```bash
olist_code_ods + test  →  olist_code_ods_test
olist_code_ods + gray  →  olist_code_ods_gray
olist_code_ods + prod  →  olist_code_ods_prod
```

- **同名即同一工作流** — 提交时按名称查重决定新建还是原地更新，因此同一环境重复提交是**更新**，不同环境各自独立、互不覆盖；
- **环境决定三件事** — 工作流名称后缀、是否注入数据血缘参数，以及作业读写哪一套环境库（见下节）；不改变提交目标项目与资源组；
- **血缘硬闸门** — 只有生产环境注入血缘（OpenLineage）参数。灰度 / 测试任务的运行时元数据不推进血缘库，避免在正式血缘图上留下只在测试跑过的临时节点；生产环境如需按任务单独关闭采集，可用文件级 `lineage.enabled=false`。

> [!NOTE]
> **为什么环境拼在名称里**：DolphinScheduler 中工作流名称就是身份标识，同名即同一个工作流。把环境拼进名称，同一份代码才能在不同环境各自拥有一份独立工作流。

## 四、库表的环境隔离

环境后缀不只落在工作流名称上，还落在**库名**上。同一业务域按环境拆成三套同构库，库名格式为 `{分层}_{业务域}_{环境}`，而表名本身**不带**环境后缀：

**同一张表在三套环境中的库名**

```bash
ods_olist_test.ods_user_info
ods_olist_gray.ods_user_info
ods_olist_prod.ods_user_info
```

三套库保持**同构**：同名表、同名字段、同分区、同更新策略，仅数据范围与运行环境不同。因此迁移环境时只需改库名后缀，表名与字段一律不动。

### 读写规则

| 提交环境 | 写入 | 读取 |
| --- | --- | --- |
| `test` 测试 | 只能写入测试库 `ods_olist_test` | 可读任意环境：test / gray / prod |
| `gray` 灰度 | 只能写入灰度库 `ods_olist_gray` | 可读任意环境：test / gray / prod |
| `prod` 生产 | 只能写入生产库 `ods_olist_prod` | **只能读生产库**，不允许引用 test / gray 的库表 |

- **写入必须同环境** — 作业写入哪套库由提交环境决定，写入目标库的环境后缀必须与提交环境一致，不允许测试作业写生产库；
- **非生产可跨环境读** — 测试 / 灰度作业允许读取其他环境的库表，用于与生产数据比对、联调验证；
- **生产严格封闭** — 生产作业涉及的所有库表（读与写）必须全部是生产环境的库表，出现任何 test / gray 库名都属违规；
- **环境后缀固定三档** — 只允许 `_test`（测试）、`_gray`（灰度）、`_prod`（生产），禁止自造 `_dev` / `_uat` / `_stage` 等其他后缀，也不得省略环境后缀；
- **未指明时按测试处理** — 环境取值以明确指定为准，未指明一律按 `_test`。

> [!WARNING]
> **库名后缀必须与工作流后缀一致**：两者取同一套环境枚举（`_test` / `_gray` / `_prod`），但拼在不同对象上——一个拼在工作流名称末尾，一个拼在库名末尾。以 `_prod` 提交的作业却写 `ods_olist_test` 库，等于同时污染两套环境，是最需要避免的一类错误。

库名在链路上的传递是**逐字照搬**：S2 设计阶段的建表语句库名、指标表「字段来源」与「下钻维度」中的库名、稽核规则「校验对象」中的库名，均须携带环境后缀并与设计文档逐字一致；S3 开发阶段代码中引用的库名照搬设计文档，禁止改写或省略环境后缀。

## 五、代码头如何变成调度任务

提交调度时，平台解析代码头并把字段映射到 DolphinScheduler 任务节点的对应位置，无需手工填一遍参数：

| 代码头字段 | 调度侧去向 | 说明 |
| --- | --- | --- |
| `@引擎` | 任务类型 | 取值限定在允许集合内（spark / flink / kyuubi / hive / doris / http 等）；未声明时默认按 SPARK 判定 |
| `@依赖` | DEPENDENT 依赖节点 | 按 `{调度项目}.{前置任务名称}` 生成依赖任务节点，支持跨项目依赖 |
| `@程序参数` | 任务节点「主参数（mainArgs）」 | 随任务一起提交的业务入参，如 `--day 20260501` |
| `@资源参数` | 节点资源字段 | 自动填入 Executor 数量 / Driver 内存 / Executor 内存与核数 / YARN 队列等 |
| `@任务参数` | 节点提交字段 + 其他参数 | 能对上字段的（部署模式、主 Class）自动填入，其余原样进「其他参数」 |
| `@数据源` | 归属与溯源信息 | 用于数据源核对与项目归属 |

主 Jar 与「应用名称」由编译产物和「项目.工作流.任务」自动生成，不写进代码头（写 `--jars` / `--name` 也无效）。

## 六、工作流与任务命名规范

- **工作流名称** — 等于程序文件所在**父目录的完整路径**，目录分隔符替换为下划线，再拼环境后缀；若文件直接放在根目录下，则取文件名（去扩展名）；
- **任务名称** — 每个处理程序文件对应一个调度任务，任务名为文件名（不含扩展名）。

例如文件路径 `pay/sql/ods/ods_trade_order_load_d.sql`，提交到生产环境后：

| 对象 | 取值 | 推导方式 |
| --- | --- | --- |
| 工作流名称 | `pay_sql_ods_prod` | 父目录 `pay/sql/ods` 的分隔符替换为下划线，再拼环境后缀 `_prod` |
| 任务名称 | `ods_trade_order_load_d` | 文件名去扩展名 |

目录结构遵循「产品线 / 程序类型 / 数仓分层」三级：程序类型分为 `sql`（SQL 程序）、`code`（Java / Scala 程序）、`algo`（Python 算法程序）三类，Java / Scala 的通用工具类统一放在 `code/utils` 下。

## 七、上线与运行

- **上线状态** — 工作流有上线 / 下线两种状态；**上线状态的工作流不能编辑、也不能删除**，需先下线再调整；
- **定时调度** — 定时只能在**已上线**的工作流上启用；同一工作流可新建定时，也可对既有定时做更新、上下线与删除；
- **运行管理** — 工作流实例可查看 DAG 与各节点状态，支持手动触发、暂停 / 停止；失败实例支持**重跑**（失败节点恢复执行）。

> [!WARNING]
> **发布顺序建议**：先在测试环境跑通全链路与依赖，再进灰度验证口径与性能，最后才提交生产并配置定时。三次提交的代码应保持同一份，仅环境不同，便于对比与回滚。
