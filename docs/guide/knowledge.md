# 知识管理

> [文档首页](../README.md) › 使用教程

知识库不是「给新人看的文档仓库」，而是**智能体的第一手上下文来源**。所有智能体在动手之前的信息获取顺序固定为：知识库 → 后端元数据服务 → 已有指标口径。这意味着知识库的内容质量直接决定智能体产出物的准确性——写错的知识库会让智能体「自信地做错」。

## 一、三类知识文档

| 类型 | 标识 | 面向对象 | 应覆盖内容 |
| --- | --- | --- | --- |
| **业务知识** | `business_knowledge` | 全体角色、需求类与设计类智能体 | 业务域划分、业务过程与业务含义、指标口径背景、术语表、常见业务问题与解释 |
| **集群运维** | `cluster_ops` | 运维与排查场景 | 集群资源与队列说明、环境与地址约定、常见故障现象与处置办法、调度与引擎配置要点 |
| **开发规范** | `dev_standard` | 开发类智能体与开发工程师 | 分层与命名规则、代码头写法、参数约定、质量规则写法、易错点与约定俗成 |

## 二、文档字段与检索

- **标题**：应可被关键词命中，用「问题/对象的名称」而非泛称（如「订单主题域口径说明」，而非「说明文档」）；
- **类型**：从上表三类中选择，选错类型会导致智能体在错误的场景下引用；
- **内容**：Markdown 格式，支持标题、列表、表格、代码块；
- **描述**：一句话摘要，用于检索结果列表中的快速判断；
- **浏览量**：系统自动记录，可作为「哪些文档真正有用」的参考。

当前检索方式为**关键字匹配**（对标题与内容做匹配），未引入向量检索或语义重排。因此**写清楚关键词**比写漂亮文笔更重要——业务方口中的说法、字段实际名称、常见错别字写法，都值得写进正文以便被命中。

## 三、编写规范

#### 1. 一文档一主题

每篇文档聚焦一个业务对象或一个规范点，不要把多个主题混写在一篇里。混写的后果是检索命中后智能体拿到大量无关上下文。

#### 2. 结论前置，口径可核对

开头直接给出定义与规则；涉及口径的，写明计算逻辑与适用范围（含不含某类订单、时间口径是自然日还是业务日）。避免「原则上」「一般情况下」这类无法执行的表述。

#### 3. 用真实名称书写

库名、表名、字段名、指标编码必须与元数据中一致，不要用口语化代称。智能体据此查证元数据，名称不一致会导致查证失败转而臆造。

#### 4. 标注时效与责任人

写明生效时间与维护责任人。业务口径会变，读到过期文档比读不到文档更危险。

#### 5. 示例优先

能用示例说明的不要只用文字。规范的代码头写法、正确的参数取值、典型的错误写法与正确写法的对比，都应以代码块给出。

## 四、维护约定

| 时机 | 应做的事 |
| --- | --- |
| 业务口径变更时 | 同步更新业务知识文档，并在文档中标注变更时间；不同步更新等于放任智能体使用旧口径 |
| 新增业务域/主题域时 | 补充业务含义与术语，避免智能体在 S2 设计阶段凭名称臆测业务过程 |
| 开发规范调整时 | 更新开发规范文档；规范类文档应保持与代码头、命名的实际约定一致 |
| 集群配置或环境变更时 | 更新集群运维文档中的地址、队列与配置项 |
| 排查出新型故障后 | 把现象 → 原因 → 处置沉淀为运维文档，形成可复用经验 |

## 五、智能体如何使用知识库

各角色的信息获取原则一致：

- **知识库优先**：先查知识库中的业务规范与开发规范，理解业务背景与约定；
- **元数据查证**：再通过后端元数据服务确认库表结构、字段业务含义与数据源；
- **口径对齐**：最后比对已有指标口径，优先复用而非新造；
- **不臆造**：查证不到的名称与口径必须明确告知用户，禁止凭猜测填写。

> [!TIP]
> 判断一篇知识库文档是否「合格」的标准很直接：**把这篇文档给一个新来的工程师，他能否在不问人的情况下写出符合约定的需求文档或代码？**如果不能，通常缺失的是名称、口径边界与示例，而不是篇幅。
