# 需求管理

> [文档首页](../README.md) › 使用教程

需求管理是数据研发链路的**第一环（S1 业务需求）**：用业务语言把模糊诉求固化成一份结构化、可被下游消费的需求文档。它只回答「要什么、为什么、怎么用」，不写 SQL、不设计表结构。

## 一、角色与边界

在「开发助手」的 AI 助手面板中，把任务类型切换为**「需求编写」**，即进入业务需求方角色：

| 职责 | 边界（不做） |
| --- | --- |
| 把业务需求转化为数据需求，界定指标口径<br>编写数据开发需求文档，并复核已有文档的数据源与业务逻辑错误<br>识别并复用已有指标，避免重复建设<br>标注本需求涉及的敏感数据范围，供下游分类分级 | 不编写 SQL<br>不设计表结构<br>不修改代码<br>不决定技术选型 |

需求文档全文使用**业务语言**，不出现 SQL、库表字段名与技术选型术语。

## 二、工作流程

#### 1. 需求澄清

先确认业务背景、目标、使用对象与决策场景；信息不足时一次性列出全部待确认问题，避免多轮追问。

#### 2. 现状调研

按 知识库（业务规范、开发规范、已有业务术语）→ 元数据服务（库表结构、字段业务含义、数据源）→ 已有指标清单 的顺序获取上下文，先查证再落笔。

#### 3. 复用优先

先查找可复用的已有指标；能复用则复用，口径有差异时说明差异并给出取舍建议，禁止同义不同名重复建设。

#### 4. 场景梳理

按业务目标拆解可分析场景，每个场景明确「看什么、给谁看、多久看一次、看完做什么」。

#### 5. 指标定义

为每个场景定义指标，区分原子 / 派生 / 复合指标，统一业务口径并声明可下钻维度。

#### 6. 质量与约束

明确数据范围、时效要求、输出方式、质量要求与优先级。

#### 7. 落地产出

写入工作空间的 `docs/{业务名称}_开发需求.md`；文件已存在时**增量追加**，不覆盖已有内容。

#### 8. 交付自检

按自检清单逐项核对，不通过先修正产出，再回复用户。

## 三、需求文档章节规范（顺序固定）

| 序号 | 章节 | 内容要点 |
| --- | --- | --- |
| 1 | **需求背景** | 业务目标、使用对象、决策场景、期望价值 |
| 2 | **可分析场景梳理** | 逐条说明分析目的、分析维度（时间 / 渠道 / 地区 / 用户分层）与期望数据粒度 |
| 3 | **数据指标** | 见下方强约束章节，该章节内除指标表外不得出现其他表格 |
| 4 | **数据范围与加工逻辑** | 数据时间范围、涉及的源系统与业务对象；加工逻辑用自然语言分步描述，不写 SQL |
| 5 | **数据时效要求** | 更新频率、最晚可用时间、历史回溯范围 |
| 6 | **数据输出方式** | 报表 / 看板 / 接口 / 导出文件 / 下游系统，以及使用方与访问方式 |
| 7 | **数据质量要求** | 需覆盖的规则类型与可接受偏差，用业务语言描述 |
| 8 | **敏感数据说明** | 本需求涉及的敏感数据范围与脱敏期望 |
| 9 | **优先级与验收标准** | 优先级（P0 / P1 / P2）与可量化的验收标准 |
| 10 | **待确认问题** | 信息缺失且查证无果的内容，逐条列出 |

## 四、数据指标表（机器解析，强约束）

需求文档必须包含 `## 数据指标` 二级标题，且表头必须**严格为以下 7 列、顺序不变**：

**需求文档「数据指标」表头**

```
| 指标名称 | 主题域 | 业务定义 | 计算口径 | 过滤条件 | 下钻维度 | 应用场景 |
```

| 列名 | 是否必填 | 填写要求 |
| --- | --- | --- |
| **指标名称** | 必填 | 简短可读的业务名称，如「日活用户数」；全局唯一，下游逐字继承 |
| **主题域** | 必填 | 指标所属业务主题，如「用户域」「交易域」「流量域」 |
| **业务定义** | 必填 | 说明「统计什么」，如「当日产生有效行为的去重用户数」 |
| **计算口径** | 必填 | 用业务语言描述统计规则，**不写 SQL 表达式** |
| **过滤条件** | 可填 | 用业务语言描述的筛选范围，无则留空 |
| **下钻维度** | 必填 | 可从哪些角度拆解、可钻取到什么粒度，层级用「→」由粗到细排列，如「时间（日→周→月）、渠道（一级→二级）」；确实无需下钻填「无」 |
| **应用场景** | 必填 | 服务哪个分析场景或决策，如「日常运营日报」；该列直接决定下游 ADS 层产出 |

> [!WARNING]
> **书写约束**：每个指标占一行，单元格内禁止换行、禁止出现竖线字符；不得合并单元格或嵌套表格；表格上方与下方除空行外不插入其他内容。

## 五、指标定义原则

- **层级清晰** — 区分原子指标（不可再拆）、派生指标（原子指标 + 业务限定 + 时间周期）、复合指标（多指标运算）；
- **口径唯一** — 同一业务含义的指标只定义一次，名称、业务定义、计算口径三者必须自洽；
- **可度量** — 每个指标都能回答「用什么数据、按什么规则算出来」，避免「用户满意度」这类模糊表述；
- **可下钻** — 必须声明下钻维度与层级关系，能回答「总量异常时按什么拆开看」；
- **名称稳定** — 指标名称一经定义即为全链路主键，下游禁止改名、合并或拆分。

## 六、下游映射（S1 → S2）

需求指标表是数仓设计指标表的**唯一输入**，映射关系固定：

| 需求列 | 设计列 | 下游变化 |
| --- | --- | --- |
| 指标名称 | 指标名称 | 逐字继承，作为链路主键 |
| 主题域 | 主题域 | 取值保持一致 |
| 业务定义 | 指标含义 | 语义不变，可补充技术细节 |
| 计算口径 | 计算表达式 | 由业务语言转写为 SQL 计算逻辑 |
| 过滤条件 | 过滤条件 | 转写为可执行的过滤条件 |
| 下钻维度 | 下钻维度 | 转写为可下钻的维度字段（维度名 + 库.表:字段） |
| 应用场景 | — | 落到 ADS 层表设计与「数据输出方式」 |
| — | 指标编码 / 字段来源 / 数据源 | 由数据架构师分配与绑定 |

> [!NOTE]
> 需求文档产出后，可在开发助手对 Markdown 文件右键使用**指标抽取**，把「数据指标」表解析为平台指标（详见「指标管理」）。
