# 数据安全

> [文档首页](../README.md) › 使用教程

DataForge 的数据安全不依赖「事后审计追责」，而是在**数据被取用的那一刻**完成管控。其核心机制是：权限配置即安全策略，SQL 在**下发到数据库之前**被改写以裁剪行与列，改写不成功则拒绝执行。本章说明掩码、下载、审计、水印四类管控的实际能力与边界。

## 一、安全底座：库表权限

数据安全的底座是权限管理中的**库表权限**。它不是一个「能不能看这张表」的粗粒度开关，而是一组行列级的约束条件，在每次查询时逐条生效：

| 配置项 | 作用 | 生效方式 |
| --- | --- | --- |
| `rowFilterSql` | 行级过滤条件，限定用户只能看到哪些行 | 条件**并入 SQL 的 WHERE** 后下发，在数据库侧完成过滤 |
| `columnPermissions` | 列级可见范围 | 投影列**裁剪为白名单**，未授权列不出现在下发语句中 |
| `dataMaskingRule` | 列级脱敏规则 | 在投影表达式中对目标列套用脱敏函数 |
| `canExport` | 是否允许下载与导出 | 控制结果集导出与文件下载入口 |
| `permissionScope` | 权限作用范围 | 限定该授权适用的数据范围 |

> [!WARNING]
> **Fail-close（拒绝对外开放优先于放行）**：当系统无法安全地把权限条件改写进 SQL 时（例如语句结构复杂、无法可靠注入 WHERE 条件），一律**拒绝执行**，而不是放行后依赖日志追责。这对使用者表现为查询报错，属预期行为。

## 二、数据掩码

脱敏粒度落在**列**上，由权限配置人员在授权时按列指定脱敏档位：

| 档位 | 效果 |
| --- | --- |
| `full` | 完全不展示该列内容（最严格） |
| 身份证 | 按身份证规则打码 |
| 手机 | 按手机号规则打码 |
| 邮箱 | 按邮箱规则打码 |
| 部分 | 部分字符遮蔽 |

### 多角色叠加时的合并规则

同一用户可能同时命中多个角色，此时**按列取更严格者**合并，而不是按角色取并集：

### 关键约束

- `full` 档位下该字段**完全不可读**，不是返回空值而是不返回该列；
- **配置了脱敏规则的字段不允许写入**——避免用「写回明文」绕过读侧掩码；
- 脱敏对**智能体同样生效**：AI 数据分析师与各类智能体取数时走同一套权限改写，不存在「对话式查询绕过脱敏」的通道。

> [!NOTE]
> 当前版本**没有**自动敏感数据识别引擎，也没有自动分级分类标签。脱敏规则由人工在权限配置中逐列指定。敏感字段的识别依赖研发链路上的约定：在 S1 阶段由业务方标注敏感字段，在 S2 阶段按 `cla:xxx` 格式写入表/字段注释（如 `cla:用户信息-一般`），S3 阶段据此实现脱敏处理。因此**上游标注缺失会直接导致下游漏脱敏**。

## 三、下载与导出管控

「能查询」与「能把数据带走」是两件事，分别控制：

| 场景 | 管控方式 |
| --- | --- |
| 查询结果导出 | 受库表权限的 `canExport` 控制；允许导出时，导出得到的是**已按其权限裁剪与脱敏后**的结果集 |
| 文件浏览器下载 | 按存储配置的访问权限控制，支持上传、预览、下载等操作 |
| 审计日志导出 | 操作日志支持导出 CSV，用于合规归档（该导出本身记录在案） |

要点在于：**脱敏发生在 SQL 层而非展示层**。因此导出、复制、图表分析拿到的都是脱敏后的数据，不存在「界面上打了码、导出拿到明文」的可能性。

## 四、写入合规

读侧靠权限改写，写侧靠引擎级闸门。平台可选择安装 **spark-listener** / **flink-listener**：

- 在 **Analysis 阶段**（SQL 解析期，尚未执行）检查目标表与路径的合规规则，命中即**抛异常**；
- 因此在**物理写入发生之前**就被阻断，不产生脏数据；
- 跨 Spark 2.4 / 3.1 / 4.1 版本适配，**不依赖 DataForge 平台在线**——即使作业被其他调度器拉起，规则依然生效。

> [!TIP]
> 读侧管控与写侧管控是互补的：前者防止「不该看的被看到」，后者防止「不该写的被写入」。前者依赖平台在链路上（SQL 经平台下发），后者内嵌在引擎里（不依赖平台），因此对绕过平台直接提交的作业同样有效。

## 五、审计与操作日志

全部关键操作留痕，用于合规审计与问题回溯。日志逐条记录以下字段：

| 字段 | 用途 |
| --- | --- |
| 操作用户 | 定位责任人 |
| 模块 / 操作名称 / 操作类型 | 还原「做了什么」 |
| 请求方法 / 响应状态 | 判断操作是否成功 |
| IP / 时间 / 耗时 | 定位来源与性能异常 |
| 敏感标记 | 标记该操作是否触及敏感数据 |
| AI 请求标记 | 区分人工操作与智能体发起，便于核查智能体行为边界 |

- 支持按用户、模块、时间范围等维度查询，并可**导出 CSV** 归档；
- **AI 请求标记**是审计上的一个要点：智能体发起的取数同样留痕，可与人工操作分开核查。

## 六、水印

> [!WARNING]
> **当前版本未提供数据水印能力**（包括明水印与暗水印）。因此不具备「从泄漏的截图或导出文件中追溯到具体用户」的溯源手段。在需要强溯源的场景下，应以下列既有机制替代：
> ① 依赖**操作日志**的完整留痕定位数据被谁取用；
> ② 通过 `canExport` **收紧导出权限**，用「不可带走」替代「带走后可追溯」；
> ③ 对高敏字段直接配置 `full` 档位**禁止读取**，而非展示后加水印。

## 七、安全自查清单

| 检查项 | 确认内容 |
| --- | --- |
| 敏感字段已标注 | S1 需求文档已识别敏感字段，S2 设计文档中已按 `cla:xxx` 写入注释 |
| 脱敏规则已配置 | 高敏字段已按列配置脱敏档位，且多角色叠加后按严格者生效 |
| 行级范围已限定 | 涉及业务归属的数据已配置 `rowFilterSql`，未依赖使用者自觉 |
| 导出权限已确认 | 确需导出的库表才开放 `canExport`，非默认开放 |
| 写入规则已下发 | 高敏目标表已在引擎侧配置写入合规规则，且以 prod 环境提交 |
| 操作可审计 | 关键操作可在操作日志中查询到，AI 请求可通过标记区分 |
