# 开发过程

> [文档首页](../README.md) › 使用教程

本节把「需求管理 → 调度上线」的全过程串成一条链路：需求管理（S1）→ 数仓设计（S2）→ 数据开发（S3）→ 质量稽核 → 提交调度（测试 → 灰度 → 生产）→ 上线运行。开始前请先按「项目管理」完成项目创建与目录规划，每一环都有明确的产出物与闸门，任一环不达标，下一环无法开始。

## 一、阶段流程

#### 1. 需求管理（S1）

以「需求编写」任务产出 `docs/{业务名称}_开发需求.md`：用业务语言写清分析场景、数据指标（7 列强约束）、时效与验收标准，不写 SQL、不设计表结构。详见「需求管理」。

#### 2. 数仓设计（S2）

把需求翻译为可实现的数仓模型：确定分层归属（ODS / DIM / DWD / DWS / DQC / ADS）、表结构与字段类型、粒度与分区更新策略、上下游依赖，产出 `docs/{业务名称}_数仓设计.md` 与 `ddls/{分层}_ddl.sql`；指标编码与字段来源在此阶段绑定。

#### 3. 数据开发（S3）

以「数据开发」任务按设计文档逐表实现处理程序，落到 `sql/` / `code/` / `algo/` 对应分层目录；**先写代码头再写主体**，代码头是机器解析契约。详见「代码管理」。

#### 4. 质量稽核

把设计文档中的稽核规则实现为独立的质量校验任务，挂在处理任务下游，规则级结果按规范回传平台。

#### 5. 提交前校验

SQL 经 `sql-validate` 校验语法、Java / Scala 经 `compile` 编译；同时校验代码头合规、`@依赖` 存在性与作业名一致性，任一不通过都无法提交。

#### 6. 提交调度：测试 → 灰度 → 生产

同一份代码在「提交调度」中依次按 `test`、`gray`、`prod` 提交，形成三套互相独立的工作流；作业写入库的环境后缀必须与提交环境一致。详见「持续集成」。

#### 7. 上线与定时调度

生产验证通过后上线工作流并配置定时；已上线的工作流不可编辑、不可删除，需先下线再调整；运行管理中可查看 DAG、手动触发、暂停 / 停止与失败重跑。

#### 8. 上线之后

只有生产环境注入血缘参数，数据血缘图随之生成；需求阶段定义的指标在指标模块中可查，统计数据反映产出表与指标的使用情况。详见「数据应用」。

## 二、阶段与产出物

| 阶段 | 任务类型 | 产出物 | 详细章节 |
| --- | --- | --- | --- |
| **S1 需求管理** | 需求编写 | `docs/{业务名称}_开发需求.md`（含数据指标表） | 需求管理 |
| **S2 数仓设计** | 数仓设计 | `docs/{业务名称}_数仓设计.md`、`ddls/{分层}_ddl.sql` | — |
| **S3 数据开发** | 数据开发 | 处理程序（`sql` / `code` / `algo`）与质量校验任务 | 代码管理 |
| **提交与上线** | — | 三套环境工作流（`_test` / `_gray` / `_prod`）与定时调度 | 持续集成 |

## 三、过程中的三个闸门

- **代码头契约** — 提交前校验代码头必填项、`@依赖` 存在性与作业名一致性，不通过即拦截，进不了调度；
- **环境后缀** — 工作流名称与库名携带同一套环境枚举，测试 / 灰度作业只能写本环境库，生产作业读写均限生产库；
- **血缘注入** — 仅生产环境注入血缘参数，避免测试 / 灰度的临时节点污染正式血缘图。

> [!NOTE]
> **发布顺序**：先在测试环境跑通全链路与依赖，再进灰度验证口径与性能，最后提交生产并配置定时；三次提交保持**同一份代码**，仅环境不同，便于对比与回滚。
