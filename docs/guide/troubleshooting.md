# 问题排查

> [文档首页](../README.md) › 使用教程

排查从**作业名**出发：先定位工作流，再沿「依赖 → 日志 → 产出 → 影响」串成全链路分析，避免只盯单个失败节点而漏掉真正的上游根因。

## 一、三类关键信息

| 信息 | 来源 | 能回答的问题 |
| --- | --- | --- |
| **运行日志** | 调度管理 → 任务实例详情 → 运行日志；或工作流实例 DAG 中点击任务节点「查看日志」 | 这个节点为什么失败？报错在哪一行？ |
| **依赖关系** | DolphinScheduler 工作流 DAG、代码头 `@依赖`、Marquez 血缘 | 它依赖谁？谁依赖它？上游是否已成功产出？ |
| **产出与影响** | 目标库表元数据、指标、血缘图谱 | 这张表喂给了哪些下游？影响面有多大？ |

## 二、按作业名定位问题

#### 1. 由作业名反推工作流

作业名（任务名）等于程序文件名去扩展名；工作流名等于程序文件父目录路径拼接再加环境后缀。例如作业 `ods_trade_order_load_d` 属于工作流 `pay_sql_ods_prod`。先在**调度管理**中按工作流定位。

#### 2. 打开工作流实例看 DAG

在工作流实例详情中查看 DAG 结构与各节点状态：先看是**本节点失败**，还是**上游未产出导致被跳过 / 等待**。

#### 3. 点节点看运行日志

点击具体任务节点查看运行日志，日志按行分段拉取，可继续加载后段内容，定位到实际报错位置。

#### 4. 结合依赖判断根因

核对上游任务是否成功、`@依赖` 是否声明完整、参数是否随批次正确下发（`@程序参数` → 节点主参数）、资源是否不足（内存 / 并行度 / 队列）。

#### 5. 处置与重跑

修复后按需重跑：失败实例可对失败节点做**重跑**；运行中的实例支持暂停 / 停止。若根因在上游，应先修复并重跑上游，再重跑下游。

## 三、依赖关系的三处来源

| 来源 | 表达的是什么依赖 | 典型用途 |
| --- | --- | --- |
| **调度 DAG** | 调度层的执行依赖：工作流实例中的任务节点与连线，跨工作流依赖以 DEPENDENT 任务节点表达 | 判断「今天这个节点为什么没跑」 |
| **代码头 `@依赖`** | 源码声明的显式前置依赖，格式 `{调度项目}.{前置任务名称}`，提交时生成依赖节点 | 核对依赖是否声明完整；新任务上线前确认拓扑 |
| **数据血缘** | 表级与字段级的真实读写依赖，由运行期元数据采集沉淀 | 判断「改了这张表会影响谁」、「这个字段从哪来」 |

> [!NOTE]
> 调度依赖与数据血缘**不完全等价**：调度依赖说明「什么时候跑」，血缘说明「数据从哪到哪」。排查数据问题时两者都要看——只看调度 DAG 会漏掉同一工作流内的数据流向。

## 四、全链路分析示例

以「首页报表数据不对」为例，从结果表反推链路：

#### 1. 确认现象与范围

在数据探索中查询 ADS 结果表，确认是全部日期错还是某个分区错，判断是数据问题还是口径问题。

#### 2. 在血缘图上回溯上游

打开数据血缘，从 ADS 表逐层回溯 DWS → DWD → ODS，定位异常首次出现的最上游一层。

#### 3. 用调度 DAG 交叉验证

找到产出该表的作业名与工作流，在工作流实例中确认对应批次是否成功、是否重跑过、上游是否延迟。

#### 4. 逐个节点查看日志

沿链路自上游向下逐个节点查看运行日志，确认哪一步数据开始异常（过滤条件、关联未命中、参数取值错误等）。

#### 5. 修复并评估影响面

修复后沿血缘查看该表的**下游节点**，确认需要一并重跑的范围，再按依赖顺序重跑。

## 五、日志查看要点

- 日志按**任务实例**维度获取，可分段加载（按起始行号 + 行数）后段内容，长日志不必等全量返回；
- 入口有两个：**任务实例详情 → 运行日志**页签（只看单个任务），或**工作流实例 DAG → 任务节点 → 查看日志**（带上下游上下文）；
- 排查顺序建议**先上游后下游**：下游失败常由上游未产出或数据为空引起，先重跑下游只是重复失败。
