# 代码管理

> [文档首页](../README.md) › 使用教程

代码管理覆盖数据开发链路**第三环（S3 数据开发）**与工程侧管理：目录结构、命名规范、代码头契约、开发规范，以及基于 Git 的版本管理。核心约束是——**代码头是机器解析的契约**，写错就等于提交不了。

## 一、职责与边界

在 AI 助手面板把任务类型切换为**「数据开发」**，即进入数据开发工程师角色：依据 `docs/{业务名称}_数仓设计.md` 与 `ddls/{分层}_ddl.sql` 实现处理程序。

- **必须做** — 按设计文档逐表产出处理程序；按设计实现指标计算并显式标注指标编码；代码完成后通过 `compile`（Java / Scala）或 `sql-validate`（SQL）校验；把质量校验结果按规范回传平台；
- **不可做** — 擅自变更数仓设计（分层归属、表结构、字段类型、指标口径）；臆造表名、字段名与业务口径。发现设计缺陷时先说明影响并给出建议，经确认后再改代码。

## 二、工作流程

#### 1. 设计解读

读取数仓设计文档与对应分层 DDL，逐表提取目标表、字段与类型、粒度、计算口径、分区与更新策略、上下游依赖。

#### 2. 现状调研

知识库（集群架构、开发规范、业务规范、处理流程）→ 元数据服务（库表结构、字段含义、数据源）→ Marquez（血缘与上下游依赖）。

#### 3. 复用优先

先查找可复用的已有程序、utils 工具类与集群同步组件，禁止重复造轮子。

#### 4. 技术选型

确定运行引擎与实现语言：能用 SQL 表达且性能可接受的一律用 SQL；数据同步优先复用集群已有组件（DataX / SeaTunnel / Sqoop）。

#### 5. 编码实现

先写代码头再写主体，按「代码头格式规范」归类三个参数字段；SQL 与 Java / Scala / Python 分别遵循对应开发规范。

#### 6. 质量实现

把设计文档定义的稽核规则实现为**独立的质量校验任务**，挂在处理任务下游，并把规则级结果回传平台。

#### 7. 校验修复

调用 `compile` / `sql-validate`，逐个修复报错直至零错误；校验不通过不得落地产出。

#### 8. 落地产出与自检

用文件写入工具落到目标目录，再按交付前自检清单逐项核对。

## 三、工程目录结构

处理程序按**语言类型**分 `sql` / `code` / `algo` 三类，再按**数仓分层**归类；Java / Scala 的公共工具类统一放在 `code/utils`。文档与建表语句分别归入 `docs/` 与 `ddls/`。

**工程目录结构**

```
project-name/                       # 项目（对应事业部，也是调度项目与血缘命名空间名）
└── {product-line}/                 # 产品线目录
    ├── docs/                       # 需求与设计文档
    │   ├── {业务名称}_开发需求.md
    │   └── {业务名称}_数仓设计.md
    ├── ddls/                       # 建表语句（按分层拆文件）
    │   ├── ods_ddl.sql
    │   └── dwd_ddl.sql
    ├── sql/                        # SQL 程序
    │   ├── ods/
    │   └── dwd/
    ├── code/                       # Java / Scala 程序
    │   ├── ods/
    │   ├── dwd/
    │   └── utils/                  # 公共工具类
    └── algo/                       # Python 算法程序
```

## 四、命名规范

| 对象 | 格式 | 示例 |
| --- | --- | --- |
| **程序文件名** | `{分层}_{业务域}_{实体描述}_{操作类型}_{执行周期}.{扩展名}` | `ods_trade_order_load_d.sql`、`dws_trade_order_etl_d.java` |
| **操作类型** | load=加载、etl=转换清洗、sync=同步、calc=计算聚合、check=质量校验、export=导出 | `etl` |
| **执行周期** | d=日、h=小时、w=周、m=月、y=年、r=实时流式、f=全量快照 | `d` |
| **库名 / 表名** | `{分层}_{业务域}_{实体描述}_{刷新周期}`，全部小写加下划线；临时表 `tmp_` 前缀，视图 `v_` 前缀 | `dws_trade_order_d` |
| **Java / Scala 包声明** | `{项目编码}.{目录路径}`，文件名与类名一致 | 工作空间 `/tmp/warehouse/TEST` 下 `code/ods/test.java` → `package TEST.code.ods` |
| **调度任务名** | 与程序文件名一致（去扩展名） | `ods_trade_order_load_d` |

## 五、代码头格式规范（机器解析，强约束）

代码头必须位于**文件最开头**，用块注释（`/* ... */`）包裹、逐行书写，格式为 `* @键: 值`；必须连续书写，中途出现非代码头的行即视为代码头结束。禁止用行注释（`--` / `//` / `#`）书写代码头，否则会被判定不符合规范并**拦截提交**。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `@备注` | 必填 | 描述业务逻辑、业务需求与注意点；若本程序产出设计文档中的指标，须写明指标编码 |
| `@引擎` | 必填 | 取值限定在允许集合内（spark / flink / flink_stream / kyuubi / hive / hivecli / doris / clickhouse / starrocks / mysql / postgresql / presto / trino / python / shell / mr / mapreduce / datax / sqoop / seatunnel / dinky / linkis / java / procedure / http）；`.java`/`.scala` 未声明时默认按 SPARK 判定 |
| `@依赖` | 必填 | 格式 `{调度项目}.{前置任务名称}`，多个用英文逗号分隔；无前置依赖填「无」 |
| `@程序参数` | 必填 | 业务入参（这次要算什么），取值写真实值；无则填「无」 |
| `@资源参数` | 必填 | 算力与资源归属（这次给多少资源）；无则填「无」 |
| `@任务参数` | 必填 | 提交形态与引擎侧配置（这个任务怎么提交）；无则填「无」 |
| `@数据源` | 必填 | 代码用到的数据源名称，多个用英文逗号分隔 |
| `@数仓` | 可填 | 所属数仓 / 项目编码 |

**三个参数字段的区别**（三者互斥，禁止混写）：

| 字段 | 回答的问题 | 典型取值 | 提交调度时的去向 |
| --- | --- | --- | --- |
| `@程序参数` | 程序这次要算什么 | `--day 20260501`、`-threshold 0.9` | 写进任务节点「主参数（mainArgs）」；参数名用于「运行程序」弹窗预填 |
| `@资源参数` | 这次给多少资源 | `--num-executors 4 --driver-memory 2g`、`-p 4 -yjm 1024`、`--queue root.default` | 自动填入节点对应资源字段，不下发到程序入参 |
| `@任务参数` | 这个任务怎么提交、引擎侧怎么配 | `--master yarn --deploy-mode cluster`、`-Dyarn.application.name=xxx` | 能对上的字段（部署模式、主 Class）自动填入，其余原样进「其他参数」 |

**判定顺序**：是业务入参 → `@程序参数`；不是业务入参、且回答「给多少资源」（数量类：并行度、内存、核数、slot、队列）→ `@资源参数`；其余提交与引擎侧配置 → `@任务参数`。主 Jar 与「应用名称」由系统自动生成，**不要**写进代码头。

**代码头示例**：

**SQL 程序代码头**

```sql
/*
 * @备注: 将 ODS 层登录明细清洗后写入 DWD 层用户登录明细，按天分区，支持重跑；产出指标 USR_0001 日活用户数
 * @引擎: kyuubi
 * @依赖: test_project.ods_user_login_load_d
 * @程序参数: --day 20260501
 * @资源参数: --num-executors 4 --driver-memory 2g --executor-cores 2
 * @任务参数: 无
 * @数据源: test_datasource
 */
INSERT OVERWRITE TABLE dwd_user_login_d PARTITION (dt = '${day}')
-- 指标: USR_0001 日活用户数
SELECT user_id, login_time, channel
FROM ods_user_login_d
WHERE dt = '${day}'
```

## 六、SQL 开发规范

- **显式列名** — 禁止 `select *`；`insert` 必须写明目标列清单，不依赖字段顺序；
- **禁止硬编码** — 业务日期与分区值一律使用参数，禁止硬编码日期、账号、密码、密钥；
- **分区与幂等** — 写入分区表必须显式指定分区字段；按业务日期分区覆盖或先清后写，保证同一分区重复执行结果一致，禁止无分区条件的全表覆盖；
- **性能** — 过滤条件前置并优先使用分区裁剪；大表 join 小表优先广播；join 键处理 NULL；聚合前先过滤去重；
- **小文件治理** — 动态分区写入时按分区键 `distribute by` / `repartition`，控制输出文件数量与大小；
- **类型与精度** — 金额一律使用 `decimal`，禁止 float / double 存金额；时间字段格式与设计文档一致。

### SQL 变量编写规范（机器解析，强约束）

运行期取值一律写成 `${参数名}` 形式，系统按此识别程序参数：

| 规则 | 说明 |
| --- | --- |
| **合法名** | 字母或下划线开头，只含字母、数字、下划线、点、连字符，如 `${day}`、`${biz_date}`；禁止中文、空格、以数字或连字符开头 |
| **写在有效语句里** | 只有正文语句中的 `${...}` 会被识别为参数；注释里的示例变量会被忽略——参数声明写在代码头 `@程序参数`，正文只负责使用 |
| **与代码头同名声明** | 正文用到的每个变量都须在 `@程序参数` 中声明同名参数（逐字一致、大小写敏感） |
| **不要用内置日期写法** | 不要使用 DolphinScheduler 内置的 `$[yyyyMMdd]`，系统不会把它当作程序参数下发，运行时会取不到值 |
| **一词一义** | 同一语义在全脚本只用一个变量名（不要 `${day}` 与 `${dt}` 混用） |
| **引用时保留引号** | 须写成 `PARTITION (dt = '${day}')`、`WHERE dt = '${day}'`，不得写成 `dt = ${day}` |

## 七、Java / Scala / Python 开发规范

- **包与类名** — 包声明为 `{项目编码}.{目录路径}`，主类名与文件名一致；
- **公共逻辑** — 抽取到 `utils/` 目录复用，禁止在多个任务文件中复制同一段实现；
- **Spark** — 合理设置并行度与分区数，避免 `collect` 大结果集到 Driver，复用 SparkSession；大表关联关注数据倾斜并做广播或加盐处理；
- **Flink** — 明确状态后端与检查点配置，状态须设置 TTL；Source / Sink 需明确幂等或 exactly-once 语义；
- **资源与提交参数** — 声明在代码头 `@资源参数` / `@任务参数`，提交调度时自动填入任务节点，禁止硬编码在代码里；
- **敏感字段** — 按设计文档的分类分级与脱敏建议实现脱敏，禁止明文落库。

## 八、指标实现与质量回传

- **指标对齐** — 指标编码、名称、计算表达式逐项照搬设计文档，不得改写口径或重命名；SQL 在对应计算字段或 CTE 处加行注释 `-- 指标: {指标编码} {指标名称}`，Java / Scala / Python 在对应计算方法处加行注释说明指标编码；
- **一个指标一处产出** — 派生与复合指标引用上游已产出的原子指标结果，不得重复计算；
- **下钻维度对齐** — 按设计文档声明的维度输出分组字段，不得遗漏、新增或私自替换；
- **质量校验** — 校验任务与处理任务分离、单独成文件并挂在下游；输出须可定位：规则名、校验对象、阈值、实际值、是否通过。

校验任务除算出结果外，还必须把每条规则的校验结果**回传平台**（平台的运行记录、告警订阅与质量大盘都依赖这份回传）：

| 回传字段 | 必填 | 取值 |
| --- | --- | --- |
| `datasourceName` / `databaseName` / `tableName` | 是 | 被校验表的数据源、库与表，数据源与代码头 `@数据源` 一致 |
| `batchNo` | 是 | 本次业务批次，与处理任务同一批次参数一致 |
| `ruleName` | 是 | 逐字取自设计文档「稽核规则清单」的规则名 |
| `ruleType` | 是 | 逐字取自 7 类质量规则类型名称 |
| `checkObject` / `threshold` / `actualValue` | 否 | 校验对象（库.表.字段）、阈值、实际值 |
| `passed` | 是 | 是否通过，true / false |
| `checkRecordCount` / `failRecordCount` | 否 | 检查记录数、未通过记录数 |
| `failDetail` | 否 | 失败明细，便于定位与修复 |

> [!WARNING]
> 回传地址与访问令牌由运行环境注入，程序读取环境变量 `DATAFORGE_QUALITY_REPORT_URL` 与 `DATAFORGE_QUALITY_REPORT_TOKEN`，**禁止把地址、令牌、账号硬编码进代码**。回传失败不得改变校验任务本身的成败判定：捕获异常、记录日志后继续执行。

## 九、Git 版本管理

开发助手内置 Git 集成，无需切换到命令行即可完成日常版本管理：

- **仓库识别与状态** — 打开工程后自动识别是否为 Git 工作区，展示当前分支、文件变更列表与领先 / 落后提交数；
- **变更查看** — 选中文件查看差异（diff），确认改动内容；
- **提交** — 勾选要提交的文件 → 暂存 → 填写提交信息 → 提交；提交信息可由 AI 依据变更内容自动生成草稿，确认后再提交；
- **文件历史** — 单个文件可查看历史版本并对比，便于追溯「这段逻辑是什么时候、为什么改的」。

## 十、交付前自检清单

- **设计对齐** — 目标表、字段、类型、分区与口径同数仓设计文档及 DDL 逐项一致，无臆造字段；
- **校验通过** — SQL 通过 `sql-validate`，Java / Scala 通过 `compile`，无语法与编译错误；
- **代码头合规** — 块注释书写、位于文件开头且连续，必填项齐全，三个参数字段齐备且无对应参数时写「无」；
- **参数归属** — 业务入参写 `@程序参数`、资源诉求写 `@资源参数`、提交与引擎侧配置写 `@任务参数`，三者未混写，且取值均为真实生效值（不是占位符）；
- **变量合规** — SQL 正文里的 `${变量}` 均为合法标识符、已在 `@程序参数` 同名声明，未使用 `$[yyyyMMdd]`，无硬编码日期；
- **可重跑** — 按分区重复执行结果一致，不产生重复数据或部分写入；
- **命名与路径** — 文件名与目录符合命名规范，Java / Scala 包声明与类名校验通过。
