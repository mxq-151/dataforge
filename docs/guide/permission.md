# 权限管理

> [文档首页](../README.md) › 使用教程

平台采用 RBAC 权限模型，权限从「能不能看到这个功能」一路收敛到「能不能看到这一列、这一行、能不能导出」。管理员在「系统管理」中维护**用户 / 角色 / 租户**三类对象，并在四类资源上完成授权。

## 一、角色体系

平台内置以下角色，分别对应研发链路上的不同职责，并决定 AI 助手使用哪一套系统指令：

| 角色 | 标识 | 职责定位 |
| --- | --- | --- |
| **超级管理员** | `SUPER_ADMIN` | 平台系统管理与运维：用户、角色、权限、租户、系统配置、服务状态与日志 |
| **业务需求方** | `BUSINESS_REQUESTER` | 需求管理链路的 S1：把业务诉求转成需求文档与指标定义，不做技术实现 |
| **数据架构师** | `DATA_ARCHITECT` | 链路 S2：数仓建模、DDL 设计、质量稽核规则设计 |
| **数据开发工程师** | `DATA_DEV_ENGINEER` | 链路 S3：按设计文档交付处理程序与质量校验任务，并提交调度 |
| **数据分析师** | `DATA_ANALYST` | 旁路角色：面向数据探索的即席查询与分析，**只读不写** |

## 二、四类资源权限

权限按**资源类型**分为四类。这四类是彼此独立的资源，**相互之间没有层级或包含关系**——既不是「由粗到细」的递进，也不存在「有了上一级就自动拥有下一级」。一个角色最终能做什么，是它在四类资源上各自取得的授权叠加的结果，因此需要分别授权：

| 权限类别 | 资源对象 | 授权内容 |
| --- | --- | --- |
| **菜单权限** | 平台功能模块 | 控制可访问的功能菜单（开发助手、数据探索、知识库、指标管理、调度管理等），可批量分配 |
| **文件权限** | 大数据集群上的数据文件 | 按「存储配置 + 文件路径」授权，可开启递归使其对子路径一并生效；控制数据文件的可读 / 读写 / 完全控制 |
| **项目权限** | 开发项目 | 控制项目在开发、指标、调度等模块中的访问级别，可批量分配给多个角色 |
| **库表权限** | 数据源下的库与表 | 控制表的增删改查与导出，支持整表授权、字段级授权、行级过滤与数据掩码 |

> [!NOTE]
> 四类权限之间**不联动**：授予项目权限不会顺带放开项目相关的数据文件，授予文件权限也不会顺带取得该路径所涉库表的查询权。缺少哪一类就单独授哪一类。

## 三、授权对象：用户 / 角色 / 租户

进入「系统管理 → 用户角色」，在用户、角色、租户三个子页签中维护授权基础数据：

- **用户** — 平台登录账号，与租户**一一对应**；
- **租户** — **访问资源的真正主体**。引入租户这一层，主要是为了解决**离职继承**问题：资源归属与授权关系挂在租户上而非自然人账号上。人员离职时把租户移交给接任者，接任者即继承原有的项目、文件与库表授权，无需逐项重新授权；若没有这层设计，人员变动会让授权关系随账号一起失效，所有权限都得重建。租户维护名称、编码、联系人、联系方式与状态，平台预置「测试租户」（`test_tenant`）；
- **角色** — 权限的载体，权限全部授予角色，再把角色关联到用户；一个用户可以拥有多个角色的权限叠加。

## 四、授权操作步骤

#### 1. 维护租户与用户

在「用户角色 → 租户」新建租户；在「用户」中新建用户并指定其所属租户（与用户一一对应），人员变动时在租户上完成移交。

#### 2. 分配菜单权限

进入「权限管理 → 菜单权限」，批量选择角色与菜单权限项，决定其能进入哪些功能模块。

#### 3. 分配项目权限

在「项目权限」中批量选择角色与项目，并按角色设定项目访问级别（可读 / 可编辑 / 完全控制）。

#### 4. 分配文件权限

在「文件权限」中选择存储配置与数据文件路径，开启递归后对其子路径一并生效，控制数据文件的可读 / 读写 / 完全控制。

#### 5. 分配库表权限

在「库表权限」中选择数据源 → 库 → 表，设定权限范围与数据安全约束后授予角色。这是**数据侧最细的一层授权**。

## 五、库表权限的配置项

库表权限是「数据授权」的核心，可配置以下内容：

| 配置项 | 可选值 / 说明 |
| --- | --- |
| **权限范围** | 整表（默认） / 指定字段 / 指定行，选择字段或行时进入更细粒度的配置 |
| **操作权限** | 查询、新增、更新、删除四项独立开关 |
| **导出权限** | 独立的「导出」开关，未开启时结果集不可导出 |
| **列权限** | 选择字段范围时，逐列勾选可访问的字段清单 |
| **行权限** | 选择行范围时填写行过滤 SQL；前端会校验其为单条比较条件、必须含比较运算符，并拦截危险 SQL 关键字 |
| **数据掩码规则** | 为该表指定脱敏档位，详见「数据安全」 |
| **授权角色** | 可同时授予多个角色，多角色命中时按列取更严格的规则合并 |

## 六、权限如何生效

库表权限不是在结果集上做「查询后过滤」，而是在 **SQL 下发前改写**：

- **行级** — 行过滤条件并入查询的 `WHERE` 子句；
- **列级** — 投影列裁剪为授权字段白名单；
- **fail-close** — 命中约束但无法安全改写时**一律拒绝**查询，宁可查不到也不越权返回；
- **对智能体同源** — 脱敏字段与不可读字段对 AI 助手同样遮蔽，保证「智能体能读到什么」与「人能读到什么」遵循同一套权限。

> [!NOTE]
> 权限由管理员在「系统管理」中直接分配，无需用户申请。预置的「测试项目」与「测试库读写权限」可作为授权的参考样例。
