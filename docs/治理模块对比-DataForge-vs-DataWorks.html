差异分析 · 数据治理

DataForge 与主流数据开发平台在治理模块上的差异

数据集成 · 数据质量 · 资产目录，及相邻治理面（权限 / 敏感数据 / 成本 / 写入合规）

对标对象：阿里云 DataWorks（DQC / 数据集成 / 数据地图）为主要参照，腾讯云 WeData、火山引擎 DataLeap、华为云 DataArts Studio 作横向补证 · 本项目结论均基于两个仓库源码核实（证据见附录）· 对标平台能力按公开资料整理，具体版本与功能以厂商文档为准

结论先行：三个治理模块上的差异，本质不是「功能多少」，而是治理动作发生的位置不同。

主流平台把治理收敛在平台侧一件事上——在平台里配置规则、绑定任务、由平台触发与判定、在平台里看大盘；DataForge 把治理拆到生成期 / 提交期 / 引擎执行期三段，平台自身只做「约束 + 校验 + 沉淀描述」，不内置规则引擎与同步引擎。由此形成三类性质完全不同的差异：取舍（有意不做）、形态不同（目标不同故形态不同）、真实缺口（该补且成本可控）。三类必须分开陈述，不能笼统说成「本平台治理能力较弱」。

一、分析框架：治理动作可以发生在四个位置

同样叫「数据质量治理」，落在不同位置，产品的形态、依赖与效果完全不同。先用这个框架对齐口径，后面的模块差异都能归位。

位置代表做法治理对象生效时刻依赖条件
生成期 DataForge 的三阶段提示词约束 + 编译与 SQL 校验 + 代码头参数声明 代码与设计文档（规则、口径、依赖、命名） 代码被写出来的当下 智能体必须先拿到准确的业务上下文（库表/指标/血缘/依赖）
提交期 DataForge 的一键上调度（环境单选、生产才注入血缘、编译不通过不得提交、参数落地任务节点） 提交物（Jar / SQL / 工作流定义） 上线动作的闸门处 本地编译闭环 + 平台侧参数与环境的统一约定
引擎执行期 DataForge 的 spark / flink-listener（分析期规则命中即抛异常，写入前阻断） 物理写入动作（表 / 路径） 写入发生之直前 规则以 SparkConf / Flink 配置下发，跨引擎版本适配
平台侧 DataWorks / WeData / DataLeap：规则配置、任务绑定、平台触发、平台判定、大盘、审批、权限 平台内的实体（表、字段、任务、规则、资产条目） 任务运行成功后 / 准入时 / 检索时 数据与作业必须跑在该平台内，元数据由平台采集器纳管

主流平台把上面四行里最重的一块——规则引擎 + 触发 + 判定 + 呈现——做成了产品；DataForge 选择了后三行（生成期/提交期/引擎期）加一个结果台账。这是后面所有差异的总开关。

二、数据集成

2.1 主流平台：一个完整的「数据同步平台」

DataWorks 的数据集成不是「能跑同步任务」，而是一整套连接器 + 资源 + 向导 + 运维的产品。数据集成属于 DataWorks 的核心能力之一，官方口径是 50+ 异构数据源，并提供 DataX 不具备的实时同步能力。

能力维度DataWorks 做法
连接器关系型数据库、大数据存储、NoSQL、消息队列、文件存储、SaaS 应用；通过 Reader / Writer 插件抽象，是 DataX 的超集
同步时效离线（周期性，小时/天级）；实时（捕获 CDC，秒级延迟）
同步范围单表 / 整库（自动建表、单任务多表）/ 分库分表（多表合并写入单表）
数据策略全量 / 增量 / 全增量一体化（离线场景「一次全量 + 周期增量」；实时场景「一次全量 + 实时增量」；准实时场景 Base 表 + Log 表，T+1 合并）
执行资源Serverless 资源组弹性伸缩、按量付费；并发数、限速、脏数据阈值容忍；分布式处理
开发方式可视化向导模式（点选完成配置）+ 脚本模式（JSON 高级配置）+ DI Agent（自然语言对话建任务、智能诊断、周期巡检）
运维离线同步融入 DAG 工作流，复用调度与运维；监控与告警；WeData 另在实时链路提供数据对账（入库即比对源表与目标表差异）
网络公网 / VPC / 高速通道 / CEN，支持混合云与本地 IDC；白名单配置
语义保证仅 at-least-once，不提供 exactly-once；批量异常时回滚取决于目标端是否支持事务，数据集成本身不提供事务
计费资源组费用 + 调度费用 + 公网流量费用

2.2 DataForge：不自研同步引擎，把同步交回集群既有组件

本项目没有数据集成模块。服务端 Java 全仓检索 datax / seatunnel 零命中，桌面端也只在调度任务类型清单里出现「数据集成」这个分类：

src/types/dolphinscheduler.ts — TASK_CATEGORIES 中 { id: 'dataIntegration', label: '数据集成', tasks: ['DATAX','SEATUNNEL','SQOOP','CHUNJUN','DATASYNC'] }

含义很清楚：这些同步任务的定义与执行是 DolphinScheduler 及其底层工具的事，DataForge 提供的是「能在 DAG 里编排它们」以及「一键把开发环境写好的东西提交成这些节点」。

本项目在数据接入上实际有两条路径：

  • 编排路径（配置化，但不是本平台的配置）：在调度管理里编排 DATAX / SEATUNNEL / SQOOP 等同步任务节点，连接器、字段映射、脏数据策略全部由 DS 与底层工具承担。
  • 编码路径（本平台的主路径）：用开发环境写 SQL / Spark / Flink 程序做同步（服务端 13 种数据源、JDBC / Kyuubi / Spark / Flink / HBase / Doris 多执行策略），即「写程序同步」而非「配向导同步」。

值得单独指出的一点：同步链路的血缘是被接上的——生产环境提交的任务由唯一拼装处注入 OpenLineage 参数，同步/计算作业的血缘事件自动进 Marquez。这与主流平台「整库同步自动建血缘」机制不同，但达到的效果可比。

2.3 逐项对照

能力项主流平台（DataWorks / WeData）DataForge差异性质

判定：数据集成在 DataForge 的定位里不是「治理模块」，而是「被编排的资源」。平台不承接数据搬运动作本身，只承接编排、提交与血缘。因此拿「数据集成完整度」来评价本项目，评价对象本身就错位了——真正受影响的是首次接入的工程量（每个源都要工程师去 DS 里手工配置），不是日常治理能力的缺失。

三、数据质量

3.1 主流平台：规则模板 → 监控规则 → 质量监控 → 强弱规则 四件套

DataWorks 数据质量（DQC）的实体链是闭合的，每一环都是平台内的一个配置对象：

环节说明
规则模板定义「如何检查」。内置丰富模板（表行数、字段唯一值个数等），并支持自建模板库统一管理
监控规则模板的具体应用：为某张表的某个字段应用模板并配置阈值。校验器覆盖固定值比较、1/7/30 天平均值波动、周期比较、方差波动、与固定值比较等，并可指定趋势（上升 up / 下降 down / 绝对值 abs）
质量监控执行计划：把一个或多个监控规则与一个调度任务关联，该任务运行成功后自动触发校验。需指定监控数据范围（分区表达式，如 dt=$[yyyymmdd-1]）
强 / 弱规则强规则校验失败触发告警并把任务实例置为失败，阻塞下游；弱规则仅告警，不影响任务继续执行。强规则会在下游任务运行前执行并计入基线运行时间
自定义规则用对应引擎 SQL 写（离线 MaxCompute SQL、Hologres 用 PostgreSQL、EMR 用 Hive SQL、实时用 Flink SQL），只接受查询语句且限制单行单列输出
呈现数据质量大盘（总览指标、校验状态趋势与分布、TOP 质量问题表及责任人、规则覆盖保障情况）+ 质量资产（规则列表、规则模板库）
配置效率按表（单表）配置与按模板批量配置（对符合条件的多张表批量下规则）
计费按质量规则实例运行数量计费；动态阈值、自定义质量报告、规则模板库等需企业版及以上

横向补证：腾讯云 WeData 内置 200 余种质量规则模板，支持表级与字段级配置，并在实时链路做数据对账；火山引擎 DataLeap 提供 80 余个治理规则覆盖存储/计算/质量/安全，并以历史运行数据建立动态基线检测异常波动。可见这一模块的行业竞争点已经落在「模板数量 + 自动推荐 + 大盘 + 归因」上。

3.2 DataForge：规则的载体是代码，不是平台里的配置行

本项目没有 DQC 式的规则引擎。质量治理分三层，且三层都不在平台侧：

层次载体实际形态
规则知识层 src/hooks/opencode/opencodeInstructions.ts 中的 QUALITY_RULE_SPEC 把规则类型硬规定为 7 类（主键唯一性 / 非空 / … / 口径一致性），要求三阶段使用同一套名称、禁止自造同义词。并明确三阶段分工：
S1 业务需求——用业务语言说明需覆盖的规则类型与可接受偏差；
S2 数仓设计——为每张新建表选择规则类型，定义规则名、校验对象、阈值与处置方式；
S3 数据开发——把设计定义的规则实现为独立的质量校验任务，挂在处理任务下游
执行层 AI 生成的校验程序 「质量校验任务与数据处理任务分离，单独成文件并挂在处理任务的下游」，校验输出须可定位（规则名、校验对象、阈值、实际值、是否通过），不通过时阻断下游或告警并输出异常明细。没有强/弱规则配置项——阻断下游靠 DAG 位置实现
结果层 dataforge-server quality 模块 只有一个实体：data_quality_check_result（数据源 / 库 / 表 / 检查项 checkItem / 检查时间 / 检查记录数 / 未通过记录数 / 未通过明细 JSON）。接口为 /quality/check-result 的分页查询、详情、增删改，以及 /statistics/fail（按表 + 日期 + 检查项聚合未通过记录数）

已核实的现状缺口（写文档时按此陈述，勿凭印象）

  • 服务端 quality 模块没有规则定义表、没有规则与调度任务的绑定关系、没有质量大盘——它是一本结果台账，不是规则引擎。
  • 桌面端前端没有任何界面消费该接口（全量检索 src/，仅 opencodeInstructions.ts 命中「数据质量」，无 check-result 调用）。
  • 智能体侧 6 个工具组（compile / indicator-query / knowledge-document / lineage / metadata-agent / sql-validate）中没有质量结果上报工具。
  • ⇒ 结论：这本台账在当前两个仓库里既没有写入方，也没有读取方（接口齐备，通路未接）。这是三个模块中最容易补、收益最直接的一处。

3.3 差异与含义

对比项主流平台DataForge含义
规则的表达载体平台里的配置行（模板 + 阈值 + 分区表达式）代码仓库里的程序（校验任务独立成文件）形态不同代码可 review、可版本化、可随表一同演进，能表达平台 SQL 规则表达不了的东西（如跨表口径一致性）；代价是没有统一台账
触发方式任务运行成功后平台自动触发其关联规则校验任务作为 DAG 节点被调度效果相近；差别在于主流平台能对未接入调度的表做周期巡检，本平台不能
判定与阻断强规则置任务失败并阻塞下游；弱规则仅告警校验任务失败 → DAG 下游不跑（等价于强规则）；无弱规则档位形态不同缺少「只告警不阻断」的中间档
规则覆盖度大盘给出规则覆盖保障情况、TOP 问题表与责任人无覆盖度统计、无大盘真实缺口
规则模板复用模板库 + 按模板批量下规则靠提示词的「7 类规则类型」保证术语一致，靠 AI 复用同构实现形态不同一致性由规范而非模板库保证

判定：表达力不弱，可观测性弱。本项目缺的不是「能不能定义规则」，而是「规则定义在哪、覆盖了哪些表、最近跑得怎么样」。最省的补法是补规则台账 + 覆盖度 + 结果看板，而不应该去补一个规则引擎——那会与「代码即规则」的模式直接打架，并制造两套并存的规则来源。

4.2 DataForge：元数据随 DDL 增量沉淀，先喂智能体，后给人看

（1）元数据入口是 DDL 驱动，不是定时采集器。MetadataSyncService.syncSingleTableMetadata 在代码执行产生建表/改表动作时增量同步单张表元数据，DROP 操作直接删除本地元数据；另有 /metadata/annotation-gaps 输出未标注表 / 字段清单，同步失败写审计日志并打 [METADATA-SYNC-ALERT] ERROR 日志。

这条路径的治理含义与主流平台不同：平台纳管的范围等于「本平台跑过的 DDL」，而不是「集群里存在的一切对象」。既有的历史表需要另行纳入。

（2）元数据模型已经是「可治理」的粒度，不只是名字和注释。

实体已沉淀字段（节选）
table_metadata数据源 / 存储引擎 / catalog / 库 / 表 / 表类型 / 表注释 / 建表与最后修改时间 / 分区列 / 存储格式 / 压缩 / location / 行数 rowCount / 大小 sizeBytes / 冷热保留天数 hotDays·coldDays·keepDays / 表与字段双指纹 / 同步时间
column_metadata字段名 / 类型 / 注释 / 是否分区 / 是否主键 / 序号 / 可空 / 默认值
indicator + indicator_field主题域 topic / 编码 code / 名称 / 业务定义 businessDefinition / 计算表达式 calcExpr / 默认过滤 / 业务与技术责任人 / 刷新周期 / 可见性；字段级绑定到 数据源 · 库 · 表 · 字段 —— 实际构成一份「指标口径目录」

（3）有两条消费通道，优先服务智能体。

  • 对人：桌面端「数据探索」的库表浏览（数据源 → 库 → 表树，支持按表名或注释关键字过滤）+ 表详情（字段结构、描述编辑）；血缘在独立的血缘视图（Marquez）中呈现，与目录分离。
  • 对智能体：/metadata/agent/{tables, table-detail, search, indicators}。注意 search 的实现是 tableName 与 tableComment 的 LIKE 匹配（非向量检索）；table-detail 会带上字段的脱敏标记 maskingType——脱敏字段对智能体同样不可读。这让「智能体能读到什么」与「人能读到什么」遵循同一套权限。

已核实的缺口清单

无类目 / 标签体系 · 无专辑 · 无热度（访问次数、最近访问、读取次数）· 无样本数据预览 · 无存储量总览与趋势 · 无变更影响通知 · 表级没有业务责任人字段（table_metadata 只有 createBy，owner 只存在于 indicator 上）

4.3 差异与含义

主流数据地图与 DataForge 目录的差别，不是能力项的多少，而是价值函数不同：

对比项主流平台：面向人的找数入口DataForge：面向智能体的上下文供给
要解决的问题「我要的那个数在哪张表里」——缩短找数时间「智能体生成代码前，是否拿到了准确的表/字段/指标定义」——提高生成准确率
因此必需检索强、类目清、热度排序、专辑推荐、样本预览描述准确、口径唯一、缺口可见（未标注清单）、结构化可被程序消费
因此不必需—热度与推荐排序、专辑、样本预览（智能体不需要「猜你会用」）
共同必需描述完整度、血缘、责任人、权限可见性

判定：这是目标不同导致的形态不同，不是能力落后。但要说清两点：一是热度、类目、预览这类「给人用」的体验对新人上手确实是缺口，不能因为「智能体不需要」就一概否认；二是表级责任人缺失是共同必需项里的缺项，主流平台把 owner 作为目录的一等属性（用于筛选与问题归因），本项目目前只在指标上有，这一条建议补。

五、相邻治理面（「等」的部分）

维度主流平台DataForge性质
权限与脱敏 云侧 RAM 访问控制 + 角色认证 + 数据脱敏；配套敏感数据识别与分级分类（数据保护伞体系） 角色—资源三级授权；行 / 列级权限在 SQL 下发前改写（行条件并入 WHERE、投影列裁剪为白名单），命中约束但无法安全改写时一律拒绝；列级脱敏支持 full / 身份证 / 手机 / 邮箱 / 部分等档位，多角色命中时按列取更严格的规则合并（full 完全不可读，有脱敏规则的字段不允许写入），并且对智能体同样遮蔽 位置更靠前「下发前改写 + fail-close」比多数平台的「查询后过滤」更靠前；脱敏对智能体一并生效也是少见的
敏感数据识别 规则 / 模型自动识别 + 分级分类标签，识别结果驱动脱敏与权限策略 无自动识别引擎、无分级分类标签；脱敏规则由人工在权限配置中指定 真实缺口人工配即意味着「不知道的地方不会被保护」
成本与生命周期 存储总览、趋势、Top 表；DataLeap 以 80+ 治理规则覆盖存储/计算/质量/安全并做基线异常检测 元数据里已经采集 rowCount / sizeBytes / hotDays / coldDays / keepDays，但只服务「数据价值评估」（规划中），没有治理规则引擎、没有展示面 真实缺口数据已在手，只差规则与呈现——投入产出比高
写入合规 平台侧权限 + 审批 + 编码期 AI 深度检查（DataWorks 已在 SQL 节点做事前检查） 可选装 spark / flink-listener：解析执行计划提取写入的库表或路径，按正则/模式规则判定，命中禁止规则时在分析（Analysis）阶段抛异常、写入发生前阻断；跨 Spark 2.4 / 3.1 / 4.1 适配，规则经 SparkConf 下发 独有位置主流平台无对应物；且它不依赖平台，能覆盖绕过平台直接提交到集群的作业
元数据缺口可见性 一般靠「待完善表」类筛选能力 /metadata/annotation-gaps 直接输出未标注表 / 字段清单；同步失败写入审计日志（METADATA_SYNC_FAILED）并打 ERROR 日志 形态不同相当，且本平台把「缺口」做成了可被智能体读取的接口
知识检索 普遍叠加语义层 / 向量检索（WeData 的 Unity Semantics 通过 MCP 做自然语言查询转换） 知识库为关键字匹配（title/content 的 LIKE），无向量库、无 embedding、无 rerank；已列为规划项 真实缺口已明确规划

六、汇总矩阵与三条本质差异

6.1 三个模块的差异性质一览

模块主流平台范式DataForge 范式性质归类

缺口CDC 向导、整库 / 分库分表、数据对账

6.2 三条本质差异

  1. 治理位置前移，且分散到三段。主流平台把治理集中在平台侧一件事上；本项目把它拆成生成期（提示词约束 + 编译与 SQL 校验）、提交期（环境闸门、生产才注入血缘、参数落地任务节点）、引擎执行期（listener 分析期阻断）三段，事后只留一本结果台账。代价是缺少统一视图（没有大盘把三段的效果汇总起来），收益是治理不依赖平台——绕过平台提交到集群的作业同样被引擎侧规则约束。
  2. 治理对象从「平台内的实体」变成「代码与提交物」。在主流平台里，表、字段、任务、规则都是平台中的配置对象；在本项目里，质量规则与同步逻辑首先是代码，平台只提供约束、校验与描述沉淀。这解释了为什么「规则台账」在本项目缺失得更明显——因为本项目的规则本来就不住在平台里。
  3. 治理成果的第一消费者从「人」变成「智能体」。目录、口径、血缘、任务依赖在本项目里先保证机器可读（结构化 + 权限一致 + 缺口可见），再考虑人的浏览体验。这不是把「给人用」的模块做差了，而是把同一批信息的服务顺序调换了；因此凡是「只服务于人的发现效率」的能力（热度、专辑、类目、样本预览）在本项目里天然缺位，而「描述准确度」的比重被显著抬高。

七、边界声明（可直接引用到文档）

取舍有意不做，不构成缺口

连接器广度与同步引擎自研 · 托管弹性与资源组计费 · CDC 实时同步的可视化向导 · 整库 / 分库分表一键迁移 · 数据对账 · 脏数据阈值策略 · 质量规则的平台化引擎 · 资产类目与专辑 · 热度与推荐排序 · 样本数据预览。这些能力的替代承接方是集群既有组件 + 配套的数据开发与集群运维服务。

形态不同目标不同故形态不同，无需对齐

质量的规则载体（代码 vs 配置行）· 质量的触发方式（DAG 节点 vs 平台自动触发）· 目录的第一消费者（智能体 vs 人）· 血缘的采集机制（OpenLineage 事件 vs 平台内解析）· 元数据纳管范围（本平台跑过的 DDL vs 采集器扫描全域）。

真实缺口可补，且投入产出比从高到低

  1. 质量结果通路未接通：结果表已建、接口齐备，但智能体侧没有上报工具、前端没有读取界面。补「一个上报工具 + 一个质量看板」即可闭环。
  2. 质量规则台账与覆盖度：当前无法回答「哪些表配了规则、覆盖了哪几类」。建议在不引入规则引擎的前提下，把规则以元数据形式登记（表 + 字段 + 规则类型 + 阈值），覆盖度即可统计。
  3. 表的业务责任人字段：目录与质量归因共同必需，目前只在指标上存在。
  4. 敏感数据自动识别与分级分类：当前脱敏规则全靠人工指定，「未被识别的字段等于未被保护」。
  5. 存储成本维度只采集未呈现：rowCount / sizeBytes / 冷热保留天数已在元数据中，补展示与规则即可支撑成本治理。
  6. 知识检索增强（向量检索）：已列为规划项，现状为关键字匹配。
