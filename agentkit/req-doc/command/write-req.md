# 任务

为用户提交的业务编写一份开发需求文档，严格遵循《需求文档内容规范》，输出到 `docs/{业务名称}_开发需求.md`。

业务名称：`$ARGUMENTS`

如果 `$ARGUMENTS` 为空，先向用户确认业务名称，不要自己猜。

# 执行流程

按 `doc-orchestrator` 的 S0→S1→S2→S3 执行，不要跳步：

1. **S0**：`extract-context({ businessName })`。
2. **S1**：派发 `chapter-writer` 依次完成第 1、2、4、5、6、7、8、9 章；派发 `metrics-writer` 完成第 3 章（每批 ≤ 5 条）。
3. **S2**：`validate-json` → `check-logic-graph` → `logic-reviewer`；有 error/blocker 回退到对应章节。
4. **S3**：`finalize-doc`（先 `dryRun=true` 预检，再正式写盘）。

# 必须遵守的规范要点

- 文档共 **9 章**，第 7 章是「质量检查要求」，没有「敏感数据说明」章节。
- 只有第 3 章标题强制带编号，写作 `## 3. 数据指标`；其余章节渲染时也带编号，但解析按标题文字匹配。
- 第 3 章表格必须且仅有 7 列：指标名称、主题域、业务定义、计算口径、过滤条件、下钻维度、应用场景。
- 「刷新周期与时效口径」「数据质量规则类型」两处外部引用用户未给出枚举，**不得虚构取值**，写占位并标注「需用户提供该章节内容」。
- 目标文档已存在时增量合并：不得覆盖已有内容；`E16_MERGE_CONFLICT` 必须问用户，不得自行决定。

# 输出

结束时只回报：

- 文档路径与文件大小
- 指标条数
- 未解决的 major/minor 审查结论数
- 待用户确认的问题数（第 9 章）
- 若未完成：卡在哪一步、最后一批错误码原文
