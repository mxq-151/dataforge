## 10:05 S3 提示词：把质检任务粒度定死为「一张被校验表一个质检程序」

用户反馈：智能体生成的质量检查代码全部集中在一个任务里。根因是提示词只说了「质检任务与数据处理任务
分离、独立成文件、挂处理任务下游」，**没定粒度**，模型自行领会成「一个业务域一个大质检程序」——
一个任务挂多个上游、失败域糊在一起、程序名对应不到任何一张表。

改动（`src/hooks/opencode/opencodeInstructions.ts`，7 处）：

1. `QUALITY_RULE_SPEC` 三阶段分工的 S3 条：补「一张被校验表对应一个质检任务，不得合并」。
2. `TASK_SPLITTING_PRINCIPLE`「质量校验独立」条（S2/S3 共享）：补同样的粒度约束，设计端也别把规则堆一起。
3. `PROGRAM_NAMING_CONVENTIONS` 示例补 `dwd_trade_order_check_d.sql`，让 check 命名有样例可抄。
4. S3 工作流程第 6 步：改为「按稽核规则清单里的被校验表逐表拆出质检程序」。
5. **S3「数据质量校验规范」重写**：粒度=一表一程序；归属依据是规则「校验对象」里的库.表（不是规则类型/
   分层/业务域）；跨表对账规则归**左侧主表**所在程序（否则模型会为它单建共享程序）；命名
   `{分层}_{业务域}_{实体描述}_check_{执行周期}`；@依赖 只写产出该表的处理任务，一个处理任务产多表就拆多个
   质检任务而不是堆上游；汇报逐个程序列出校验的表与规则条数。
6. 回传规范里「不得为回传单独新建调度节点」补一句澄清：**这条只是不给回传单开节点，不是把多张表合并进
   一个程序** —— 这句本身也是模型合并的一个诱因。
7. S2 侧：规则清单要求**按库.表分组连续书写**，并新增「表格必须是一张连续表格，行间不得插小标题/分组说明/
   空行」——`qualityRuleImport.ts::parseQualityRulesFromDesignDoc` 遇首个非 `|` 行即 `break`，
   行间插小标题会把其后的规则整段漏读（这是既有解析器的真实边界，以前没写进提示词）。

配套单测：`opencodeInstructions.test.ts` 新增 `describe('质检任务粒度 — 一张被校验表一个质检程序')`
6 例，锁住粒度文案、命名模板、@依赖 挂载方式、自检项、S2/S3 一致性、连续表格约束。

验证：`tsc --noEmit` 无输出；全量 vitest **65 文件 / 1096 例全过**（基线 1090 + 新增 6）。

单独成文件并挂在处理任务的下游」原文（该句故意原样保留未改），文档未提及新的粒度约束 —— 若该对比文档要

## 10:23 提示词：把「数据分类分级」的档位与分类枚举写死

用户要求：提示词里的分级分类要规定好有几个级别。现行提示词只给了 `cla:用户信息-一般` 一个例子，
没有枚举 —— 模型每次自造档位（"机密/内部/公开"、"一般1级"），三份产物对不上，也无从统计分级分布。

**先查证国标**（GB/T 43697-2024《数据安全技术 数据分类分级规则》，2024-10-01 实施）：
分级**只有三档** 核心数据 / 重要数据 / 一般数据，**没有小级**（一般数据细分 1~4 级是金融行业标准
JR/T 0197-2020 的做法，不是这份国标）。且国标原文明确「**仅影响组织自身或公民个体的数据一般不作为
重要数据**」⇒ 单条个人信息（手机号/身份证）应归**一般数据**。

**由此发现现行提示词有一处实质错误**：旧口径写「敏感字段分类分级不得低于"重要"」。按国标，把个人信息抬成
重要数据会触发**重要数据目录报备与风险评估的法定义务** —— 是抬高合规成本而非提高安全性。已废除该口径。

三问确认后定稿（用户选择）：三档分级 / 敏感字段=一般数据+强制脱敏 / 分类固定 5 类（+其他 兜底）。

改动（`src/hooks/opencode/opencodeInstructions.ts`）：

1. 新增共享常量 `CLASSIFICATION_SPEC`（口径唯一来源）：三档分级及判据；分类六类枚举
   `个人信息 / 业务数据 / 经营数据 / 公共数据 / 运维数据 / 其他`；写法 `cla:{分类}-{分级}`
   （表级写表注释尾部、字段级写字段注释尾部，一表/一字段只打一个标记）；个人信息定位（易错点）；
   三阶段分工。**注入 S1 / S2 / S3 三份提示词**。
2. `SECURITY_PRINCIPLES` 敏感数据链路条：**不写跨章节引用**，自带「分级固定三档，个人信息默认一般数据
   但必须脱敏」——因为超管/数据分析师这两份提示词也复用该常量，却没有 `CLASSIFICATION_SPEC` 章节，
   写「见"数据分类分级口径"」会指向不存在的章节。
3. S2 DDL 规范：`cla:xxx` → `cla:{分类}-{分级}`；删掉「敏感字段不得低于重要」，改为「据实填写，**不得靠
   抬高分级代替脱敏**」。
4. S2 设计文档 3「分层库表设计」补「分类分级（cla: 标记）与敏感字段的脱敏/加密要求」——以前脱敏建议
   没有指定章节承载，S3 无从定位。
5. S1 职责条与需求文档第 8 章：数据类别改为取自分类枚举。
6. 自检：S2 加「分类分级合规」（未自造档位、未把个人信息抬成重要数据），S3 加「分类分级落地」。
7. S3 敏感字段条改为按 `cla:` 标记与脱敏建议实现。

配套单测：`describe('数据分类分级口径 — 三档分级 + 六类分类')` 7 例（含 3 例 `it.each(STAGES)`
三方一致性），并显式断言 S2 **不含**旧的 `不得低于"重要"`，以及旁路角色提示词引用不到的口径章节不会出现。

验证：`tsc --noEmit` 无输出；全量 vitest **65 文件 / 1103 例全过**。

与现状不符 —— DDL 注释里是有 `cla:` 标记的（只是无自动识别 + 无法解析统计）。
