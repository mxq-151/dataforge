# 2026-09-06 工作日志

## 智能体对话模块性能优化（长回复卡顿）

### 目标
智能体回复内容较长时界面不流畅，需优化 AI 对话模块，且不影响其他模块（尤其 Monaco 代码编辑框），并给出前后性能对比。

### 基准方案（新增，可复用）
- 免登录基准页 `src/views/ai-bench/`（`bench.html` 独立入口 `bench-main.tsx`），跑在真实生产代码路径上：合成 SSE 事件喂给真实 `useOpencodeEvents` → 真实 `MessageTimeline/TextPartDisplay/PacedMarkdown` 渲染，旁边挂真实 `EditorArea`（Monaco）+ 输入延迟探针。
- CDP 驱动脚本 `scripts/ai-bench.mjs`（Edge headless + ws，采集主线程阻塞/长任务/React Profiler 分树提交/编辑器输入延迟），`--out perf/before.json` / `--after.json`。
- 对比脚本 `scripts/ai-bench-compare.mjs` → `perf/report.md`。
- 关键坑：基准必须用全新浏览器 profile 且每次重跑（ai-bench.mjs 每次 rm profile 再 spawn），避免 HMR/缓存污染；脚本末尾要 `process.exit(0)`（Windows 下 Edge 子进程残留句柄会让 Node 挂起）。

### 优化改动（2 处，均为 AI 子树内部，未碰编辑器链路）
1. `src/components/ai/parts/PacedMarkdown.tsx` — 分块增量渲染：打字机文本拆成「稳定前缀(useMemo 缓存) + 活动尾部(最后一段)」，优先在**空行（段落）边界**重解析稳定前缀（列表/表格/段落整体固化，不拆散），活动尾部超过 1500 字符时退化为换行边界；拆分点避开围栏代码块(`findStableSplit`)。消除长回复下 Markdown 的 O(n²) 重复解析。
2. `src/components/ai/timeline/MessageTimeline.tsx` — 用 `entryByID` Map 替换 `renderRow/getMsgPart/assistantCopyPartID` 里的 O(n) `messages.find`。

### 结果（3 次迭代取中位数，Edge headless，空行边界版）
- medium-8k：AI 提交总耗时 -60%，主线程阻塞 -36%，编辑器输入延迟 p95 -67%。
- long-24k：AI 提交总耗时 -54%，主线程阻塞 -39%，编辑器输入延迟 p95 -50%；Monaco 提交次数 195→194 基本不变（证明未波及）。
- 回归：`vitest run src/components/ai` 212/212 通过（含新增 `parts/PacedMarkdown.test.ts` 的 `findStableSplit` 12 个边界用例）；全量 440 通过（2 个既有失败与本次无关）。

### 结论/经验
- 长回复卡顿的根因是 `PacedMarkdown` 每次打字机步进都对整段文本重新 `ReactMarkdown` 解析（O(n²)），不是 setMessages 频率——`useOpencodeEvents` 里已有 33ms 的 `flushDeltas` 合并刷新 + `partTextAccumDelta` ref 累积。
- 「稳定前缀元素 useMemo + 返回同一 element 引用」能让 React 走 `memoizedProps===pendingProps` 提前 bailout，跳过整段重解析——这是关键技巧。
- 拆分粒度：换行边界（-43%）→ 空行边界 + 活动尾部上限（-54%），空行边界既更快又把列表/表格整体固化（视觉更稳），是更优解。
