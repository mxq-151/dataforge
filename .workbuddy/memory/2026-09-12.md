## 诊断：「为什么每次重跑测试都这么慢」（上午，诊断驱动）

用户提问测试耗时异常。**结论：与项目代码、vitest 配置、jsdom 都无关**，
根因是 **WorkBuddy agent shell 注入的 `NODE_OPTIONS` shim**。

### 事实链
1. 环境注入 `NODE_OPTIONS=--require="/Applications/WorkBuddy.app/.../cli/vendor/shim/node-language-shim.cjs"`。
2. 该 shim 见到 `CODEBUDDY_BROKERED_FS_HOOK_ENABLED` / `CODEBUDDY_SAFE_DELETE_SANDBOX` 已设，
   进而 `require('./node-brokered-fs-shim.cjs')`。
3. 该 shim 第 935–936 行 patch：`fs.openSync`、`fs.readFileSync`。
   `wrappedReadFileSync` = `tryBrokerFileTokenSync('read', p)` **+** 原生读；
   而 `tryBrokerFileTokenSync` 调 `nativeAddon.requestBrokerSync(CODEBUDDY_SANDBOX_BROKER_IPC_ADDRESS, …)`
   —— **每次读取文件都是一次同步 IPC 往返**。
4. Node 加载模块 = 海量 `readFileSync`。jsdom 有 **788 个 .js 文件**，
   96s ÷ 788 ≈ **~120ms/文件**，量级与一次 IPC 往返吻合。

### 量化对照（同一台机、同一命令）
| 对象 | 保留 shim | `env -u NODE_OPTIONS` |
|---|---|---|
| `node -e ""` | 0.039s | — |
| `import 'jsdom'` | **94.29s** | **0.539s**（175×） |
| 单测试文件 `programLayout.test.ts` | 121.32s / wall 2:56 | **792ms / wall 1.58s**（111×） |
| 全量 `vitest run` | **>10min 未跑完（中止）** | **8.84s / 34 文件 / 613 用例全通过** |

拆项（单文件）：environment 95.77s→538ms、setup 16.76s→123ms、CPU 占用 1%→95%。
**CPU 1% 是关键指纹**——纯等待，非计算。

### 关键纠正
- 记忆里长期记的「jsdom 初始化 ~88s」「textmateFix.test.ts 必然超时、应忽略」**都是 shim 的副作用**，
  不是 jsdom 的问题、也不是测试本身的问题。09-11 那条结论**作废**。
- 耗时与"包文件数"近似线性（ws 15 文件 2.59s；jsdom 788 文件 96s），
  而 `typescript` 虽有 112 文件却只 0.19s —— 因为实际只加载入口单文件，**决定因素是实际加载的模块数**。

### 处理方式
- 跑 node 工具链（vitest / vite build / tsc）时：**`env -u NODE_OPTIONS <cmd>`**。
- 只关 fs 读取 hook（保留 safe-delete 保护）可等价加速：
  `CODEBUDDY_BROKERED_FS_HOOK_ENABLED=0 CODEBUDDY_SAFE_DELETE_SANDBOX=0 <cmd>`。
- 注意：用户自己在 Terminal 跑通常没有这个注入，**减慢只发生在 agent 代跑的 shell 里**。

### 诊断方法论（可复用）
怀疑"无故变慢"时按阶梯二分，不要凭猜测：
`空脚本(0.04s) → 只 import 大包(94s) → 加 process.exit(0)(仍 97s)` ⇒ 定位到 **import 阶段**，
而非退出/GC；再用 `env -u <可疑变量>` 单变量对照，即可锁定。
本次正是靠 `import 后立刻打印耗时` + `process.exit(0)` 排除"退出阶段卡住"这一误导性假设。
- jsdom 环境初始化本机耗时 90~180s，且 `transform/import` 也随负载涨到 150s；逐文件 `--maxWorkers=1` 跑。
