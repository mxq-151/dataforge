## 真因已证实 + 已修复（用户用探针复现，铁证）
渲染进程日志（`/tmp/dataforge-renderer.log`，00:35 那次）：
```
00:35:16.070 connected working dir: .../admin/individual            ← 启动连基础目录
00:35:27.905 connected working dir: .../admin/individual/1791736527892  ← 切到会话目录 ✅
```

**会话目录那次连接从未产生自己的订阅**（无 `directory=...1791736527892` 的订阅行）——基础目录客户端在 13ms 后覆盖了 `clientRef`，React 最终只用基础目录提交渲染，订阅 effect 于是订阅到基础目录。对照：同时段开发助手（`dev-assistant`）订阅正常、`message.updated` tokens 正常收到 ⇒ 只有数据探索错。
**真因**：`App.tsx:131-138` `DataExploreClientSlot` 的自动启动 effect 依赖 `backend.connected`；`setWorkingDirectory` 内部 `doDisconnect()` 把 connected 瞬时置 false，该 effect **在切换完成之后**（实测 13ms）才跑到，调用**无 cwd** 的 `start()`，而 `start()` 的目标写死为模块基础目录 `individual/` ⇒ 覆盖刚切到的会话目录。
**上一版修复（b8b2ee5）为什么没用**：它加的 `switchingDirRef` 闸门只在「切换进行中」生效，而那一枪打在**切换完成之后**（闸门已释放）；测试又是并发调用 `start()` 的，恰好落在闸门有效窗口内 ⇒ 测试通过但真实链路照样失败。**测试时序错了，不是修复方向错了。**

**本次修复**（`src/hooks/opencode/useOpencodeClient.tsx`，未经 commit）：
1. `start()` **语义守卫**：`if (!cwd && clientRef.current && connected) return;` —— 无 cwd 的 `start()` 只表示「确保已连接」，不得改写已确定的目录。条件含 `connected` 是为了不挡住 sidecar 崩溃后的重连（那时 connected=false 但 clientRef 仍在）。
2. `setWorkingDirectory` **全程持有闸门**：新增 `startBusyDepthRef` 计数 + `beginStartBusy()` 工厂（`start()` 与目录切换共用，计数归零才放开）。必须在 `doDisconnect()` 之前**同步**置位，使 `connected=false` 与 `starting=true` 落在同一次提交里——这样那个 effect 闭包里读到 starting=true，条件不成立。
3. 订阅 effect 依赖 `[connected, subscribe]` → `[connected, client, currentDirectory, subscribe]`（用 `client` state 与 `currentDirectory`，删掉只为它服务的 `directoryRef`）。
4. 加 `[agent-client]` 日志：`start() 跳过` / `切换工作目录开始/完成`。

**验证**：新增 `src/hooks/opencode/useOpencodeClient.dataExploreDir.test.tsx`（4 例，**关键是把 `start()` 放在 `await setWorkingDirectory` 之后**，另加「切换进行中」时序）。反向验证：撤掉修复 ⇒ **4/4 全失败**，失败信息正是 `currentDirectory` 停在 `individual` 且只有 1 条事件流；修复在位 ⇒ 4/4 通过。`tsc --noEmit` 通过；全量 **72 文件 / 1157 例全绿**。
