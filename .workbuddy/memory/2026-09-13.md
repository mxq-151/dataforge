## 上下文使用量上限错误（181.7k / 128.0k = 142%）+ 悬停提示慢

**现象**：智能体对话头部进度条分母是 128.0k，超 100%；鼠标悬停要等很久才出提示。
模型是 `deepseek/deepseek-flash`（显示名 **DeepSeek V4.1 Flash**，即界面上的 "ds-v4.1"）。

**根因（两层，缺一不可）**
1. `getHardcodedContextLimit('deepseek-flash')` 落进泛化 `includes('deepseek')` 分支 → 128_000。
   旧表只认 `deepseek-v4` 前缀，而 `deepseek-flash` 名字里既没有 v3 也没有 v4。
2. API 本可纠正（sidecar `/api/model` 对 `deepseek/deepseek-flash` 返回
   `limit.context = 1000000`），但调用方 `c.v2.model.list()` **只查一次**、且
   **不带 location**；该接口按 location 惰性初始化实例，冷实例首次返回 `200 + data: []`，
   于是静默回落到那张错的硬编码表。

**实测证据**（sidecar 在 127.0.0.1:4096，app 关闭即消失）
- `GET /config` → `"model":"deepseek/deepseek-flash"`（确认真实 modelID）
- `GET /provider`、`GET /api/model?location[directory]=…` → deepseek 四个模型的
  `limit.context` 均为 1_000_000（models.dev 官方口径也是 1e6，不是 1MiB=1048576）
- SDK 复现：`createOpencodeClient({directory})` 后 `v2.model.list()` 在**冷目录**返回
  `Array.isArray(body.data)===true` 但 `length===0`；同一目录几秒后再查变 96 条。
  传不存在的目录 → 500（`PlatformError: NotFound: FileSystem.realPath`，见
  `~/.local/share/opencode/log/opencode.log`）
- SDK 实际请求 URL：`/api/model?location%5Bdirectory%5D=…&directory=…`（两种写法服务端都认）

**改了什么**
- 新增纯函数 `src/hooks/opencode/modelContextLimit.ts`：`getHardcodedContextLimit`（V4 家族
  显式包含 `deepseek-flash`，值改 **1_000_000**，不再用 1_048_576 以免通过 Math.max 虚高分母）、
  `resolveContextLimit(apiLimit, modelID)`（取较大值做下限保护）、`DEFAULT_CONTEXT_LIMIT`=128k。
- `useOpencodeClient.tsx`：删掉内联表改 import；`fetchModelContextLimit` 增加
  `dir` 与 `isCancelled` 参数，`model.list(dir ? {location:{directory:dir}} : undefined)`，
  按 **0 / 800 / 1600 / 3200ms** 重试 4 次（冷实例自愈窗口），每次尝试都写日志；
  自增 `limitFetchSeqRef` 保证「最后一次调用生效」，effect 依赖补 `currentDirectory`。
- `ContextUsageBar.tsx`：原生 `title` → 自定义 tooltip（`mouseenter` **零延迟**弹出，
  `position: fixed` 由 `getBoundingClientRect` 定位，避开 `.ai-panel{overflow:hidden}` 裁剪；
  resize/scroll 时关闭；保留 `aria-label` 承载同样文案）。

**验证**：`tsc --noEmit` 零错误；全量 `vitest run` **44 文件 / 756 例全过**
（新增 modelContextLimit 10 例 + ContextUsageBar 8 例）。

**待用户确认**：重启应用后进度条应为 `/ 1.00M`，日志面板应出现
`模型 deepseek/deepseek-flash contextLimit=1000000（API=1000000, 硬编码=1000000, 第 1 次查询）`。
注：其它带 `title=` 的控件（如「压缩」按钮）仍是原生提示，存在同样的延迟，未在本轮改动。

## 事故取证：test_project 工作区被清空（AI 面板「回滚到此消息」是真凶）

**现场**：`code/test_project/src/test_project/`（warehouse 链接工作树）只剩 83B 的 `.git`，
目录 mtime = 10:57；`git status --porcelain` 恰好 **71 条 ` D `**（= 分支 `dataforge/test_project`
全部 tracked 文件：olist/ 38 + ads/ 29 + 4）；`.metals/.bloop/target` 在树外故幸免。

**定责（三条独立证据）**
1. opencode sidecar 无辜：`~/.local/share/opencode/log/opencode.log` 在 10:57:50–10:58:30 只有
   `message=cancel`（abort）+ 重启 loop；全库检索 `clean`/`reset --hard`/`worktree remove`/
   `snapshot`/`restore` **零命中**；`message=tracking|restore|reverting|initialized` 自 08-26 起
   从未出现 ⇒ opencode 的 git 快照链在这套部署里根本没启用。
2. 删除者是渲染层：`DevAssistantView.tsx:507 handleRollback()`——用「发消息时客户端在内存拍的
   整目录内容快照」当权威清单，`deleteNode`（→ `fs.remove(recursive)`，无回收站）删除差集里的
   所有文件与目录。`.git` 因 `useFileSystem.ts:405` 过滤 `.` 开头条目而不在文件树里 ⇒ **「只剩
   .git」是这条路径的指纹**。
3. 触发链路：`UserMessageDisplay.tsx:143`「回滚到此消息」按钮 → `AIPanel.tsx:193` →
   `handleRollback` 回填输入框 + 客户端删文件 + `session.revert`；下一次 prompt 触发 opencode
   `SessionRevert.cleanup` 删消息 —— DB `event` 表 `message.removed.1` × 9（seq 122–130）+
   `part` 表该会话只剩 10:58:13 之后的记录，与「先 abort(10:57:54)、再点回滚、再重发(10:58:13)」
   完全吻合（重发文本 = 首条消息 + 「olist中的」= 回填被编辑）。

**护栏缺口**：`if (snapshot)` 对空对象 `{}` 为真；无「快照覆盖率=0 就中止」判断；`saveFile` 只
还原快照项，所以「什么都没还原 + 全删」= 快照集合零命中（文件树未装载 / rootPath 与 projectCwd
不一致两种成因）。另：`git.ts:560` 的 `isInsideWorkTree` 分支让 `restoreMissingWorktreeFiles`
（`git checkout -- .`）在工作树已注册时永不执行 → 启动时不会自愈被清空的 tracked 文件。

**恢复边界**：`git diff --cached` 为空、reflog 无 reset ⇒ 71 个文件可 `git checkout -- .` 无损
恢复（无需依赖会话库 write 记录）；09-11 17:04 之后未提交的改动才需从 `part.state.input.content`
（olist 41 / ads 33 个 filePath 有 write 记录）或 `build/test_project/<ts>/src/test_project` 比对补。

**取证工具（下次复用）**：`event` 表（aggregate_id=session_id，type 含 message.removed.1）是时间线
真相源；`part` 表读 bash 输出可复原「当时磁盘长什么样」；`sqlite3 -readonly "file:<db>?mode=ro"`，
注意 `strftime('%s',...)` 按 UTC 解释、需自行换算时区。渲染层日志（`[DA][debug]`/`[FS][debug]`/

## 处置：恢复 + 加固（同日下午，「按建议处理」）

**恢复**：执行 `git -C <wt> checkout -- .` 时被陈旧 `index.lock` 挡住（0 字节、mtime 11:18、
`ps` 无 git 进程、`lsof` 无持有者）⇒ 判断为只读 git 诊断被中断的残留，**`mv` 到
`.workbuddy/recovery/index.lock.stale-112420.bak` 保留证据**（不用 `rm`），随后恢复成功：
**71/71 文件全部回来**，`git status` 归零（olist 40 + ads 31，与分支 tracked 数一致）。
审计清单：`.workbuddy/recovery/2026-09-13-worktree-restore.txt`。

**加固**（新增 2 个模块、改动 4 个文件）：
- 新增 `utils/rollbackSafety.ts`：纯函数闸门 `assessRollbackSafety`（4 种拦截码 + 混淆阈值常量）、
  `isMassFileLoss`、`formatTrashStamp`、`uniqueTrashName`。
- 新增 `utils/workspaceTrash.ts`：`ensureTrashIgnored` 把 `.dataforge-trash/` 写进 git `info/exclude`，
  否则 untracked 条目会让 `syncWorktreeWithRemote` 静默跳过、并被 `git add -A` 带进版本库。
- `useFileSystem.ts`：新增 `trashNode`——`rename` 到 `<root>/.dataforge-trash/<stamp>/<原相对路径>`。
- `DevAssistantView.handleRollback`：接闸门；快照结构 `Record<string,string>` → `{root, files}`

  拍照前若文件树为空先 `refreshTree`。顺手修掉「在 `setTabs` updater 内调 `setEditorContent`」

  （全空必恢复；否则 ≥5 个且 ≥50%），并在 `isInsideWorkTree` 分支里**先于** `syncWorktreeWithRemote`
