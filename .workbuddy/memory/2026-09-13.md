## 上下文使用量上限错误（181.7k / 128.0k = 142%）+ 悬停提示慢

**现象**：智能体对话头部进度条分母是 128.0k，超 100%；鼠标悬停要等很久才出提示。
模型是 `deepseek/deepseek-flash`（显示名 **DeepSeek V4.1 Flash**，即界面上的 "ds-v4.1"）。

**根因（两层，缺一不可）**
1. `getHardcodedContextLimit('deepseek-flash')` 落进泛化 `includes('deepseek')` 分支 → 128_000。
   旧表只认 `deepseek-v4` 前缀，而 `deepseek-flash` 名字里既没有 v3 也没有 v4。
2. API 本可纠正（sidecar `/api/model` 对 `deepseek/deepseek-flash` 返回
   `limit.context = 1000000`），但调用方 `c.v2.model.list()` **只查一次**、且
   **不带 location**；该接口按 location 惰性初始化实例，冷实例首次返回 `200 + data: []`，
   于是静默回落到那张错的硬编码表。

**实测证据**（sidecar 在 127.0.0.1:4096，app 关闭即消失）
- `GET /config` → `"model":"deepseek/deepseek-flash"`（确认真实 modelID）

  `limit.context` 均为 1_000_000（models.dev 官方口径也是 1e6，不是 1MiB=1048576）

  `Array.isArray(body.data)===true` 但 `length===0`；同一目录几秒后再查变 96 条。

  `~/.local/share/opencode/log/opencode.log`）

**改了什么**
- 新增纯函数 `src/hooks/opencode/modelContextLimit.ts`：`getHardcodedContextLimit`（V4 家族
  显式包含 `deepseek-flash`，值改 **1_000_000**，不再用 1_048_576 以免通过 Math.max 虚高分母）、
  `resolveContextLimit(apiLimit, modelID)`（取较大值做下限保护）、`DEFAULT_CONTEXT_LIMIT`=128k。

## 回滚加固的复核结论（11:38）

**运行版本判定方法（可复用）**：不要只看 `dist/` 的 mtime，要看 **Electron 是否与 vite dev server 有
ESTABLISHED 连接**：`lsof -nP -iTCP:5173`。本次 Electron(28852) ↔ 127.0.0.1:5173 ESTABLISHED，
而 `dist/` 停在 09-10（未被加载）⇒ 运行的 app 走的是 **dev server 服务的当前源码**，
`curl -s http://127.0.0.1:5173/src/views/dev-assistant/DevAssistantView.tsx` 可验证指纹
（`assessRollbackSafety`/`trashNode` 命中、旧注释串 0 命中）。所以源码加固对运行中的 app 生效。

**闸门覆盖**：无快照 / 拍摄时 root 为空 / root 不同源 → 硬拦（不动文件）；删除比例 ≥50% 且现存 ≥4
→ `window.confirm` 确认。`snapshotWorkspaceFiles` 遍历的 `fileTree` 是 `buildFileTree` **递归预读**的
完整树（useFileSystem:402-432），无懒加载缺项问题。

1. `buildFileTree` 的 `catch` 在子目录 `readDir` 失败时**静默 `return []`**（useFileSystem:428-430）

   漏项 <50% 时不弹确认，但只**移进回收站**（可移回），不再是不可逆删除。
2. `saveFile` → `api.writeFile` 是**覆盖式直写、无备份**（useFileSystem:598-608）。回滚的「还原」

## 任务类型切换与会话上下文（11:47，咨询/无代码改动）

**问题**：对话中切换「任务类型」再继续聊，会不会影响上下文？现状是切换会新建对话。

**代码事实（已核实）**：

- 系统指令是**逐轮下发**、不固化在会话里：`useOpencodeChat.ts:70` 每次 `sendMessage` 重算
  `getDeveloperInstructions(roleType, username, moduleId)`，`:96` 作为 `session.prompt` 的
  `body.system` 传服务端；`roleType` 由 `useOpencodeClient.tsx:710` 用 `taskType || roleType` 注入。
- SDK `UserMessage`（`types.gen.d.ts:48-58`）带 `agent/model/system/tools` ⇒ 每条用户消息**存下**自己那轮的
  system 快照。
- **修正（11:55 核实，此前判断有误）**：服务端**只取最后一条用户消息的 system**，不是「按轮回放」。
  `packages/opencode/src/session/llm/request.ts::prepare()`：
  `system = [[agent.prompt ?? SystemPrompt.provider(model), ...input.system, ...(input.user.system ? [user.system] : [])].join("\n")]`，
  其中 `input.user` = `lastUser`；`processor.ts` 只把 `LLM.StreamInput` 原样透传给 `llm.stream`，不碰 system。
  ⇒ 角色指令是**追加**在默认 agent prompt 之后、**只对当前轮生效**；中途换角色不会污染历史轮次，
  「保留上下文换角色」机制上无障碍，且当前 DataForge 的角色提示词确实生效。
- 现状：`AIPanel.tsx:145-149 handleTaskTypeChange` 主动 `newSession()`，`handleNewSession`
  （`useOpencodeClient.tsx:1177-1197`）`resetState()` + `setCurrentSessionId(null)` ⇒ 下一轮
  `session.create` 开新会话，**旧上下文完全不进新会话**。
- `resetState`（`useOpencodeEvents.ts:356`）**只清本地状态、不删服务端会话**：旧对话仍在任务历史
  （任务下拉）里，可切回；不是数据丢失。
- 切类型**只换 `system` 文本、不传 `agent`**（`SessionPromptData.body.agent?` 未使用）⇒ 工具集与审批
  策略不随类型变。
- `TaskRecord` 只有 `sessionId/title/createdAt/updatedAt`（`useOpencodeClient.tsx:32-41`），**不记任务
  类型**；标题取首条消息前 80 字（`useOpencodeChat.ts:77`）。
- 数据探索模块的 `handleNewSession` 额外做「新建时间戳工作目录」并切过去
  （`useOpencodeClient.tsx:1181-1195`，会话=标签页）⇒ 那里的类型切换绑定了目录语义。

**结论**：机制上「保留上下文换角色」可行（去掉 `newSession()` 即可，只影响下一轮 system）；
代价是需给 `TaskRecord` 补类型标记、接受一次 provider prefix cache 失效、压缩摘要会跨角色。
但数据探索不能照搬（会共用工作目录）。**未改任何代码**。

## 调度模块：定时调度功能开发（15:30–15:50）

**需求**：完成调度模块的定时调度（DolphinScheduler Schedule）功能；**定时只对超级管理员与运维人员开放**。

**入口**：`ProjectDetailView.tsx` 工作流列表行内原有一个占位按钮
`onClick={() => setError('定时功能开发中...')}` —— 本次把它接到真实实现。

### 关键设计决策

1. **API 依据 DS 3.2 的 form-data 风格 v1 接口**（与既有 `workflow-definition` 命名同代）：
   - `POST /projects/{pc}/schedules`：form-data，其中
     `schedule=JSON.stringify({startTime,endTime,crontab,timezoneId})`，其余字段平铺
     （`workflowDefinitionCode / failureStrategy / warningType / warningGroupId /
     workflowInstancePriority / workerGroup / [environmentCode] / [tenantCode]`）。
     **注意是 `workflowInstancePriority`**（3.2 改名），不是 `processInstancePriority`。
   - `PUT /projects/{pc}/schedules/{id}`、`DELETE .../{id}`、
     `POST .../{id}/online`、`POST .../{id}/offline`、`POST .../schedules/preview`。
   - preview 返回形态跨版本不一致（`Result.data` / 裸数组 / `data.totalList`），已在 API 层归一化。
2. **一个工作流只有一个定时**：DS 重复创建会返回 `SCHEDULE_ALREADY_EXISTS`，所以弹窗先按
   `workflowDefinitionCode` 查已有定时 → 有则「编辑+上下线+删除」形态，无则「新建」形态。
3. **DS 硬约束**：定时上线要求**关联工作流已上线**（否则 `WORKFLOW_DEFINITION_NOT_RELEASE`）；
   已在启用前拦下并提示。启用状态下改 crontab 可能被拒（需先停用），已加非阻断提示。
4. **权限判定收敛为唯一真源** `src/utils/roleAccess.ts`：
   `PLATFORM_ADMIN_ROLE_NAMES` = 超管(`ROLE_ADMIN/ADMIN/SUPER_ADMIN/超级管理员`) +
   运维(`ROLE_OPS_ENGINEER/OPS_ENGINEER/运维工程师`)；`hasPlatformAdminRole(roles)`；
   `canManageSchedule(user)`（= `isSuperAdmin || hasPlatformAdminRole(roles)`）。
   **顺手去重**：`dev-assistant/ProjectList.tsx` 原本自带一份同内容数组 + `canManageProject()`，
   已改为复用该 util（无行为变更）。
   门禁做**双重防御**：父组件按钮 `disabled` + `title` 说明原因（沿用 ProjectList
   「无删除权限」的既有模式），弹窗内再拦一次提交。

### crontab 是 Quartz 方言（不是 Linux 5 段）

`src/utils/crontab.ts`（纯函数）：`parseCrontab / validateCrontab / describeCrontab /
nextFireTimes / isLocallyComputable / defaultScheduleRange / validateScheduleRange /
formatScheduleDateTime / zonedParts`。要点：
- 6 或 7 段（秒 分 时 日 月 周 [年]）；**周字段 1=周日**（与 JS `getDay()` 差 1）；
- **「日」「周」必须有一个是 `?`**，且不能同时为 `*`（Quartz 硬约束，最容易踩）；
- 只支持 `* ? , - /` 与日字段 `L`；`W` / `#` / `nL` **语法上接受但标记 `needsServerPreview`**，
  `nextFireTimes` 直接返回空 —— 宁可让用户去问调度系统，也不本地算错时间；
- 时区靠 `Intl.DateTimeFormat.formatToParts` 取墙上时间（`hourCycle:'h23'`，
  非法时区名回退本地时区不抛错）；
- **性能**：逐分钟空转会被「2 月 30 日」这类永不成立表达式放大到 2.5s（卡 UI）。
  已改成**日期不匹配时按天跳到目标时区次日 00:00**，最坏 366 次迭代，整文件从 2.5s → 78ms。
  按天跳跃必须用 `wallTimeToUtc`（迭代逼近）算「次日 00:00」的 UTC——
  **量偏差时必须带上时分秒**，只比日期会「看起来已收敛」而整体偏移一个时区偏移量
  （曾因此让跳跃落到当天 08:00、漏掉凌晨触发点，3 个用例当场抓住）。
  跨年那一刻同理不能用 `+24h` 硬跳。
