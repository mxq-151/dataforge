## 代码结构解耦审查与重构（审查 + 已实施）

对 /Users/mxq/Desktop/dataforge（Electron + React 19 + TS，约 5.5 万行）做了一次架构耦合扫描，随后按低风险优先顺序实施了 4 项解耦改动。全部通过 `tsc -p tsconfig.json --noEmit` 与 `vite build`。

### 关键事实（后续复查基线）
- 渲染进程宿主桥叫 `window.dataforge`（不是 window.electron），preload 走 contextBridge + sandbox + contextIsolation，安全边界正确。
- `src/bridge/` 是薄封装层（ipc/http/fs/store/shell/path/event），window.dataforge 基本收敛在此，仅 App.tsx 有 3 处越界。
- 主进程 `electron/backend/` 依赖无环：maven 是叶子 → compile/lspPom → compileServer → opencode；lspBridge 独立依赖 eventBus。
- opencode hooks 已拆为 backend / events / chat / sessions 四个子 hook，但编排层 useOpencodeClient 仍 1341 行。

### 发现的主要问题（严重度排序）
1. `src/components/editor/EditorAreaCopy.tsx` 与 `EditorAreaTest.tsx` **diff = 0 完全相同**，各 1030 行，无任何 import 引用 → 2060 行死代码。
2. `src/contexts/AuthContext.tsx:225/250` 直接 `invoke('start_opencode_after_login')` / `invoke('stop_opencode')`，且 login 内混入工作目录计算与 store 写入 → 关注点错配。
3. api 层请求基建 5 份平行实现：index.ts 的 `request()` 之外，codeExecution(6 处 fetch)、dolphinscheduler(4)、fileExplorer(3)、marquez(2) 各写各的超时/错误处理。
4. IPC 契约弱类型：`invoke<T>(cmd: string, args?: Record<string, unknown>)`，主进程用 `Record<string, fn>` 字符串分发，调用点靠手写泛型 + `as unknown as`。
5. `src/bridge/fs.ts` 缺 symlink 封装，导致 `src/App.tsx:442` 裸调 `window.dataforge.fs('symlink', ...)`。
6. hooks 层反向依赖组件层：`src/hooks/useProgramRunner.ts:9` → EditorArea；`src/hooks/opencode/useOpencodeClient.tsx:37` → FileReviewPanel。
7. `electron/backend/opencode.ts:16` 直接依赖 compileServer 拿 endpoint → 跨领域耦合。
8. 持久化方式不统一：LoginPage / DataExploreEditor 直接用 localStorage，而项目已有 bridge/store（userData/df-stores）。

### 客观说明（非深层耦合，勿误判）
- `task-forms.tsx` 2105 行实为 30+ 个并列独立表单（每个 30-80 行），属文件粒度问题，非逻辑耦合。
- views 层无硬编码 URL、未绕过 api 层、无 localStorage 滥用以外的越界。

### 6. 统一持久化（按分类原则，非一刀切）
- 新建 `src/utils/syncedStore.ts`：`SyncedStore` = 同步读写的持久化外观，init() 预热内存、
  写操作异步落盘。给 `bridge/store.ts` 加了 `snapshot()` 支持预热。
  **必须用 useMemo 缓存返回对象**，否则调用方把它放进依赖数组会导致 cleanup 反复触发。
- 新建 `src/utils/historyStore.ts`：统一查询/执行历史持久化 + 旧 localStorage 数据迁移。
- 已迁移（敏感/大数据）：LoginPage 记住的主机与**明文密码**、DataExploreEditor 查询历史、
  useProgramRunner 执行历史。后两者原先是几乎相同的重复实现，现已合并。
- **刻意保留 localStorage**：
  - UI 偏好（AIPanel 面板宽度、ExecutionResultTabs 高度、useTodoDockState 折叠态）
    ——同步读取、无敏感信息，异步化会拖慢首帧。

  - `useOpencodeClient.tsx` 的会话ID→工作目录映射 ——被 useRef 同步初始化，
    异步化会让首帧拿到空映射导致会话关联丢失；已在代码注释中固化此决策。

opencode 只依赖该注册表。main.ts 启动序列已保证 startCompileServer 先于 autoStartOpencode。

### 发现并修复
1. **循环依赖 ×2**
   - `ActivityBar ↔ AuthContext`（真实运行时循环）：菜单常量 MENU_CODE_MAP /
     FIRST_LEVEL_MENU_CODES 定义在 UI 组件里却被 AuthContext 引用 → 下沉到
     `src/types/index.ts`，ActivityBar re-export。顺带把 FIRST_LEVEL_MENU_CODES 改为
     `Object.values(MENU_CODE_MAP)` 派生，消除 10 个字符串的重复定义。
   - `rows.ts ↔ projection.ts`（仅类型循环，运行时安全但易恶化）：PartRef/PartGroup
     下沉到 rows.ts，projection re-export。
2. **层次违规 ×3（utils → api）**：utils/historyIsolation 取 getApiHost、
   utils/commitSummary 取 host/token、utils/extractMetrics 取 IndicatorDTO 类型。
   **根因**：会话配置寄居在胖模块 api/index.ts。
   → 新建 `src/session.ts`（host + token，只依赖 bridge/store，属最底层）
   → 新建 `src/types/indicator.ts`（DTO 下沉）
   → api/index.ts 与 api/indicator.ts 原样 **re-export**，既有 9 处引用零改动。
   注意：`export { x } from '...'` 不会让 x 在本地作用域可用，本地还要用需额外 import。
3. **SyncedStore 竞态（自己上一轮引入的缺陷）**：init() 进行中若发生 set()
   （此时 store 仍为 null，只写内存、未落盘），init 完成后 `cache = snapshot()` 会整体
   覆盖这次写入 → 数据静默丢失。改为合并（pending 优先）并把 pending 补写回磁盘。
4. 删掉上一轮写了却没派上用场的 `httpCore.buildUrl`。
