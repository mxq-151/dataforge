### 核心结论（改变了方案性质）

1. **两个模块都不是从零新增，而是补齐既有契约的两端。**
2. **数据质量**：规则契约已完整写在 `src/hooks/opencode/opencodeInstructions.ts`：
   - `QUALITY_RULE_SPEC`（L81-96）：**7 类规则类型**（主键唯一性/非空/值域/行数波动/行数环比/上下游对账/口径一致性），
     明令「三阶段同名词，禁止自造同义词」；S1 提要求 / S2 定规则名+校验对象+阈值+处置方式 / S3 独立成文件挂处理任务下游。
   - `LAYERING_SPEC`（L99-110）：**DQC 质量层 = 质量规则定义 + 稽核结果存储**；前缀 `dqc_`；`TABLE_NAMING_CONVENTIONS` 用 `dqc_`。
   - 文档命名规范：DDL 按分层拆文件 → `ddls/dqc_ddl.sql`。
   - 「数据质量校验规范」段（L580-585）：校验任务与处理任务分离、**输出须可定位（规则名/校验对象/阈值/实际值/是否通过）**、
     不通过时阻断下游或告警。⇒ **「阻断下游」的实现方式在提示词里已被约定为「独立质检任务挂下游」，不是 DataWorks 式的「反向置调度节点失败」。**
   - 结论：契约完备、落点缺失。质量模块设计第一原则 = 规则类型与 7 类同源（提示词/前端枚举/服务端枚举三处一致 + 单测断言）。
3. **质量侧是「半条链路」**：服务端 `modules/quality` 仅 7 文件 671 行 = `DataQualityCheckResult` 实体 + CRUD + 失败统计
   （`/quality/check-result` 四接口）；表 `data_quality_check_result` 是**接收结果**形态，「检查项」为自由文本 `varchar(200)`，
   未与 7 类枚举绑定。**缺：规则定义、模板、质检任务、触发、强弱处置、告警、界面、大盘。**
   桌面端全仓检索「数据质量」只命中提示词文件 ⇒ **零 UI**。
4. **资产目录的分类体系无需人工维护**：命名规范强制 `{分层}_{业务域}_{实体描述}_{刷新周期}` + 分层枚举（ods/dwd/dws/ads/dim/dqc/tmp）
   + 刷新周期后缀枚举（d/h/w/m/y/r/f）⇒ 分层与业务域可**从表名确定性解析**，解析失败即「未分类」并自动成为治理项。
   这是相对 DataWorks「人工维护业务分类树」的核心差异。
5. **资产属性存量比预期多**：`table_metadata` 已有 row_count/size_bytes/hot_days/cold_days/keep_days/partition_columns/
   storage_format/location/last_modify_time/sync_time + 表/字段双指纹；`column_metadata` 有 comment/is_partition/is_primary_key/nullable；
   `indicators` 有 **topic/business_owner/tech_owner/visibility/code/refresh_***，`indicators_fields` 建立 **指标 → 数据源/库/表/字段**。
   ⇒ `table_metadata` 的 owner/topic/visibility 改造应**对齐 `indicators` 既有语义**，不要另发明一套。
   `table_metadata` 缺：owner、分类、标签、热度、使用说明、资产等级。

### 两个关键判断（与评估稿不同，属"如实测所迫"）

1. **真目标只有 PG + MySQL**：查 pom.xml 发现**没有 h2、没有 mariadb 驱动**；PG 由 docker 部署
   （`run-dataforge.sh` 覆盖数据源），MySQL 是 `application.yml` 默认（本机实为 MySQL 9.6）。
   ⇒ init 四份都改以保持平行，migrate 只做 PG + MySQL 两份（不做 H2/MariaDB 迁移）。
2. **参考数据放 init 而非 testdata**：部署导入顺序是 init（`sys_user` 不存在时）→ testdata
   （`username='test'` 不存在时）。种子放 testdata 会导致"新装没有模板"，故规则模板与分层分类进 init；
   菜单仍只在 testdata（历史如此），已上线库由 migrate 补。

### 被真实执行抓出来的 bug（静态检查发现不了）

`table_metadata` 新增索引 `idx_table_metadata_owner` 建在 `business_owner varchar(1024)` 上
⇒ utf8mb4 下 4096 字节 > InnoDB 上限 3072 ⇒ **整张 table_metadata 建不出来**（不是只失败索引）。
`indicators` 的同名列是 1024 但故意不建索引，所以历史上没暴露。
修法：负责人列收窄到 `varchar(255)` 再建索引，并注明与 indicators 的宽度差异是有意的。

### 验证手法（已固化为 skill `dataforge-sql-dialect-verification`）

1. `df_sql_check.py` 静态：四方言表集合 / 新增表列一致 / 类型跨方言等价（integer≡int、timestamp≡datetime、
   text≡clob）/ **migrate 与 init 逐字一致** / 类型白名单（绝对校验，四方言都写错也能抓）/ 三方契约 /
   引号括号配平。
2. `verify_pg.sh`：一次性 `postgres:14` 容器。**用"执行 init 再把新增物删掉"模拟升级前的库**（不需要 git 历史），
   再跑两遍 migrate 验幂等；比对 fresh 与 upgrade 的 167 列 + 45 索引；另建库导入 testdata（6 角色）
   删菜单后重跑 migrate，验授权覆盖（asset_catalog→全部 6 角色含业务需求方/数据分析师，data_quality→4 个治理角色）。
3. `verify_mysql.sh`：本机无 mysql 客户端，改用 **Java 17 + JDBC**（`SqlRunner`，必须打印 ResultSet）
   对一次性库执行；自写切分器处理 `DELIMITER`（是 CLI 指令，JDBC 不需）。

结果：**PG 与 MySQL 两端全绿**，新装与升级 schema 完全一致（167 列 / 45 索引），migrate 各跑两遍幂等。
